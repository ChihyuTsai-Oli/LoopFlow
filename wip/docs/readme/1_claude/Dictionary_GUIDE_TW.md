# LoopFlow 2.0 — Excel 字典使用說明

> 本文件說明 `LoopFlow_Dictionary.xlsx` 的格式、欄位意義、撰寫規則，以及它跟 Rhino 模型之間的同步邏輯。指令怎麼操作見 [指令逐項說明](./COMMANDS_TW.md)；整體流程見 [使用說明總覽](./USER_GUIDE_TW.md)。

## 1　字典是什麼

`LoopFlow_Dictionary.xlsx` 是 LoopFlow 的**材質／工項預設值表（Type Catalog）**。

每一列代表一種材質或工項（稱為一個 **Type**），對應到 Rhino 裡的一個子圖層。執行 [04 Nexus](./COMMANDS_TW.md#04-nexus開案主控台) 的「同步 Type Layers」時，系統會依這份表建立圖層並帶入預設值；之後建模時把物件放到對應圖層，[寫入模型 Metadata](./COMMANDS_TW.md#5-寫入模型-metadata) 就會依物件實際使用的 Type 寫入資料。

字典管的是「這個 Type 預設長怎樣」，**不是**物件實際的現況——同一個 Type 底下的每個物件，仍然可以有各自不同的建構狀態、備註等內容。

## 2　檔案格式與放置位置

| 項目 | 說明 |
|---|---|
| 檔案名稱 | 預設 `LoopFlow_Dictionary.xlsx`，可以改用同一個工作檔資料夾裡的其他 `.xlsx` 檔名 |
| 放置位置 | 工作檔根目錄（環境變數 `LOOPFLOW_WORKFILES_ROOT` 指向的資料夾） |
| 格式要求 | 只支援 `.xlsx`；不接受 `.csv` 或 `.xls` |
| 工作表 | 使用第一張工作表，目前檔名為 `LoopFlow_Dictionary` |
| 第 1 列 | 版本標題列，例如 `LoopFlow Dictionary v2.0`（程式會跳過） |
| 第 2 列 | **欄位標題列**，欄名必須完全符合下方定義 |
| 第 3 列起 | 每一列代表一個 Type，對應一個 Rhino 子圖層 |

第一次執行「同步 Type Layers」時會跳出選檔視窗，選過一次後檔名會被記住（存在 Rhino 文件的 `lf_dictionary_filename`），之後不會再問，除非那個檔名被改掉、找不到。**系統不會自動掃描資料夾裡所有的 Excel 檔，也不會用檔名以外的方式亂猜。**

## 3　欄位說明（現行 15 欄）

字典目前有 15 欄，前 9 欄（含圖層路徑）是每個 Type 都要有的基本資料，後 6 欄（`Q_01`～`Q_06`）是保留給後續 Grasshopper 數量計算用的欄位，2.0 本身不計算也不下放到物件。

| 欄名 | 是否必填 | 說明 |
|---|---|---|
| `__Rhino Layer` | 必填 | 這個 Type 對應的完整 Rhino 圖層路徑（見「4　圖層命名規則」），是**同步時**用來對照圖層的鍵值，不是 Type 的正式編號 |
| `_01_空間名稱` | 留空 | 由模型自動計算，字典不需要填 |
| `_02_建構狀態` | 選填 | 這個 Type 新建圖層時的預設施工狀態：`New`／`Existing`／`Demolished`／`Relocated`。結構類通常填 `Existing`，其餘通常填 `New`。**只影響新建圖層的初始值**，之後每個物件可以自己改，不會被字典重新同步覆蓋 |
| `_03_ID編號` | 必填 | Type 的唯一編號，格式 `類別碼-序號`，例如 `EX-01`、`CL-03`（見「4　圖層命名規則」的類別碼表） |
| `_04_ID名稱` | 必填 | 人看得懂的材質／工項名稱，會顯示在 Tag 與圖說上，例如「鋁製檢修孔」 |
| `_05_高程基準` | 必填 | 這個 Type 預設用哪個基準量高程，只能是下列四種之一（見下表） |
| `_06_高程計算` | 留空 | 由模型自動計算，字典不需要填 |
| `_07_UUID` | 留空 | 物件的識別碼，由系統自動產生，字典不需要也不應該填 |
| `_08_備註` | 選填 | 預設備註提示，通常填 `(手動輸入備註)`，讓使用者在物件上自己填實際內容 |
| `Q_01_寬度W` | 留空 | 留給後續 Grasshopper 使用，2.0 不計算、不寫入物件 |
| `Q_02_深度D` | 留空 | 同上 |
| `Q_03_高度H` | 留空 | 同上 |
| `Q_04_單位` | 必填 | 工程估算單位（不是 Rhino 文件單位），例如 `cm`、`坪`、`才`、`組`（見「5　撰寫規則」） |
| `Q_05_計量規則` | 必填 | 這個單位要用哪種方式計算數量（見「5　撰寫規則」的計量規則表），現行 92 筆已全部填妥 |
| `Q_06_實作數量` | 留空 | 留給後續 Grasshopper 計算，2.0 不計算 |

### `_05_高程基準` 可用值

| 縮寫 | 全名 | 說明 |
|---|---|---|
| `BH` | Bottom Height | 從物件**底面**量高程 |
| `TH` | Top Height | 從物件**頂面**量高程 |
| `CH` | Ceiling Height | 從**天花板底面**量高程（燈具、天花材料適用） |
| `BC` | Bottom + Ceiling | 同時參考底面與天花板（設備類常用） |

## 4　圖層命名規則

`__Rhino Layer` 欄的格式是：

```text
頂層群組::英文名稱.中文名稱
```

例如 `01_Ceiling_天花::Access_Panel.檢修口`。目前字典有 **12 個頂層群組**，各自對應固定的類別碼前綴：

| 類別碼 | 頂層群組 | 範例（ID編號／ID名稱） | 高程基準 | 常見 `Q_04` 單位／`Q_05` 計量規則 |
|---|---|---|---|---|
| `EX` | `00_STR_結構` | `EX-01`／鋼筋混凝土（樑） | `BH`／`TH` | `m3` / `VOL_WDH`；`cm` / `LEN_W`；`坪` / `AREA_WD`；`座` / `COUNT` |
| `CL` | `01_Ceiling_天花` | `CL-01`／鋁製檢修孔 | `CH` | `片` / `COUNT`；`坪` / `AREA_WD`；`cm` / `LEN_W` |
| `WL` | `02_Wall_牆面` | `WL-01`／輕隔間牆 | `BH` | `cm` / `LEN_W` |
| `FL` | `03_Floor_地坪` | `FL-01`／陽台磁磚地坪 | `TH` | `坪` / `AREA_WD` |
| `CB` | `04_CB_櫃體` | `CB-01`／木作櫃體 | `BH` | `mm` / `LEN_W` |
| `LS` | `05_LT_燈帶` | `LS-01`／天花燈帶 | `BH` | `cm` / `LEN_W` |
| `EL` | `06_EL_電控系統` | `EL-01`／對講機 | `BC` | `組` / `COUNT` |
| `MP` | `07_MEP_空調機電` | `MP-01`／空調面板 | `BC` | `組` / `COUNT` |
| `SA` | `08_SAN_衛浴設備` | `SA-01`／浴缸 | `BC` | `組` / `COUNT` |
| `EQ` | `09_EQP_專用設備` | `EQ-01`／影音設備 | `BH` | `組` / `COUNT` |
| `FP` | `10_FP_消防系統` | `FP-01`／緊急照明燈 | `BC` | `組` / `COUNT` |
| `DW` | `20_DW` | `DW-01`／門窗 | `BH` | `樘` / `COUNT` |

`04_CB_櫃體` 只是一般材質分類，跟日後獨立的櫃體工具（不屬於 2.0）無關，不要混淆。

### `20_DW`（門窗）是特例

門窗的資料寫在**圖塊本身**（見 [Tag Block 說明](./TAG_BLOCKS_TW.md#dw-tag--門窗標註)），不是寫在子圖層上，所以 `20_DW` 這一列的備註直接寫明「Block 放在此圖層，資料寫在 Block，不寫在子圖層」。同步時 `20_DW` 只當成單一 Type，排除底下的子圖層。

## 5　撰寫規則與注意事項

- **`_03_ID編號` 格式固定為 `類別碼-序號`**（例如 `EX-07`），載入時會嚴格拆分驗證，類別碼要跟圖層所在的頂層群組一致。
- **`Q_04_單位` 與 `Q_05_計量規則` 的量綱要一致**，否則載入字典會直接被擋下。允許的計量規則與對應量綱：

  | 計量規則 | 量綱 | 允許的 `Q_04` 單位 |
  |---|---|---|
  | `COUNT` | 計數 | 樘、片、組、台、座 |
  | `LEN_W`／`LEN_D`／`LEN_H` | 長度 | cm、mm |
  | `AREA_WD`／`AREA_WH`／`AREA_DH` | 面積 | 坪、才 |
  | `VOL_WDH` | 體積 | m3 |

  換算常數：`坪 = 指定面積（m²）× 0.3025`；`才 = 指定面積（cm²）÷ (30.3 × 30.3)`。這些換算是保留給後續 Grasshopper 使用，**2.0 本身不會從模型幾何實際求值**。
- `_08_備註` 建議統一填 `(手動輸入備註)` 當預設提示，讓使用者在物件上一眼看出這欄是空的、該自己填。
- Excel 維持**中文顯示欄名**（如上表），程式載入後會自動轉換成內部使用的英文欄位，使用者不需要處理這一層轉換。
- **欄名、欄數跟目前的 15 欄定義不符時，會直接停止載入**，不會靠猜測比對欄位，所以不要自己改欄名或调整欄位順序範圍以外的內容。
- 字型：繁中版統一用**微軟正黑體 10**。

## 6　字典與 3dm 的關係邏輯

執行 [04 Nexus](./COMMANDS_TW.md#04-nexus開案主控台) 「同步 Type Layers」時的合併規則：

- **字典有、Rhino 沒有的圖層**：自動建立該圖層，並把字典裡的 `_02_建構狀態` 當作**這個圖層新建物件的預設值**寫入圖層屬性，不是寫進每個物件。
- **Rhino 已經有的同名圖層**：**保留既有內容**，字典不會覆蓋。
- **物件的實際現況只由物件自己維護**：重新同步字典，不會覆寫任何物件上已經填好的資料，也**不會把物件現況回寫到字典**——字典跟模型是單向關係（字典 → 新圖層預設值），不是雙向同步。
- 新建 Type 圖層時，系統會在原點放一個 `DNA_REF_` 參考點，避免這個空圖層被 Rhino 的 Purge 清除；重新同步時會依 Type 編號更新或取代這個點，不會一直累加新的點。
- 圖層顯示色會依類別碼前綴自動套用；新建材質名稱會是去掉專案前綴的相對路徑，顏色跟圖層一致。如果 Rhino 裡已經有同名材質，只會掛接使用，**不會改動使用者已經調整過的顏色**。

簡單說：**字典負責「這個 Type 一開始長什麼樣」；已經建好的圖層跟已經存在的物件，改動權都在 Rhino 端，字典不會回頭覆蓋。**

## 7　`Q_01`～`Q_06` 數量欄目前的定位

這 6 欄留在字典裡，但 **2.0 完全不使用**：不會下放到物件、不會出現在發布出去的 Registry、也不會在 Nexus 的資料化流程裡被計算或驗證幾何。現行 92 筆資料裡，`Q_04_單位` 與 `Q_05_計量規則` 已經全部填妥（供未來換算使用），`Q_01`～`Q_03`（寬深高）與 `Q_06`（實作數量）則留白，等後續 Grasshopper 工作流程接手。

## 8　核對模型與字典的差異

字典跟模型現況難免會慢慢出現落差（例如建模過程中臨時調整了某個圖層）。核對流程：

1. 執行 [03 匯出字典](./COMMANDS_TW.md#03-匯出字典)，把 Rhino 現況匯出成 `{原檔名}_Export.xlsx`。
2. 執行 [02 開啟匯出字典](./COMMANDS_TW.md#02-開啟匯出字典) 打開來看，比對 `diff_status` 欄的顏色標示（紅＝字典有模型沒有、藍＝模型有字典沒有、橙＝內容不同）。
3. 打開 [01 開啟正式字典](./COMMANDS_TW.md#01-開啟正式字典)，**手動**把需要的修改抄回正式字典。藍字（模型新增）併回去時，記得給一個字典裡還沒用過的 `_03_ID編號`。

這份匯出檔**只供核對，永遠不能取代正式字典**，程式也不會自動幫你合併。

## 9　中途切換字典檔案（不建議）

`lf_dictionary_filename` 只記住檔名，換成另一份 `.xlsx` 之後，新檔案裡沒有涵蓋到的 Type 就無法再被同步邏輯辨識。如果真的需要換檔，建議先用「8　核對模型與字典的差異」的流程確認新舊字典的 Type 編號、欄位定義是否一致，避免既有物件的 `_03_ID編號` 在新字典裡對不到 Type。
