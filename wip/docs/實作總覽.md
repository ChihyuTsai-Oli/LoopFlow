## 產品工作鏈

LoopFlow 的核心工作邏輯是：

```text
Type Catalog／Dictionary
→ 建立 3D 模型
→ 建立 Space Boundary
→ 掃描、注入並驗證模型資料
→ 發布 Registry revision
→ 建立 Section／View
→ 產生可獨立編輯的 Drawing
→ 建立 Sheet／圖框
→ 建立並綁定 Tag
→ 同步顯示資料
→ Health 檢查與可預覽修復
```

使用者決定何時執行、處理哪些問題、採用哪次更新，以及是否覆蓋可重建成果。系統不得把這條半自動工作鏈改成不可中斷的一次性操作。

## 不可破壞的架構原則

1. Dictionary 是 Type Catalog；3D Object 保存 instance 現值。
2. Layer 是人類分類入口，不是永久資料 ID。
3. Registry 是版本化唯讀發布快照，不是另一份人工資料庫。
4. Section 產生的 Drawing 可獨立編輯；更新不得靜默覆寫人工成果。
5. Sheet metadata 是圖框與輸出命名的真相；Layout 名稱只是輸出。
6. 一般 Tag 綁定穩定 Object／View／Sheet ID；位置只協助找候選。
7. 狀態、revision 與問題是正式資料；顏色只作可復原提示。
8. 每個階段都可預覽、單獨執行、驗證、重跑、取消與復原。
9. 每個產生幾何或改寫資料的指令都有冪等政策，且能辨認前次產出。
10. ID 變更前先列影響、建立 mapping 並可 rollback；不得靜默換號。
11. 模型單位與工程估算單位分離；所有量綱常數具名並標註單位。

## 正式資料實體

| 實體 | 穩定身分 | 唯一責任 |
|---|---|---|
| Project | `project_id` | 工作檔根目錄、schema、發布與 revision 範圍 |
| Type | `type_id` | Dictionary 預設、顯示資訊、估算規則與 layer mapping |
| Model Object | `object_id` | 3D instance 現值、尺寸、空間、高程與 revision |
| Space | `space_id` | 空間顯示名稱、`level_id` 與 boundary |
| View | `view_id` | Section／平面方向、範圍與固定 2D↔3D transform |
| Drawing | `drawing_id` | 可編輯 2D 成果、來源 revision、provenance 與人工狀態 |
| Sheet | `sheet_id` | 圖種、樓層、序號、圖名、比例與版次 |
| Tag | `tag_id` | Template、binding、人工鎖定、同步 revision 與 health |
| Registry Revision | `registry_revision` | 經驗證後發布的唯讀模型快照 |
| Health Issue | `issue_id` | 問題原因、影響、修復建議與結果 |

## 模組邊界

```text
wip/src/
  loopflow/
    bootstrap.py
    command_catalog.py
    features/
      project/        # NX-01 Console 開案檢查
      dictionary/     # C01 Type Catalog 載入／驗證；NX-02 layer 同步
      model_data/     # NX-03 Space；NX-04 物件 ID；NX-05 命中與高程
      dimension/      # C05 local frame／W／D／H／quantity；NX-06 已接 Nexus Scan／Apply
      registry/
      view/
      drawing/
      sheet/
      tagging/
      health/
      drawing2d/
    platform/
      rhino/
      excel.py        # C01 簡單 xlsx，不依賴 openpyxl
      files.py
    foundation/
      config.py
      paths.py
      logging.py
      results.py
      atomic_io.py
      version.py
  entrypoints/
wip/tests/
wip/fixtures/
```

- `entrypoints/` 只轉交 command，不保存第二份業務邏輯。
- `features/` 依一起變動的功能群組織，不按舊按鈕一檔一模組硬切。
- `platform/` 隔離 Rhino、Excel 與檔案系統副作用。
- `foundation/` 只放跨 feature 的小型共用能力。
- `LF_Nexus` 是 Project Console／指令入口，不再同時承擔 UI、幾何、Excel、Registry 與所有規則。C02 的工作包見 `Nexus拆分計畫.md`。

## 安全基礎

### Registry

- 使用真正的 exclusive lock，包含 PID、主機與時間。
- 取得 lock 後重新讀取，不以先讀後鎖覆寫別人更新。
- 寫入 pending，flush 並完整驗證後再 atomic replace。
- 發布失敗時保留 last-good，不先刪除正式檔。

### Rhino 狀態

- selection、lock、visibility、color 與 modified state 由 platform adapter snapshot／restore。
- 成功、取消、失敗與 exception 都必須驗證復原結果。
- Health 本身唯讀；套用顏色或 Repair 是另外的明確動作。

### Migration

- 舊資料只由獨立 scanner／converter 處理。
- 流程固定為掃描、報告、使用者確認、備份、轉換、2.0 validator、失敗 rollback。
- 日常指令不雙讀、雙寫或偷偷改名。

## 實作關卡

1. **契約關卡**：canonical schema、Block manifest、fixtures、validator 與 migration mapping 完成。
2. **最小架構關卡**：bootstrap、command catalog、foundation、Rhino adapter 與測試骨架可載入。
3. **核心資料鏈關卡**：Dictionary → Object → Registry 可以安全完成並重跑。
4. **圖面與 Tag 關卡**：View → Drawing → Sheet → Tag → Sync → Health 接通。
5. **實機關卡**：Rhino 8 測試正常、取消、失敗、中斷、重跑與人工成果保護。
6. **發布關卡**：migration、installer、RC、rollback 與 checksum 通過後才合入 `main`。

## 每批完成條件

- 一批只處理一個安全問題或一條 feature。
- contract／fixture／自動測試與適用的 Rhino 實機測試通過。
- 沒有非預期 Rhino 狀態、資料或 last-good 損失。
- 文件、task status、驗證結果與限制同步。
- Git diff 不含秘密、快取、私人工作檔或無關變更。
- commit、push、回復點與未驗證項目可追溯。
