# LoopFlow Toolkit — 1.x 程式盤點

> 本文件記錄現況證據，不把 1.x 的檔案結構或副作用視為新產品契約。

## 1　候選範圍

| 現行檔案 | 行數 | 主要功能 | 風險 |
|---|---:|---|---|
| `LF_2D_Shelf_Gap.py` | 93 | 依矩形、方向、板厚與目標間距產生等距層板／隔板線 | 中低 |
| `LF_2D_Cabinet_Gen.py` | 199 | 由矩形產生四種櫃體 2D 符號；衣櫃含隨機衣架 | 中 |
| `LF_2D_DW_Gen.py` | 509 | 8 種門、3 種窗；含動態方向 preview、layer 與線型 | 高 |
| `LF_Cabinet_Suite.py` | 706 | 3D 櫃體、層板／隔板、`_CB.*` 寫入與 BOM updater | 很高 |

repo 裡只找到上述三支 `LF_2D_*`。2.0 契約把 `LF_Cabinet_Suite` 列為第四支未納入功能；使用者本輪是否確實要包含 Suite，仍待裁決。

## 2　三支 2D 工具

### 2.1 `LF_2D_Shelf_Gap`

- 輸入：X／Y 方向、單選或多選矩形、板厚、目標間距
- 算法：`round((L - target_spacing) / (thickness + target_spacing))`，再平均分配實際間距
- 輸出：每塊板一個封閉 polyline；每個櫃體各成一組
- 優點：邏輯小、沒有 LoopFlow 資料依賴，最適合第一支重建
- 問題：UI、計算與文件寫入在同一函式；所有常數假設 cm；摘要只回報最後一個矩形；exception 時沒有保證恢復 redraw

同一個分隔算法在 `LF_Cabinet_Suite.run_shelf_gap()` 又寫了一次。新 Toolkit 應只保留一份純計算核心，2D 與 3D adapter 各自把結果轉成線或實體。

### 2.2 `LF_2D_Cabinet_Gen`

- 輸入：四種櫃型之一與一條矩形曲線
- 輸出：外框、內框、對角線／吊衣桿／衣架並群組
- 相依：1.x `_LoopFlow_Config.py` 的 layer 名稱與顏色
- 會把使用者選到的原矩形改到輸出 layer
- 衣架位置與角度使用 global `random`，同一輸入每次結果不同，也無法可靠作 golden test
- 關閉 redraw 後若 offset、centroid 或中途幾何失敗，沒有 transaction 保證恢復
- 現行 tall／low 分支在迴圈內重複 `extend(lines)`，顯示單檔腳本已不適合繼續堆功能

應把隨機來源注入 geometry function：正式操作可每次產生新 seed，測試使用固定 seed；若要重建同一組輸出，metadata 保存 seed 與參數。

### 2.3 `LF_2D_DW_Gen`

- 8 種門、3 種窗，這 11 種幾何是最重要的領域知識
- 門以 A／B 兩點、牆厚、方向 flip 與部分型式參數產生；窗另有分割數
- 動態 preview 與最終 bake 共用部分 geometry function，方向正確
- `setup_layers()` 在使用者選型前就建立／修改 layer；即使取消，也可能改變文件
- 會修改既有 layer 的 PlotWeight；這是全文件副作用，不應由單一小工具靜默執行
- layer、line type、bake、group、UI 與 11 種幾何規則混在同檔
- 數十個 1、2、3、4、5、6、12、45、65、90 cm 常數沒有具名契約與單位轉換

這支不應直接拆段複製。先為 11 種型式建立參數 fixture 與期望幾何，再把 `calculate_*` 重建為「只回傳記憶體幾何、不碰文件」的 functions。

## 3　`LF_Cabinet_Suite`

現行單檔同時負責：

1. Eto launcher 與操作狀態
2. 3D carcass／門片／玻璃產生
3. 3D Shelf／Divider 產生
4. `_CB.01`～`_CB.04` UserText 寫入、舊 key 清除與物件命名
5. BOM updater：由幾何位置、體積比、world axis 與舊值猜零件種類／尺寸

主要風險：

- 產生成功後直接刪除使用者選取的輸入 box
- `write_cabinet_tags()` 先把三邊排序，會丟失 local L／W／T 語意
- updater 以 world X／Y／Z、最大面、位置與 0.2 cm 補差猜分類，旋轉櫃體與人工修改可能被誤判
- updater 會刪除大量歷史 UserText key；這不是單純產生幾何
- `_CB.01`～`_CB.04` 已明確不屬於 2.0 schema，不能照舊宣稱需再跑 Nexus／TagTrigger
- `rs.Command()`、selection、redraw、Boolean、臨時幾何與資料寫入沒有完整 transaction
- error dialog 寫死單機路徑，不能跨電腦

因此 Suite 不應當成「第四支腳本」原樣搬入。至少要拆成：

- `cabinet_3d_generate`
- `cabinet_3d_dividers`
- `cabinet_bom`／`cabinet_metadata`

其中 BOM／metadata 在資料契約定案前保持 experimental，不登錄正式工具列。

## 4　共同缺口

- 沒有單一 command／feature catalog
- 沒有版本化 input、output 或 settings schema
- 沒有一個 command 一個 undo record 的 transaction
- 取消、失敗、exception 時不保證 selection、current layer、redraw 與臨時物件復原
- cm 常數散落，非 cm 文件會產生錯誤尺度
- 沒有 unit tests、golden geometry、Rhino integration tests
- 檔名、UI、geometry、bake、layer 與資料寫入互相直接依賴
- 新增功能只能複製舊檔；刪除功能則會同時影響工具列、設定與使用者既有輸出
