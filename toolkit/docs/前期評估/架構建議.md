# LoopFlow Toolkit — 架構建議

## 1　產品邊界

**已定案（TKO-02，2026-09-03）**：比照 QTY，Toolkit 留在同一 repo 的 `toolkit/`，但作為獨立產品：

- 不 import `v2/src/loopflow` 或 `qty/src`
- 不進 LoopFlow 2.0 的 Yak、RUI、版本號或完成條件
- 自己的 Python package、tests、assets、版本與 `loopflow-toolkit` Yak
- 可獨立安裝，也可和 LoopFlow 2.0 同時存在

2.0 規劃文件原本寫「未來獨立 repo `Loopflow_Toolkit`」，使用者已明確指定在 `LoopFlow/toolkit/` 作業。對目前只有數支工具、需要共用 CI 與多人接手的狀況，同 repo／不同產品比立刻拆 Git repo 更省維護；日後 package 邊界穩定，仍可完整抽離。2026-09-03 已依此定案同步改寫 `v2/docs/` 六份實作文件與工作區根目錄的 `工作檔路徑.md`、`雙電腦作業.md`，避免出現「文件說要另立 repo、實際卻在同 repo」的矛盾。

## 2　一個產品，不是一個巨型工具

建議發布一個 Toolkit 安裝包，但每項功能是獨立 feature：

```text
Toolkit launcher
    ├─ 2D Shelf Gap
    ├─ 2D Cabinet Symbol
    ├─ 2D Door / Window Symbol
    ├─ Cabinet Group               （建立／命名／改名；已裁決，不受 Cabinet Suite 影響）
    ├─ Cabinet Group Check         （唯讀檢查，零寫入）
    ├─ 3D Cabinet Generator        （待確認／可 experimental）
    ├─ 3D Cabinet Dividers         （待確認／可 experimental）
    └─ Cabinet BOM / Metadata       （資料契約未定前不發布）
```

這樣新增或停用某支工具，只會改 feature catalog、該 feature 與測試；不需複製一套 layer、unit、undo、error 與安裝程式。

## 3　建議目錄

```text
toolkit/
├─ src/loopflow_toolkit/
│  ├─ catalog.py                 # 唯一 feature／command 登錄表
│  ├─ contracts.py               # typed input、result、status、provenance
│  ├─ foundation/
│  │  ├─ units.py
│  │  ├─ settings.py
│  │  ├─ errors.py
│  │  └─ result.py
│  ├─ geometry/                  # 不碰 Rhino 文件
│  │  ├─ equal_division.py
│  │  ├─ cabinet_symbol_2d.py
│  │  ├─ door_window_2d.py
│  │  ├─ cabinet_3d.py
│  │  └─ obb_zup.py              # 凸包＋旋轉卡尺求最小面積矩形
│  ├─ features/                  # 每支工具的 use case
│  │  └─ cabinet_group/          # 建立／命名／改名、Check、QTY 交接輸出
│  ├─ platform/rhino/            # prompt、preview、layer、bake、undo、restore
│  ├─ commands/                  # 極薄 Rhino entrypoints
│  └─ runners.py                 # command ID → runner；只查表轉交
├─ tests/
│  ├─ unit/
│  ├─ contract/
│  ├─ golden/
│  └─ rhino/
├─ assets/                       # RUI、icons、packaged defaults
└─ docs/
```

依賴方向固定為：

```text
commands/UI → features → geometry/contracts/foundation
      │
      └─────→ platform/rhino
```

`geometry` 不 import UI、rhinoscriptsyntax 或文件 adapter；`platform/rhino` 不決定門窗／櫃體商業規則。

## 4　Feature catalog 與入口

**強烈建議**以 typed Python catalog 作唯一登錄，不把功能清單散在 RUI、README 與多個 entrypoint：

| 欄位 | 用途 |
|---|---|
| `feature_id` | 永久 machine ID，不隨檔名或顯示名稱改變 |
| `command_id` | **正式 Rhino 指令名，無底線**（`LFCabinetGroup`），沿用 2.0 慣例 |
| `dev_entry_id` | 開發期入口 ID，可用底線（`LF_Cabinet_Group`）；不是對外指令名 |
| `display_name` | launcher／工具列顯示名稱 |
| `category` | `2d`、`3d`、`data` |
| `runner` | 實際 use case |
| `status` | `experimental`、`stable`、`deprecated`、`removed` |
| `capabilities` | 會建立／刪除幾何、寫 metadata、需要選取等 |
| `tool_version` | 寫入 provenance 與錯誤報告 |

入口採混合方式：

- 一個長期穩定的 `LFToolkit` launcher，新增功能時自動依 catalog 出現
- 每支穩定工具仍有直接 command，方便快捷鍵與 RUI
- RUI 只放 launcher 與少數高頻穩定功能；不要每新增一支就要求使用者重排整套工具列

**指令命名（TKO-12）**：Rhino 指令名在同一個 Rhino 裡是全域的，Toolkit 與 LoopFlow 2.0 可能同時安裝，因此沿用 2.0 的既有慣例——正式指令一律無底線，開發期入口才用底線；兩者在 catalog 分欄登錄。發布前必須與 `v2/docs/指令名稱.txt` 對照，確認沒有撞名。

## 5　新增、修改、停用與移除

| 生命週期 | 行為 |
|---|---|
| `experimental` | launcher 明確標示；不承諾資料向後相容 |
| `stable` | command ID、input contract 與輸出 provenance 受相容性保護 |
| `deprecated` | launcher 顯示替代功能與預定移除版；現有輸出不受影響 |
| `removed` | 不再執行，但 catalog 保留 tombstone 一個發布週期，說明替代方式 |

移除軟體功能**不得刪除模型裡既有幾何或 metadata**。修改已生成輸出的預設策略是「產生新的」；若未來提供 regenerate／replace，必須先 preview 差異、辨識人工修改並明確確認，不靜默覆寫。

## 6　輸出 provenance

為了日後知道「這組線是哪支工具、哪版、哪些參數產生」，建議對新建輸出使用 Toolkit 自己的 namespace：

```text
lftk_schema_id
lftk_schema_version
lftk_feature_id
lftk_tool_version
lftk_instance_id
lftk_params
```

- 2D 工具的 provenance 只服務追蹤、選取與未來 regenerate，不是 LoopFlow 2.0 資料真相
- 不寫 `Q_*`、`lf_*`、`_CB.*` 或 2.0 canonical keys
- 3D Cabinet metadata 必須先以 2.0 Verify／Publish 實機測試，確認不造成主鏈問題才可升 stable
- 若使用者拆 group 或人工改線，幾何仍屬使用者成果；Toolkit 不自動修復

## 7　設定與單位

設定優先序建議：

1. 安裝包內版本化 defaults
2. 選用的專案設定 `<3dm>/_LoopFlow_Config/loopflow_TOOLKIT/settings.json`
3. 當次 UI 輸入

`_LoopFlow_Config/` 是各產品共用的命名空間，2.0 已登錄 `loopflow`、`loopflow_R2B`、`loopflow_R2O`、`loopflow_QTY`。Toolkit 依同一風格用 `loopflow_TOOLKIT`，並須登錄進 `v2/docs/資料契約.md` 與 `系統設定.md`，不得各產品自行佔名（TKO-21）。

設定不得引用某台電腦的絕對路徑；未知 schema version 停止載入該設定，不猜欄位。

所有領域常數標示物理單位，透過 unit adapter 轉成文件單位。初版至少驗證 cm 與 mm；不可再把 `1.8`、`12.0`、`90.0` 無條件當成目前 model units。

## 8　Rhino 文件安全

每次 command 必須：

- 計算與 preview 階段零寫入
- 確認後才開一個 undo record 並一次 bake
- 取消／錯誤時不建立 layer、不改 PlotWeight、不留下臨時幾何
- 恢復 selection、current layer、redraw 與原有物件屬性
- 不刪使用者輸入；若某流程確實需要 consume input，另列明選項並再次確認
- 回傳 created／skipped／failed 的 typed result，不以空 stdout 當成功

產生器成功後 `doc.Modified = true` 是預期結果；關鍵是取消或失敗時不能留下部分變更。

## 9　Cabinet Group 與 QTY 交界

完整櫃體不建立為 Block，改以 Rhino Group 組織，讓群組內每個零件仍可使用 LoopFlow Tag。這個選擇不改 Nexus：Nexus 繼續逐物件處理；Toolkit 只負責建立／檢查群組，QTY 才把群組當成一筆幾何量測單位。

### 9.1 唯一權威與命名

- QTY 只認 Rhino Group Table 的真正 Group Name，不讀成員的「物件名稱」來判斷群組。
- Group Name 使用保留前綴 `QTY_CB_`，唯一且可辨識，例如 `QTY_CB_001_主臥櫃`；前綴只供 QTY 找出櫃體群組，不編入高／矮、深／淺或特殊櫃代碼。
- **命名格式、類別表、比對規則與唯一性防護以 [`qty/docs/前期評估/群組前綴名稱.md`](../../../qty/docs/前期評估/群組前綴名稱.md) 為唯一來源**，Toolkit 是寫入端、QTY 是讀取端，兩邊不各自維護一份規則。特別注意該檔 §5：worksession attach 的群組名稱會帶 `<來源檔名> : ` 前綴，直接用 `startswith("QTY_")` 比對會從 2D 側一個都找不到且不報錯。
- `SetGroupName` 已直接寫入真正名稱，不需要再同步。
- **不提供物件名稱轉群組名稱的同步指令**（2026-09-03 裁決取消，見 TKO-15 修正）。命名一律由 `LFCabinetGroup` 直接寫入真正 Group Name；成員的「物件名稱」永遠只是屬性，不是識別來源。

### 9.1.1 Rhino 群組生命週期（2026-09-03 實測，決定工具行為）

> 命名格式與類別見 [`群組前綴名稱.md`](../../../qty/docs/前期評估/群組前綴名稱.md)；本節只談 Rhino 的行為與工具必須做的防護。

| 動作 | Rhino 實際行為 | 工具必須怎麼做 |
|---|---|---|
| 解散最外層群組 | 該群組名稱直接消失（群組表留空殼、成員 0），**子群組不受影響**；index 不回收 | 名稱視為可拋棄；不要把 Group Index 當識別，也不要試圖「還原」舊名 |
| 解散後重新成群 | 得到**新 index 與自動名稱**（`Group01` 之類），舊名不會回來 | 重新命名一次即可；但必須確認選取的是完整成員集合 |
| `Groups.Add` 指定已存在的名稱 | **靜默改名**加流水號：`QTY_CB_TEST` → `QTY_CB_TEST01` → `QTY_CB_TEST02`，不報錯 | 寫入後**讀回實際名稱核對**；與請求不符要當場告知，不可假設寫入成功 |
| `ChangeGroupName` 改成已存在的名稱 | 回傳 `false`，名稱維持原狀 | 檢查回傳值；失敗要明確提示，不可靜默略過 |
| `_Copy` 複製整組已命名櫃體 | 複本自成**新群組但沒有名稱**（自動名），不會併入原群組 | 複製出來的櫃體不會污染原櫃體，但也不會自動有名字；Check 必須把它列為待命名，否則數量表會靜默少一個櫃 |

因此「解散重組」對使用者只是「再命名一次」，工具不需要保存或追蹤舊 Group Index；真正需要防的是**重新選取時漏掉零件**，這由 Check 負責。

### 9.2 建議指令責任

| 正式指令 | 開發期 ID | 責任 |
|---|---|---|
| `LFCabinetGroup` | `LF_Cabinet_Group` | 將選取零件建立為最外層櫃體群組並直接設定真正 Group Name；選取內容已在群組內時判斷是「改名」還是「再包一層」，不盲目加深巢狀。寫入後讀回實際名稱核對（Rhino 會靜默加流水號） |
| `LFCabinetGroupCheck` | `LF_Cabinet_Group_Check` | 唯讀檢查並報告，不改幾何、不改名 |

只有這兩支。原先規劃的第三支 `LFCabinetGroupSync`（物件名稱 → Group Name）已於 2026-09-03 取消：實測工作檔的成員完全沒有物件名稱，這支工具在真實模型裡沒有輸入可用，留著只會多一份要維護的寫入路徑。

命名與檢查都必須辨認外層群組。若兩個群組的成員集合互相重疊、且任何一方都不是另一方的完整子集合，視為交叉衝突；不得依 Group Index、`Group03` 之類自動名稱或選取順序猜測。

Check 至少要涵蓋（2026-09-03 實測後補齊）：

1. 真正 Group Name 存在、帶 `QTY_CB_` 前綴且唯一；**已成群但未命名**（複製、解散重組後最常見）必須列出
2. 最外層成員集合正確；巢狀子群組不得各自重複計量。若 `QTY_CB_` 名稱被誤寫在子群組上，該群組與外層互為子集合，必須當成重疊衝突報告
3. 交叉／重疊群組衝突
4. OBB 可量測性（成員數為 0、退化幾何、方向無法推定）
5. **位於櫃體圖層、卻不屬於任何 `QTY_CB_` 群組的零件**（TKO-19）——實測工作檔中 04_CB 圖層 29 個物件裡就有 7 個未成群，只掃群組會靜默漏掉
6. **成員的 `_09_空間ID`／`_01_空間名稱` 是否一致**（TKO-20）
7. 群組內混入非櫃體圖層物件

第 5 項只報告不自動成群；是否提供「一鍵成群」另行裁決。

### 9.3 QTY 量測契約

QTY 集合真正 Group Name 對應的全部成員，固定世界 Z 為高度軸，只在 XY 平面推定主要方向並計算 OBB：

- 高：世界 Z 範圍
- 長：方向校正後較長的水平尺寸
- 寬：方向校正後較短的水平尺寸

輸出忠實反映完整群組的外包尺寸，不套標準值、不自動分類，也不因不規則／弧形而改成另一套算法。人工分類、單位與估價判斷留到 QTY 輸出階段；幾何量測值仍保留作依據。

方向推定以**凸包＋旋轉卡尺求最小面積矩形**實作，不得只取單一最長邊。2026-09-03 於 `LoopFlow_3D.3dm` 實測：同一組幾何（體積皆 `95035.7251 cm³`）旋轉 0° 與 30°，World bbox 分別為 `100 × 36.746 × 75` 與 `104.976 × 81.823 × 75`，方向校正後 Z-up OBB 都是 `100 × 36.746 × 75`。

### 9.4 空間歸屬（TKO-20，待裁決）

櫃體群組本身不判斷空間。2.0 的 Nexus 已逐物件寫入 `_09_空間ID`／`_01_空間名稱`，Toolkit 與 QTY 只讀取成員既有值：

- 全體成員一致 → 輸出該空間
- 不一致 → 列為診斷並照實輸出多個值，不取多數決、不自行重算包含關係
- 落在所有空間框外 → 沿用 Nexus 既有的 `EXT`，量測值不受影響

實測佐證：`LoopFlow_3D.3dm` 的 0° 櫃 11 個成員全部是「廊道」；30° 櫃因在所有空間框與 FFL 樓層框之外，Nexus 已寫成 `EXT`。另注意 `_03_ID編號` 是類型編號，兩個不同櫃體的零件會有完全相同的 `CB-01`～`CB-07`，不能用它區分櫃體。
