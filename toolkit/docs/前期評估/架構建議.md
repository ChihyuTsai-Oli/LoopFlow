# LoopFlow Toolkit — 架構建議

## 1　產品邊界

**強烈建議**：比照 QTY，Toolkit 留在同一 repo 的 `toolkit/`，但作為獨立產品：

- 不 import `v2/src/loopflow` 或 `qty/src`
- 不進 LoopFlow 2.0 的 Yak、RUI、版本號或完成條件
- 自己的 Python package、tests、assets、版本與 `loopflow-toolkit` Yak
- 可獨立安裝，也可和 LoopFlow 2.0 同時存在

2.0 規劃文件原本寫「未來獨立 repo」，但使用者本輪已明確指定在 `LoopFlow/toolkit/` 作業。對目前只有數支工具、需要共用 CI 與多人接手的狀況，同 repo／不同產品比立刻拆 Git repo 更省維護；日後 package 邊界穩定，仍可完整抽離。

## 2　一個產品，不是一個巨型工具

建議發布一個 Toolkit 安裝包，但每項功能是獨立 feature：

```text
Toolkit launcher
    ├─ 2D Shelf Gap
    ├─ 2D Cabinet Symbol
    ├─ 2D Door / Window Symbol
    ├─ 3D Cabinet Generator        （待確認／可 experimental）
    ├─ 3D Cabinet Dividers         （待確認／可 experimental）
    └─ Cabinet BOM / Metadata       （資料契約未定前不發布）
```

這樣新增或停用某支工具，只會改 feature catalog、該 feature 與測試；不需複製一套 layer、unit、undo、error 與安裝程式。

## 3　建議目錄

```text
toolkit/
├─ src/loopflow_toolkit/
│  ├─ catalog.py                 # 唯一 feature／command 登錄表
│  ├─ contracts.py               # typed input、result、status、provenance
│  ├─ foundation/
│  │  ├─ units.py
│  │  ├─ settings.py
│  │  ├─ errors.py
│  │  └─ result.py
│  ├─ geometry/                  # 不碰 Rhino 文件
│  │  ├─ equal_division.py
│  │  ├─ cabinet_symbol_2d.py
│  │  ├─ door_window_2d.py
│  │  └─ cabinet_3d.py
│  ├─ features/                  # 每支工具的 use case
│  ├─ platform/rhino/            # prompt、preview、layer、bake、undo、restore
│  ├─ commands/                  # 極薄 Rhino entrypoints
│  └─ runners.py                 # command ID → runner；只查表轉交
├─ tests/
│  ├─ unit/
│  ├─ contract/
│  ├─ golden/
│  └─ rhino/
├─ assets/                       # RUI、icons、packaged defaults
└─ docs/
```

依賴方向固定為：

```text
commands/UI → features → geometry/contracts/foundation
      │
      └─────→ platform/rhino
```

`geometry` 不 import UI、rhinoscriptsyntax 或文件 adapter；`platform/rhino` 不決定門窗／櫃體商業規則。

## 4　Feature catalog 與入口

**強烈建議**以 typed Python catalog 作唯一登錄，不把功能清單散在 RUI、README 與多個 entrypoint：

| 欄位 | 用途 |
|---|---|
| `feature_id` | 永久 machine ID，不隨檔名或顯示名稱改變 |
| `command_id` | Rhino 直接指令 |
| `display_name` | launcher／工具列顯示名稱 |
| `category` | `2d`、`3d`、`data` |
| `runner` | 實際 use case |
| `status` | `experimental`、`stable`、`deprecated`、`removed` |
| `capabilities` | 會建立／刪除幾何、寫 metadata、需要選取等 |
| `tool_version` | 寫入 provenance 與錯誤報告 |

入口採混合方式：

- 一個長期穩定的 `LFToolkit` launcher，新增功能時自動依 catalog 出現
- 每支穩定工具仍有直接 command，方便快捷鍵與 RUI
- RUI 只放 launcher 與少數高頻穩定功能；不要每新增一支就要求使用者重排整套工具列

## 5　新增、修改、停用與移除

| 生命週期 | 行為 |
|---|---|
| `experimental` | launcher 明確標示；不承諾資料向後相容 |
| `stable` | command ID、input contract 與輸出 provenance 受相容性保護 |
| `deprecated` | launcher 顯示替代功能與預定移除版；現有輸出不受影響 |
| `removed` | 不再執行，但 catalog 保留 tombstone 一個發布週期，說明替代方式 |

移除軟體功能**不得刪除模型裡既有幾何或 metadata**。修改已生成輸出的預設策略是「產生新的」；若未來提供 regenerate／replace，必須先 preview 差異、辨識人工修改並明確確認，不靜默覆寫。

## 6　輸出 provenance

為了日後知道「這組線是哪支工具、哪版、哪些參數產生」，建議對新建輸出使用 Toolkit 自己的 namespace：

```text
lftk_schema_id
lftk_schema_version
lftk_feature_id
lftk_tool_version
lftk_instance_id
lftk_params
```

- 2D 工具的 provenance 只服務追蹤、選取與未來 regenerate，不是 LoopFlow 2.0 資料真相
- 不寫 `Q_*`、`lf_*`、`_CB.*` 或 2.0 canonical keys
- 3D Cabinet metadata 必須先以 2.0 Verify／Publish 實機測試，確認不造成主鏈問題才可升 stable
- 若使用者拆 group 或人工改線，幾何仍屬使用者成果；Toolkit 不自動修復

## 7　設定與單位

設定優先序建議：

1. 安裝包內版本化 defaults
2. 選用的專案設定 `<3dm>/_LoopFlow_Config/loopflow_toolkit/settings.json`
3. 當次 UI 輸入

設定不得引用某台電腦的絕對路徑；未知 schema version 停止載入該設定，不猜欄位。

所有領域常數標示物理單位，透過 unit adapter 轉成文件單位。初版至少驗證 cm 與 mm；不可再把 `1.8`、`12.0`、`90.0` 無條件當成目前 model units。

## 8　Rhino 文件安全

每次 command 必須：

- 計算與 preview 階段零寫入
- 確認後才開一個 undo record 並一次 bake
- 取消／錯誤時不建立 layer、不改 PlotWeight、不留下臨時幾何
- 恢復 selection、current layer、redraw 與原有物件屬性
- 不刪使用者輸入；若某流程確實需要 consume input，另列明選項並再次確認
- 回傳 created／skipped／failed 的 typed result，不以空 stdout 當成功

產生器成功後 `doc.Modified = true` 是預期結果；關鍵是取消或失敗時不能留下部分變更。

## 9　Cabinet Group 與 QTY 交界

完整櫃體不建立為 Block，改以 Rhino Group 組織，讓群組內每個零件仍可使用 LoopFlow Tag。這個選擇不改 Nexus：Nexus 繼續逐物件處理；Toolkit 只負責建立／檢查群組，QTY 才把群組當成一筆幾何量測單位。

### 9.1 唯一權威與命名

- QTY 只認 Rhino Group Table 的真正 Group Name，不讀成員的「物件名稱」來判斷群組。
- Group Name 使用保留前綴 `QTY_CB_`，並保持唯一且可辨識，例如 `QTY_CB_001_主臥櫃`；前綴只供 QTY 找出櫃體群組，不編入高／矮、深／淺或特殊櫃代碼。
- `SetGroupName` 已直接寫入真正名稱，不需要再同步。
- 既有模型若把共同名稱寫在各成員的物件名稱，才使用一次性／可重跑的 `LF_Cabinet_Group_Sync` 轉入真正 Group Name；轉換後 Group Name 是唯一權威，不維護雙向同步。

### 9.2 建議指令責任

| 指令 | 責任 |
|---|---|
| `LF_Cabinet_Group` | 將選取零件建立為最外層櫃體群組並直接設定真正 Group Name |
| `LF_Cabinet_Group_Sync` | 把最外層群組成員唯一且一致的物件名稱寫成真正 Group Name；空白、不一致、重名或交叉時停止，不猜測 |
| `LF_Cabinet_Group_Check` | 檢查真正名稱、唯一性、最外層成員集合、交叉／重複群組與 OBB 可量測性；只報告，不改幾何 |

同步與檢查都必須辨認外層群組。若兩個群組的成員集合互相重疊、且任何一方都不是另一方的完整子集合，視為交叉衝突；不得依 Group Index、`Group03` 之類自動名稱或選取順序猜測。

### 9.3 QTY 量測契約

QTY 集合真正 Group Name 對應的全部成員，固定世界 Z 為高度軸，只在 XY 平面推定主要方向並計算 OBB：

- 高：世界 Z 範圍
- 長：方向校正後較長的水平尺寸
- 寬：方向校正後較短的水平尺寸

輸出忠實反映完整群組的外包尺寸，不套標準值、不自動分類，也不因不規則／弧形而改成另一套算法。人工分類、單位與估價判斷留到 QTY 輸出階段；幾何量測值仍保留作依據。
