# LoopFlow 2.0 — Excel 字典使用說明

> 本文件說明 Dictionary 的格式、欄位意義、撰寫規則，以及它跟 Rhino 模型之間的同步邏輯。官方範本有繁中、英文各一份，Nexus 選哪本、專案就認哪本。指令怎麼操作見 [指令逐項說明](./COMMANDS_TW.md)；整體流程見 [使用說明總覽](./USER_GUIDE_TW.md)。

## 1　字典是什麼

`LoopFlow_Dictionary.xlsx` 是 LoopFlow 的**材質／工項預設值表（Type Catalog）**。

每一列代表一種材質或工項（稱為一個 **Type**），對應到 Rhino 裡的一個子圖層。執行 [04 Nexus](./COMMANDS_TW.md#04-nexus開案主控台) 的「同步 Type Layers」時，系統會依這份表建立圖層並帶入預設值；之後建模時把物件放到對應圖層，[寫入模型 Metadata](./COMMANDS_TW.md#5-寫入模型-metadata) 就會依物件實際使用的 Type 寫入資料。

字典管的是「這個 Type 預設長怎樣」，**不是**物件實際的現況——同一個 Type 底下的每個物件，仍然可以有各自不同的建構狀態、備註等內容。

整體資料流是這樣：

```text
Excel 字典               每列一個 Type：ID、名稱、圖層、預設值與規則
      │  LFNexus「同步 Type Layers」
      ▼
Rhino Type 圖層           以 _03_ID編號 對回字典；保存新建圖層時的預設值
      │  建模，把物件放進對應圖層
      │  LFNexus「寫入模型 Metadata」
      ▼
3D 物件                   一般物件各自的 UUID、空間、實際高程、建構狀態、備註、資料版次（`00_STR` 結構層不寫）
      │  檢核通過後 LFPublishExchange
      ▼
Registry 版次              唯讀的模型資料快照
      │  LFInfuserPart／LFInfuserAll
      ▼
2D Tag 圖塊                畫面上顯示出來的 Type、高程、圖號等資料
```

## 2　檔案格式與放置位置

| 項目 | 說明 |
|---|---|
| 檔案名稱 | 預設 `LoopFlow_Dictionary.xlsx`，可以改用 `.3dm` 同一層的其他 `.xlsx` 檔名 |
| 放置位置 | 已存檔 `.3dm` 所在資料夾；這個資料夾就是 LoopFlow 的專案工作資料夾 |
| 專案設定 | `.3dm` 同層的 `_LoopFlow_Config/LoopFlow_Project.json`，只記 Dictionary 檔名，不記絕對路徑 |
| 格式要求 | 只支援 `.xlsx`；不接受 `.csv` 或 `.xls` |
| 工作表 | 讀取第一張工作表；目前工作表名稱為 `LoopFlow_Dictionary` |
| 第 1 列 | 版本標題列，例如 `LoopFlow Dictionary v2.0`（程式會跳過） |
| 第 2 列 | **欄位標題列**：整列 15 欄須同一語系（全部繁中或全部英文，見「3　欄位說明」） |
| 第 3 列起 | 每一列代表一個 Type，對應一個 Rhino 子圖層 |

第一次執行「同步 Type Layers」時會跳出選檔視窗，選過一次後檔名會記在 `_LoopFlow_Config/LoopFlow_Project.json` 的 `dictionary_filename`，之後不會再問。Dictionary 必須和 `.3dm` 在同一層；若已記住的檔案被改名或移走，系統會先請你把檔案放回，再從 `.3dm` 所在資料夾重新選取。選到其他資料夾時會說明並再問。**系統不會掃描資料夾裡所有 Excel，也不會保存某台電腦的絕對路徑。**

`.3dm`、Dictionary 與 `_LoopFlow_Config/` 只靠相對位置綁定。整個專案資料夾搬到其他上層目錄、磁碟或電腦仍可使用；只複製 `.3dm` 則不會帶走原專案名稱與 Dictionary 選擇。官方 Dictionary 範本會放到「文件\LoopFlow」，再複製到 `.3dm` 同一層使用。

**介面語言與字典檔無關。** 切換 English／正體中文只改 LoopFlow 視窗與訊息；專案字典永遠是 Nexus 選中並記住的那一本，不會依介面語言自動換成 tw 或 en 檔。

### 兩份來源範本

| 範本 | 內容 | Nexus 載入 |
|---|---|---|
| `LoopFlow_Dictionary_tw.xlsx` | 繁中欄名、雙語 Rhino Layer、微軟正黑體 10 | **可以** |
| `LoopFlow_Dictionary_en.xlsx` | 英文欄名與內容、英文 Rhino Layer、Arial 10；計數／面積使用 `ea`／`m2` | **可以** |

兩份都是完整的 92 列官方範本。專案要用哪本，在 Nexus「同步 Type Layers」選一次即可。不要把同一列的繁中欄名與英文欄名混在一起。

> **不要選錯檔**：檔名以 `_Export.xlsx` 結尾的是差異核對檔（見「9　核對模型與字典的差異」），不能當正式字典開啟，更不能直接改名頂替正式檔。

## 3　欄位說明（15 欄）

字典有 15 欄，前 9 欄（含圖層路徑）是每個 Type 都要有的基本資料，後 6 欄（`Q_01`～`Q_06`）是保留給後續 Grasshopper 數量計算用的欄位，2.0 本身不計算也不下放到物件。第 2 列標題必須整列同一語系；載入後會對到同一組英文 machine key。下表以繁中欄名為主，括號內是英文範本的對應標題。

| 欄名 | 是否必填 | 說明 |
|---|---|---|
| `__Rhino Layer`（`Rhino Layer`） | 必填 | 這個 Type 對應的完整 Rhino 圖層路徑（見「4　圖層命名規則」），是**同步時**用來對照圖層的鍵值，不是 Type 的正式編號 |
| `_01_空間名稱`（`_01_Space Name`） | 留空 | 由模型自動計算，字典不需要填 |
| `_02_建構狀態`（`_02_Construction`） | 選填 | 這個 Type 新建圖層時的預設施工狀態，例如 `New` 或 `Existing`。**只影響新建圖層的初始值**；之後每個物件可以自己改，不會被字典重新同步覆蓋 |
| `_03_ID編號`（`_03_Type ID`） | 必填 | Type 的唯一編號，格式 `類別碼-序號`，例如 `EX-01`、`CL-03`（見「4　圖層命名規則」的類別碼表），**不可重複** |
| `_04_ID名稱`（`_04_Type Name`） | 必填 | 人看得懂的材質／工項名稱，會顯示在 Tag 與圖說上，例如「鋁製檢修孔」。可以改名，但不是永久身分——永久身分是 `_03_ID編號`／`_03_Type ID` |
| `_05_高程基準`（`_05_Elevation Basis`） | 必填 | 這個 Type 預設用哪個基準量高程，只能是下列四種之一（見下表） |
| `_06_高程計算`（`_06_Elevation Value`） | 留空 | 由模型自動計算，字典不需要填 |
| `_07_UUID` | 留空 | 物件的識別碼，由系統自動產生，字典不需要也不應該填 |
| `_08_備註`（`_08_Remarks`） | 選填 | 預設備註提示，通常填 `(手動輸入備註)`，讓使用者在物件上自己填實際內容 |
| `Q_01_寬度W`（`Q_01_Width W`） | 留空 | 留給後續 Grasshopper 使用，2.0 不計算、不寫入物件 |
| `Q_02_深度D`（`Q_02_Depth D`） | 留空 | 同上 |
| `Q_03_高度H`（`Q_03_Height H`） | 留空 | 同上 |
| `Q_04_單位`（`Q_04_Unit`） | 必填 | 工程估算單位（不是 Rhino 文件單位）。繁中範本用 `cm`、`mm`、`m3`、`坪`、`才`、`樘`、`片`、`組`、`台`、`座`；英文範本計數用 `ea`、面積用 `m2`（見「5　撰寫規則」） |
| `Q_05_計量規則`（`Q_05_Measurement Rule`） | 必填 | 這個單位要用哪種方式計算數量（見「5　撰寫規則」的計量規則表），現行 92 筆已全部填妥 |
| `Q_06_實作數量`（`Q_06_Quantity`） | 留空 | 留給後續 Grasshopper 計算，2.0 不計算 |

### `_05_高程基準` 可用值

| 縮寫 | 全名／取樣位置 | 說明 |
|---|---|---|
| `BH` | Bottom Height，物件底部 | 從物件**底面**量高程，適用牆、落地設備等一般幾何 |
| `TH` | Top Height，物件頂部 | 從物件**頂面**量高程，適用地坪、門檻等以頂面標示者 |
| `CH` | Ceiling Height，天花物件底部 | 從**天花板底面**量高程（燈具、天花材料適用） |
| `BC` | Block 基準點 | 讀取 **Block instance 的插入基準點**，**只能用在圖塊（Block）**——開關、面板、設備等以圖塊形式插入的物件。若一般幾何（非 Block）的 Type 用 `BC`，寫入模型 Metadata 與檢核時會直接擋下，不會偷偷改用其他基準 |

> 舊版 1.x 用過的 `TH/BH`（同時記錄頂面與底面）**不是** 2.0 合法值，只在 migration 對照時參考。

## 4　圖層命名規則

繁中範本的 `__Rhino Layer` 欄格式是：

```text
頂層群組::英文名稱.中文名稱
```

例如 `01_Ceiling_天花::Access_Panel.檢修口`。英文範本路徑不含中文，例如 `00_STR::Beam`。兩種路徑都能載入；不要在同一份檔裡混用繁中與英文欄名。

目前繁中字典有 **12 個頂層群組**，各自對應固定的類別碼前綴：

| 類別碼 | 頂層群組 | 範例（ID編號／ID名稱） | 高程基準 | 常見 `Q_04` 單位／`Q_05` 計量規則 |
|---|---|---|---|---|
| `EX` | `00_STR_結構` | `EX-01`／鋼筋混凝土（樑） | `BH`／`TH` | `m3` / `VOL_WDH`；`cm` / `LEN_W`；`坪` / `AREA_WD`；`座` / `COUNT` |
| `CL` | `01_Ceiling_天花` | `CL-01`／鋁製檢修孔 | `CH` | `片` / `COUNT`；`坪` / `AREA_WD`；`cm` / `LEN_W` |
| `WL` | `02_Wall_牆面` | `WL-01`／輕隔間牆 | `BH` | `cm` / `LEN_W` |
| `FL` | `03_Floor_地坪` | `FL-01`／陽台磁磚地坪 | `TH` | `坪` / `AREA_WD` |
| `CB` | `04_CB_櫃體` | `CB-01`／木作櫃體 | `BH` | `mm` / `LEN_W` |
| `LS` | `05_LT_燈帶` | `LS-01`／天花燈帶 | `BH` | `cm` / `LEN_W` |
| `EL` | `06_EL_電控系統` | `EL-01`／對講機 | `BC`（圖塊） | `組` / `COUNT` |
| `MP` | `07_MEP_空調機電` | `MP-01`／空調面板 | `BC`（圖塊） | `組` / `COUNT` |
| `SA` | `08_SAN_衛浴設備` | `SA-01`／浴缸 | `BC`（圖塊） | `組` / `COUNT` |
| `EQ` | `09_EQP_專用設備` | `EQ-01`／影音設備 | `BH` | `組` / `COUNT` |
| `FP` | `10_FP_消防系統` | `FP-01`／緊急照明燈 | `BC`（圖塊） | `組` / `COUNT` |
| `DW` | `20_DW` | `DW-01`／門窗 | `BH` | `樘` / `COUNT` |

`04_CB_櫃體` 只是一般材質分類，跟日後獨立的櫃體工具（不屬於 2.0）無關，不要混淆。

### `20_DW`（門窗）是特例

門窗的模型資料寫在**圖塊本身**（見 [Tag Block 說明](./TAG_BLOCKS_TW.md#dw-tag--門窗標註)），不是寫在子圖層上，所以 `20_DW` 這一列的備註直接寫明「Block 放在此圖層，資料寫在 Block，不寫在子圖層」。同步時 `20_DW` 只當成單一 Type，排除底下的子圖層；`TAG_DW` 的 No./W./H. 則是 2D 圖面端手動欄位，不會因此建立子 Type，也不會回寫為 3D 物件資料。

### `00_STR`（結構）不寫物件資料

`00_STR` 結構層與其子層**仍會**由字典同步成 Type 圖層，並寫圖層 `lf_type_id`。放在這些圖層上的 3D 物件**不會**寫入物件 ID、空間、高程等 Metadata，也不當 Laser／Grab 來源。下次跑「寫入模型 Metadata」時會清掉這些物件上既有的物件資料。數量計算走獨立產品，不靠這些物件的 UUID。

## 5　撰寫規則與注意事項

- **`_03_ID編號` 格式固定為 `類別碼-序號`**（例如 `EX-07`），載入時會嚴格拆分驗證，類別碼要跟圖層所在的頂層群組一致，且不可與既有列重複。
- **`Q_04_單位` 與 `Q_05_計量規則` 的量綱要一致**，否則載入字典會直接被擋下。允許的計量規則與對應量綱：

  | 計量規則 | 量綱 | 允許的 `Q_04` 單位 |
  |---|---|---|
  | `COUNT` | 計數 | 樘、片、組、台、座、ea |
  | `LEN_W`／`LEN_D`／`LEN_H` | 長度 | cm、mm |
  | `AREA_WD`／`AREA_WH`／`AREA_DH` | 面積 | 坪、才、m2 |
  | `VOL_WDH` | 體積 | m3 |

  換算常數：`坪 = 指定面積（m²）× 0.3025`；`才 = 指定面積（cm²）÷ (30.3 × 30.3)`。這些換算是保留給後續 Grasshopper 使用，**2.0 本身不會從模型幾何實際求值**。`ea` 與 `m2` 是英文範本的計數／面積單位，量綱表已登錄；Nexus、Infuser、Catalog、Tagger 都不拿單位字串做業務判斷，單位只在載入時檢查，並快照進 Registry 的 `types[]`。
- `_08_備註` 建議統一填 `(手動輸入備註)` 當預設提示，讓使用者在物件上一眼看出這欄是空的、該自己填。
- Excel 第 2 列必須是**整列繁中 15 欄或整列英文 15 欄**；程式載入後會轉換成內部使用的英文鍵值。同一列中英混用會擋下。
- **欄名、欄數跟目前的 15 欄定義不符時，會直接停止載入**，不會靠猜測比對欄位，所以不要自己改欄名或調整欄位順序範圍以外的內容。
- 字型：繁中範本統一用**微軟正黑體 10**；英文範本統一用 **Arial 10**。匯出檔的欄名與字型跟著來源字典，不跟介面語言。

### 哪些欄位是「Type 規則」，哪些要留白

字典填的是 Type 的**規則與預設值**，不是物件實際內容：

- **由字典決定的規則**：`__Rhino Layer`、`_02_建構狀態`（初始預設）、`_03_ID編號`、`_04_ID名稱`、`_05_高程基準`、`_08_備註`（初始提示）、`Q_04_單位`、`Q_05_計量規則`。
- **要留白，由模型計算或系統產生**：`_01_空間名稱`、`_06_高程計算`、`_07_UUID`、`Q_01`～`Q_03`、`Q_06`。填了這些欄不會被讀取，也不代表模型會照抄。

## 6　新增或修改一個 Type

### 新增

1. 在相近類別附近新增一列，或複製最接近的 Type 列再修改。
2. `__Rhino Layer` 改成新的完整圖層路徑。
3. `_03_ID編號` 給一個**還沒用過**的編號，例如既有到 `WL-14`，新的就用 `WL-15`。
4. 填 `_04_ID名稱`、確認 `_02_建構狀態` 預設、依幾何意義選 `_05_高程基準`。
5. 填 `Q_04_單位` 與量綱相容的 `Q_05_計量規則`。
6. 確認 instance／計算欄仍留白，存檔。
7. 回 Rhino 執行 [04 Nexus](./COMMANDS_TW.md#04-nexus開案主控台) 的「同步 Type Layers」，確認新圖層出現後，才開始把物件放進去。

### 修改既有 Type

**可以放心改**：`_04_ID名稱`、`_02_建構狀態` 預設、`_08_備註` 預設、`_05_高程基準`、`Q_04`／`Q_05`。改完重新同步、重新檢核即可。

**要特別小心**：`_03_ID編號`、`__Rhino Layer`、類別碼。這幾個是已經被物件、Registry、Tag 引用的穩定身分，改了字典裡的值不會自動更新已經寫入的物件——不要只在 Excel 把舊編號改成新編號就繼續工作，要先想清楚既有物件怎麼處理。

## 7　字典、3dm 與專案設定的關係

LoopFlow 不把專案名稱、Dictionary 檔名等環境設定寫進 `.3dm`。這些資料保存在旁邊的 `_LoopFlow_Config/LoopFlow_Project.json`；Registry 與 log 也都在 `_LoopFlow_Config/` 下面。這樣同一份 `.3dm` 被複製到新專案時，不會自動帶著舊專案的路徑與設定。

執行 [04 Nexus](./COMMANDS_TW.md#04-nexus開案主控台) 「同步 Type Layers」時的合併規則：

- **字典有、Rhino 沒有的圖層**：自動建立該圖層，並把字典裡的 `_02_建構狀態` 當作**這個圖層新建物件的預設值**寫入圖層屬性，不是寫進每個物件。
- **Rhino 已經有的同名圖層**：保留既有 UserText 與建構狀態；顯示顏色仍依 Type 分類重新套用。
- **物件的實際現況只由物件自己維護**：重新同步字典，不會覆寫任何物件上已經填好的資料，也**不會把物件現況回寫到字典**——字典跟模型是單向關係（字典 → 新圖層預設值），不是雙向同步。
- 新建 Type 圖層時，系統會在原點放一個 `DNA_REF_` 參考點，避免這個空圖層被 Rhino 的 Purge 清除；重新同步時會依 Type 編號更新或取代這個點，不會一直累加新的點。
- 圖層顯示色會依類別碼前綴自動套用；新建材質名稱會是去掉專案前綴的相對路徑，顏色跟圖層一致。如果 Rhino 裡已經有同名材質，只會掛接使用，**不會改動使用者已經調整過的顏色**。

簡單說：**Dictionary 管 Type 身分、對照、預設與規則；模型物件保有自己的當前值。** 同步會維護 Layer 對照、顏色、材質附著與 `DNA_REF`，但不覆寫物件既有的建構狀態、備註、UUID 或標高。

## 8　`Q_01`～`Q_06` 數量欄目前的定位

2.0 不做尺寸或數量計算，也不把 Q 欄寫入模型物件或 Registry。`Q_04_單位` 與 `Q_05_計量規則` 仍會參與尺寸一致性檢查；`Q_01`～`Q_03`（寬深高）與 `Q_06`（實作數量）請留白，保留給後續 Grasshopper 工作流程。

## 9　核對模型與字典的差異

字典跟模型現況難免會慢慢出現落差（例如建模過程中臨時調整了某個圖層）。核對流程：

1. 執行 [03 匯出字典](./COMMANDS_TW.md#03-匯出字典)，把 Rhino 現況匯出成 `{原檔名}_Export.xlsx`。
2. 執行 [02 開啟匯出字典](./COMMANDS_TW.md#02-開啟匯出字典) 打開來看，比對 `diff_status` 欄的顏色標示。
3. 打開 [01 開啟正式字典](./COMMANDS_TW.md#01-開啟正式字典)，**手動**把需要的修改抄回正式字典。

| `diff_status` | 顏色 | 意思 | 建議處理 |
|---|---|---|---|
| `unchanged` | 黑字 | 字典與模型一致 | 不用處理 |
| `modified` | 橙字 | 兩邊都有，但內容不同 | 人工比對後決定以哪邊為準 |
| `missing_in_rhino` | 紅字 | 字典有、模型沒有 | 確認是否該重新同步，或這個 Type 已經不再使用 |
| `added_in_rhino` | 藍字 | 模型有、字典沒有 | 併回字典時要給一個**還沒用過**的 Type ID（繁中來源寫 `_03_ID編號`，英文來源寫 `_03_Type ID`） |

這份匯出檔**只供核對，永遠不能取代正式字典**，程式也不會自動幫你合併，只會彙整圖層層級的差異，不會彙總個別物件的資料。頂部紅字、15 欄欄名與字型跟著**來源字典**（繁中微軟正黑體與 `_03_ID編號`；英文 Arial 與 `_03_Type ID`），不跟介面語言。

## 10　常見錯誤

| 情況 | 常見原因 | 處理方式 |
|---|---|---|
| 字典無法載入 | 版本標題、欄名、欄數跟目前 15 欄定義不符，或同一列混用繁中與英文欄名 | 恢復成官方範本的 15 欄結構；整列用同一語系，不要自行增刪或改欄名 |
| `_03_ID編號` 重複 | 新增列時沿用了舊編號 | 改成尚未使用過的新編號 |
| 高程基準錯誤 | 填了 `BH`／`TH`／`CH`／`BC` 以外的值（例如舊版 `TH/BH`） | 改成四個合法值之一 |
| 寫入模型時 `BC` 檢核失敗 | `BC` 用在非圖塊（Block）的一般幾何上 | 改用圖塊插入，或把該 Type 的高程基準改成 `BH`／`TH`／`CH` |
| 計量規則錯誤 | `Q_04_單位` 跟 `Q_05_計量規則` 量綱不一致 | 對照「5　撰寫規則」的量綱表修正 |
| 開不到正式字典 | 檔案被改名、搬離 `.3dm` 同一層，或只複製了 `.3dm`、沒有帶 `_LoopFlow_Config/` | 把 Dictionary 放回 `.3dm` 同一層，再於 [04 Nexus](./COMMANDS_TW.md#04-nexus開案主控台) 的同步步驟重新選檔 |
| 誤開了 `_Export.xlsx` | 把差異核對檔當成正式字典打開來編輯 | 改開正式檔；核對檔的修改不會被讀取 |
| Excel 改了，Rhino 沒反應 | 忘記重新執行「同步 Type Layers」 | 存檔後回 Rhino 重新同步 |
| Tag 上顯示舊資料 | 還沒走完寫入 → 檢核 → 發布 → 注入這條鏈 | 依序補做缺的步驟 |

## 11　中途切換字典檔案（不建議）

專案設定的 `dictionary_filename` 只記住檔名，不含路徑。換成另一份 `.xlsx` 之後，新檔案裡沒有涵蓋到的 Type 就無法再被同步邏輯辨識。如果真的需要換檔，建議先用「9　核對模型與字典的差異」流程確認新舊字典的 Type 編號、欄位定義是否一致，避免既有物件的 `_03_ID編號` 在新字典裡對不到 Type。
