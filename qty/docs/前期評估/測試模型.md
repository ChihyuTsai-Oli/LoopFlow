# LoopFlow QTY — 測試模型補強項目

> 本文件列出目前驗證模型**缺少或可補充**的項目，用來擴大量測方法的驗證範圍。
>
> 驗證模型有兩份：`LoopFlow_R_MCP.rws`（QTY MCP 測試環境，§1～§6 的基準）與 `LoopFlow_3D.3dm`（LoopFlow 主工作檔，2026-09-03 的櫃體群組實測來源）。兩者狀態不同，樣本引用時要標明來自哪一份。
>
> 建立日期：2026-09-02　｜　最後更新：2026-09-03　｜　現況數字見 [`資料盤點.md`](./資料盤點.md)

## 0　測試資產規則

### 0.1 為什麼需要補強

目前模型的可量測候選只有 **48 個**（Brep 39 ＋ Block 9），而量測方法的兩個失效情境**各只有 1～2 個樣本**：

| 已知失效 | 目前樣本數 |
|---|---|
| 多段包覆面（面積法失效） | **1**（`WL-14`） |
| 轉角擠出（長度法失效） | **1**（`CL-03`） |
| 閉合環（長度法無端面） | **1 種**（`CB-04`，兩個實例相同） |
| 開口 | **2**（22.4%、5.0%） |

**單一樣本無法區分「方法有效」與「這一件剛好對」。** 補強的目的不是讓模型更完整好看，而是讓每個已知失效情境**至少有三個彼此不同的樣本**，並補上目前完全沒有的規則與資料情境。

### 0.2 必須與原始工作檔隔離

- **不得直接改目前的 `LoopFlow_3D_R_MCP.3dm`、`LoopFlow_2D_R_MCP.3dm`、正式 Dictionary 或 Registry**。它們是 48 件候選的原始 baseline，也是使用者工作檔。
- Rhino 幾何測試另建可丟棄的 `.3dm`／`.rws` 副本；測試 Type、Space 與 `m2` 規則使用測試 Dictionary／Registry。副本內才使用 `_QTY_TEST` 前綴圖層或命名。
- 效能放大模型與參照失效模型各自獨立，不能和正確性模型混在同一檔，否則盤點數字與 golden baseline 會一起漂移。
- repo 只保存可合法提交的小型 fixtures、期望輸出與建立說明；大型或含專案資料的 Rhino 工作檔留在工作檔區，repo 內以 manifest 記錄檔名、版本與雜湊，不寫某台電腦的絕對路徑。

### 0.3 每個樣本都要有 oracle

只「加一個形狀」不足以形成測試。每個樣本至少記錄：

1. 建構尺寸／方式與用途
2. 預期 measurement token、估價單位與 exact value
3. 可接受容差
4. 預期 measurement status、Coverage status 與警告原因
5. 身分來源（`object_id` 或 `source_model_key + Rhino GUID`）

若預期答案尚未能由人工或另一種可信方法確認，該物件只能標為探索樣本，不能列入 golden pass/fail。

## 1　幾何形狀（優先）

**1. 新增弧形牆面**
目前所有 Brep 都是平面組成。弧牆的「最大單一面」是一個曲面，`AreaMassProperties` 給的是展開面積——這正是估價要的，但**完全沒有驗證過**。若曲面被切成多片，最大面法會像 `WL-14` 一樣少算，需要對照值抓。

**2. 新增 L 型與 U 型牆面（各至少 2 個，轉角角度不同）**
`WL-14` 是目前唯一的多段包覆樣本。需要不同轉折數與不同夾角，才能確認「最大面 vs 體積÷厚度」的 10% 閾值是否合理，或該不該依轉折數調整。

**3. 新增斜面物件（斜天花、斜屋頂或樓梯側牆）**
目前所有面不是水平就是垂直。斜面會讓「最大面朝哪裡」的判讀進入灰區，也會影響 `AREA_WD`／`AREA_WH` 的相容性檢查（QR-09）。

**4. 新增弧形收邊條或弧形燈帶**
長度法的「體積 ÷ 端面截面積」理論上對曲線路徑成立，但目前**只有直線與一個轉角**驗證過。弧形是實務常見（弧牆的收邊），必須測。

**5. 新增第二、第三種閉合環物件**
`CB-04 鐵件框架` 是唯一的閉合環，且兩個實例完全相同。需要不同尺寸與斷面的環（例如圓形燈帶、口字型框），才能驗證 fallback「取環的中心線周長」。

**6. 新增更多開口樣本，並涵蓋不同開口比例**
目前只有 22.4%（門洞）與 5.0%（小開孔）。建議補：兩個開口的牆、開口占比 40～60% 的牆、以及**開口貫穿但形狀不規則**的牆。用來定 QR-07 的閾值。

**7. 新增「中空但不是開口」的對照物件**
`CB-04`（95.6%）與 `CL-03`（79.2%）目前是僅有的中空構件。多幾個（例如格柵、百葉、鏤空屏風）才能確認「扣除率分不出開口與中空」這個限制的實際嚴重程度。

## 2　規則涵蓋（優先）

**8. 補上使用 `m2` 單位的 Type**
目前字典用到的單位是 mm、cm、坪、才、組——**沒有 `m2`**。而舊 `quantity.py` 的 `m2` 換算有缺陷（少除 10000，錯一萬倍）。**沒有 `m2` 樣本就測不到這個已知缺陷**，修完也無從驗證。

這個 Type 只加在**測試 Dictionary**，不得為了測 QTY 修改現行 2.0 正式 Dictionary。

**9. 補上 `VOL_WDH` 的裝修材樣本**
目前 `VOL_WDH` 只出現在結構體（樑、柱），而結構體另有計算方式。裝修材若有體積類項目（例如填充、灌漿），需要樣本。

**10. 補上 `AREA_DH`、`LEN_D`、`LEN_H` 的樣本**
字典的規則詞彙有 8 個 token，但本模型只用到 4 個（`COUNT`、`AREA_WD`、`AREA_WH`、`LEN_W`）。另外 4 個從未執行過任何一次。即使實務上少用，也應各有一個樣本確認程式路徑會動。

**11. 補齊結構體的實體幾何**
`Column.柱` 與 `Wall-Brick.磚牆` 目前**只有 `DNA_REF_` 參考點，沒有真實 Brep**。結構體走 `layer_path` 查字典這條路只在 5 個圖層上驗證過（Beam、Slab、Curb、Stair、Wall-RC），另外 2 個沒有實體可測。

只在結構測試副本補上，保留原模型「沒有真實 Brep」的基準事實。

同一組樣本要順便驗 **`layer_path` 正規化**：模型的圖層全名帶專案 `layer_prefix`（實測 `M3D::00_STR_結構::Beam.樑`），Registry／字典側則沒有（`00_STR_結構::Beam.樑`）。直接拿 `FullPath` 比對會全部查不到。詳見 [`資料盤點.md`](./資料盤點.md) §6。

## 3　資料情境

**12. 增加空間數量到至少 5 個，並包含同名跨樓層**
目前只有「廊道」29 個與「衛浴」8 個。分組、排序、`space_display → sort_key` 對照都無法驗證。同名跨樓層（例如兩層都有「主臥」）是 QO-14 明確點名的風險。

**13. 新增落在 `EXT`（空間外）的物件**
2.0 的 `EXT` 同時代表「真的在室外」與「漏畫 boundary」（ED-07 已接受此代價）。QTY 的 Coverage 報告要能列出 `EXT` 物件，但目前**一個樣本都沒有**。

**14. 新增刻意的「一式」候選物件**
一式黑名單是主動差集（QD-10），但目前模型沒有任何標記為一式的物件，整條排除邏輯無從測試。
2026-09-03 追加：一式的載體改以命名群組提案（QD-23），代表樣本與完整驗收條件見 **項目 27**。

**15. 建立一個刻意的參照失效情境**
Coverage 五態的「已選取但參照失效」需要可重現的樣本。建議另存一份測試 `.rws`，其中 3D 檔缺少某些物件，用來驗證失效偵測與報告文字。

**16. 補上未標記門窗 Block 的處置樣本**
`base` 圖層有 `3D_W1`、`3D_D1` 兩個 linked block，**沒有 `_03_ID編號`**。它們應該進計算、進 Coverage、還是排除？字典有 `DW-01`，但這兩個沒被標記。需要決定並建立對應樣本。

## 4　工作方式與規模

**17. 建立兩種合法配置的 fixture（2026-09-03 依 QD-26 改寫）**

原本這一項是「補上直接開 3D 檔的對照」，因為當時只測過 worksession。QD-26 之後合法配置只有兩種，**而且先前用來建立所有 baseline 數字的 `LoopFlow_R_MCP.rws`（3D attach 進 2D）兩種都不是**：

| | 配置 | 需要驗證 |
|---|---|---|
| **a** | 直接開 3D 模型檔 | 物件為本機、`layer_path` 不帶檔名前綴、群組名稱為原名 |
| **b** | `.rws`，2D attach 進 3D | 同上；另驗 attach 的 2D 內容（參照＋Curve）確實完全不進全集與 Coverage |
| **反例** | 3D attach 進 2D（舊 rws） | 應**報設定錯誤並停止**，不得照樣量測 |

a 與 b 必須得到**完全相同**的計算結果與 Coverage；反例則必須被擋下。三者共用同一份 3D 模型副本，只改開檔方式。

`LoopFlow_R_MCP.rws` 仍保留作為既有數字的來源與反例樣本，但不再是實務配置的代表。

**18. 建立效能測試用的放大模型**
目前可量測候選只有 48 個，列舉總量 3116。QO-17 要求測 100／1,000／5,000 候選。可用複製方式產生，但需注意 GUID 會改變（複製產生新 ID）。

**19. 建立三層 fixture 集**

不要把「不需 Rhino」與「能驗證 Rhino 幾何辨識」混為一談：

- **純 Python domain fixtures**：保存 adapter 已抽出的 typed records（面積、體積、候選端面／rail、身分、規則與來源 revision），驗證規則 join、狀態機、單位換算與報告；CI 可直接跑。
- **Rhino integration fixtures**：小型 `.3dm`／`.rws`，驗證 RhinoCommon 的面、端面、block transform、reference 與 layer 正規化；需在 Rhino 內跑。
- **Golden outputs**：兩層都對到同一份期望結果；若 integration 擷取結果改變但 domain 測試仍綠，差異必須可見，不能更新 golden 掩蓋。

合法／錯誤至少各一組，涵蓋直線、轉角、閉合環、包覆面、開口、Block、結構體與參照失效。

**20. 補上身分生命週期與碰撞測試**

- 儲存／關閉／重開後，同一物件仍能解析
- worksession 改變 attach 順序或多附加一個模型後，locator 仍指向原來源
- 同一 3D 檔直接開啟與作為 reference 時，得到相同 canonical locator
- 複製來源 `.3dm` 造成兩個模型具有相同 Rhino GUID 時，必須靠 `source_model_key` 分開
- 專案根目錄搬到另一台電腦後，相對來源鍵仍能解析
- 來源檔改名、物件刪除重畫、同一專案出現重複 `_07_UUID` 時，回傳 lost／conflict，不自動猜配

**21. 補上模型單位對照**

以已知尺寸分別建立 cm、mm（必要時再加 m）的小型模型，確認幾何 raw、估價單位 exact value 與顯示值不會因文件單位相差 10／100 倍。不可直接改原始模型單位來測。

**22. 補上 Block transform 與不支援幾何**

至少包含旋轉、鏡射、非等比縮放、巢狀／linked block、多個 instance 共用 definition，以及 open／invalid Brep。Mesh、SubD 等範圍外型別也要有排除案例與明確原因，避免它們被無聲漏掉。

## 5　建議的補強順序

| 順序 | 項目 | 理由 |
|---|---|---|
| 1 | 19（fixture 三層）與 oracle 格式 | 先固定怎樣才算「測過」，否則後續只是在堆模型 |
| 2 | 8（`m2`）、11（結構實體）、20（身分） | 補**已知缺陷**、未完整路徑與 QR-01 的安全契約 |
| 3 | 1～7（幾何形狀） | 直接決定 QR-03 的長度 fallback 與 QR-07 的開口閾值能不能定案 |
| 4 | 12～17、21、22、26、27、28 | 解鎖分組、Coverage、直接開檔、單位、Block、Cabinet Group／一式群組與失效行為 |
| 5 | 9、10、18 | 補完整性與效能；效能模型獨立建立，可與實作並行 |

> **注意**：原始工作檔不補強，因此 [`資料盤點.md`](./資料盤點.md) 的 48 件 baseline 保持不變。各測試副本另有自己的 manifest 與盤點，不把數字混回原始模型。

| `EL-07` 隱藏、`SA-01` 鎖定 | 原始模型已有 hidden／locked 樣本，但仍應在副本做成可重跑的 oracle；見項目 24 |

| 結構末層實名是 `Wall-Brick.牆-Brick`、`Wall-RC.牆-RC` | 測試副本的 `layer_path` 必須用這個字，不能寫「磚牆」 |

### 建議新增

**23. 建立 Registry 漂移副本（優先，對應 QR-02）**
原始檔已經 37／37 對齊，測不到失敗路徑。隔離副本至少要有：live 有、Registry 無；Registry 有、live 無；revision／內容雜湊不同；未知 `schema_id`。每種都要有期望狀態，不能只改一個數字。

**24. 將 hidden／locked 做成可重跑 oracle（對應 QR-04）**
原始模型已有 `EL-07` 隱藏、`SA-01` 鎖定。副本應明確記錄「這兩件必須進全集、必須能量測或標不可量測，不得因隱藏／鎖定被漏掉」。

**25. 重複 `_07_UUID` 與來源複本 GUID 碰撞（對應 QR-01）**
本 session 3116 個 GUID 不重複、37 個 UUID 不重複，所以「conflict、不猜配」這條路目前是空的。

**26. 將 Cabinet Group／Z-up OBB 做成正式 fixture（對應 QD-16～19）**

已有兩組探索性樣本，每組相同櫃體各含 11 個 Brep：`LoopFlow_R_MCP.rws`（09-02）的 0°／45°，World bbox `100 × 36.746 × 75`、`96.694 × 96.694 × 75` cm；`LoopFlow_3D.3dm`（09-03）的 0°／30°，World bbox `100 × 36.746 × 75`、`104.976 × 81.823 × 75` cm。四組方向校正後的 Z-up OBB 都是 `100 × 36.746 × 75` cm，09-03 兩組體積同為 `95035.7251 cm³`。正式 fixture 還須補：

- 真正 Group Name 與成員物件名稱不同，QTY 只採前者
- 巢狀子群組、部分重疊與交叉群組，避免同一零件重複計量
- 90°、任意角、鏡射，以及把手／檯面突出造成外包尺寸改變
- 弧形與不規則櫃；仍輸出 OBB，並驗證方向診斷不會靜默宣稱高信心
- cm／mm 文件單位換算後得到相同物理尺寸
- Group 改名、解散、增減成員後的 lost／changed 報告
- `_Copy` 複製整組櫃體：複本自成新群組但**不帶名稱**，必須被列為待命名，不得靜默從數量表消失
- 解散最外層後子群組仍在、重新成群取得新 index 與自動名稱；重新命名一次即可恢復可量測
- 重新成群時漏選一個零件：名稱照樣寫得上去但 OBB 變小，必須由檢查抓出
- 櫃體圖層上未成群的零件必須被報告（QD-20）；同類零件需同時有已成群與未成群兩種
- 成員空間一致、不一致與 `EXT` 三種情形各一（QD-21）
- Group Table 內混有非櫃體群組（樓板、飾條）時不得被當成櫃體
- **群組內混入 curve／point（QD-25）**：目前兩份工作檔的所有群組都只有 Brep，這條完全沒有樣本。fixture 需刻意放一條**超出櫃體範圍的參考線**與一個放置點，驗證 OBB 與沒有它們時完全相同；另建一個「只有線」的群組，驗證回報「無可量測成員」而不是零尺寸
- Block 成員（例如把手圖塊）須套用實例 transform；旋轉與鏡射的 Block 各一個樣本

兩份工作檔的命名狀態不同，fixture 要分別對待：`LoopFlow_R_MCP.rws` 的 `櫃體群組測試0`／`櫃體群組測試45` 是成員物件名稱，真正外層 Group Name 仍為 `Group03`／`Group04`；`LoopFlow_3D.3dm` 則是 12 個群組全為自動名稱、成員完全沒有物件名稱（Toolkit 的同步指令已因此取消，一律直接命名）。正式 fixture 應先用 `SetGroupName` 建立可辨識的真正名稱，再保存 manifest 與 oracle，不要直接拿正式工作檔當 fixture。

補強順序建議把 **23、25 插入第 2 批**（與身分、`m2` 一起），**24、26 可與第 4 批**的 Coverage／開檔方式一起。
