## 0　雙 AI 覆核說明（2026-09-02）

- `Claude 意見` 是對 Claude 第一版文件既有主張的摘要，不代表本輪重新詢問 Claude
- `Codex 意見` 是依 LoopFlow 2.0 的開發方式、現行六份權威文件與 repo 程式接縫所做的獨立覆核
- 本輪只增加覆核意見，**不直接改變原決策狀態**；標為「建議改列暫定／未定」者，須由使用者裁決後再移表並留下理由

### 覆核結論

整體方向正確：QTY 維持獨立產品、單向唯讀、GH1 可視流程、外部 Python 核心、先視覺檢核再輸出 Excel，均符合 2.0「人決定、系統檢查、可預覽、可重跑、不靜默修復」的原則。

但目前仍有三個實作阻擋項：

1. **輸入權威未定**：`Project_Registry.json`、現況物件與現行 Dictionary 發生 revision 漂移時，誰優先尚未裁決（QO-13）
2. **持久身分未閉合**：一般物件可用 `_07_UUID`，但結構體沒有 UUID；「一式」黑名單與外部選取 JSON 尚無全類型共同身分契約（QD-02／QD-08／QD-10）
3. **長度算法尚非可交付答案**：15 件中已有 2 件失效，且轉角與閉合環是常見實務幾何；目前只能標異常，不能保證產出正確數量（QD-07）

### 進入實作前關卡

比照 2.0，不先做大型 `.gh`：

1. 先裁決上述三項阻擋，定義 QTY 的 `schema_id`／`schema_version`、輸入優先序與物件身分
2. 先建立合法／錯誤 fixtures 與 golden baseline，至少涵蓋直線、轉角、閉合環、包覆面、開口、Block、結構體、參照失效與直接開 3D 兩種工作方式
3. 先做可在 Rhino 外測試的純 Python 核心，再做 Rhino adapter；GH Python 電池只負責轉交與顯示
4. 實作以「掃描 → 分類／選取 → 量測 → Coverage → 預覽 → 明確確認 → Excel」分批，每批都要能取消、重跑並留下可驗證停點
5. Rhino MCP 只用於開發期唯讀觀察與安全的無互動驗證，不成為產品 runtime 相依

| **QO-17** | **大量物件的效能** | 掃描涵蓋 3116 筆但未計時 | 需計時 | 先定 benchmark：列舉總量、候選 3D 數、逐物件量測與 preview 分開計時；至少測 100／1,000／5,000 候選，ReferenceObjects 開關與取消路徑都要量 |

## 4　必須先修的既有缺陷

| 項目 | 狀況 |
|---|---|
| `quantity.py` 的 `m2` 換算 | `_area()` 對「才」「坪」正確，但 `m2` 直接回傳 cm²（**少除 10000**）。目前字典沒用到 `m2` 所以**不會發作**，一旦有人新增 `m2` 規則就會出現，錯誤量級一萬倍。**撈回該檔時務必先修** |
| 撈回 `measure.py` 的三處調整 | `load_from_workfiles` → `load_dictionary(session)`；`TYPE_ID_KEY` 已搬到 `foundation.usertext`（值 `"_03_ID編號"`）；`QUANTITY_KEY` 已刪除且本來就不該用 |
| 文件路徑 | 舊報告寫的 `wip/src/loopflow/` 已過時，現在是 **`v2/src/loopflow/`** |

## 5　安全紀律（不可協商）

以下不是設計選擇，是實測付出代價換來的：

| 禁止 | 原因 |
|---|---|
| 在承載使用者工作檔的 Rhino 內以 MCP headless 載入 `.gh` | 已造成一次 Rhino 凍結退出。工具逾時後 MCP ping 成功**不代表** runtime 已恢復 |
| 用 MCP 代開 `.rws` | 需由使用者手動開啟 |
| 用 `run_command` 執行 LoopFlow 產品指令 | 模態視窗導致靜默失效 |
| 把空 `stdout` 當作成功 | 那正是靜默失效的表徵 |
| 把 MCP 設定寫進任何 repo | 本機專屬，路徑含使用者名稱與版本號 |

完整說明見 [`MCP評估/MCP設定交接.md`](../MCP評估/MCP設定交接.md) §7。
