0.1 Codex 第二輪覆核結論（2026-09-02）

Claude 建立的第二輪骨架可沿用，但進入實作前要修正四點：

  1. 裸 Rhino GUID 不能單獨作全類型持久主鍵。它只在單一來源模型內唯一；來源的絕對路徑與 worksession model index／serial 又不能跨電腦、開檔方式與 attach 順序持久化。應採版本化、可分流的 locator（QR-01）。
  2. Dictionary token 與目前算法有語意衝突。2.0 的 ND-28 明定 AREA_WD／WH／DH、LEN_W／D／H 各自選軸；現行量測方法卻把三種面積 token 都算最大面、三種長度 token 都算中心線。這不是單純 warning，須先裁決（QR-15）。
  3. 測試資產必須與原始工作檔隔離。幾何、Dictionary、Registry 都在副本補強；每個案例要有期望值、容差與期望狀態，不能只加形狀。
  4. QTY 是獨立產品。可參考 2.0 的契約與 writer，但不能把 v2/src/loopflow 的私有模組變成未版本化的 runtime 相依；實作期也應仿照 2.0 使用獨立整合分支。

QR-09規則與幾何相容性（QO-08）一般建議：先作 warning，不阻擋、不自動換規則。AREA_WH／AREA_WD 是估價語意，不等同幾何朝向——CB-06 水平檯面掛 AREA_WH 可能是字典登錯，也可能是估價慣例，程式不該判斷一般建議同意 warning 原則，但它不能掩蓋 QR-15：相容性檢查可只警告，實際執行哪個 measurement token 的語意仍須先裁決；程式不得把 token 自動換掉或把不同 token 靜默當同義詞一般建議同意 warning，且不得掩蓋 QR-15。 CB-06 證明「最大面能算出數」與「token 寫的是哪個軸」是兩件事。警告可以有；把 AREA_WH 靜默當成最大面不行待決定
QR-10QTY_Save 寫入時機（QO-07）強烈建議：預覽不寫；明確確認才 atomic write，並有 pending／last-good，對齊 2.0 Registry 發布模式。禁止 Panel Stream Contents。這條屬強烈是因為它防的是「使用者以為只是看看、結果狀態被改掉」強烈建議同意。確認前檔案系統零寫入；確認後先寫 pending、完整驗證與讀回，再原子取代 current 並保留 last-good。寫入失敗不得破壞上一版，也不得讓 GH re-solve 自動重試覆寫強烈建議同意。 確認前零寫入；確認後 pending → 驗證讀回 → atomic replace → 保留 last-good。GH re-solve 不得重試覆寫待決定
QR-11自訂 GH 型別（QO-09）輕鬆建議：MVP 不建自訂 GH type，核心用 Python dataclass，GH 邊界才轉 Data Tree輕鬆建議同意。先以 typed record／dataclass 固定欄位；只有跨多個 GH 元件後仍無法可靠維持 schema，才另評估自訂型別輕鬆建議同意。 MVP 用 dataclass；過早自訂 GH type 會讓多 AI 難接手待決定
QR-12Label 定位（QO-10）一般建議：只用非持久化 preview／conduit，不得新增 Rhino 文件物件——新增物件會違反 QD-11 的唯讀 invariant。第一版允許重疊並標示強烈建議採非持久化預覽：這不是版面偏好，而是 QD-11 的唯讀安全線。驗收須比較 preview 前後物件、UserText、顯示屬性與 doc.Modified；第一版重疊可接受強烈建議同意 Codex：非持久化是 QD-11 invariant，不是版面偏好。驗收必須證明 preview 前後物件數、UserText、顯示屬性與 doc.Modified 不變。第一版重疊可接受待決定
QR-13Coverage 五態（QO-11）一般建議：先定 enum、互斥規則與優先序，再定顏色。顏色不得作為唯一狀態來源；報告必須保留文字狀態與原因強烈建議部分調整：Coverage 五態可互斥，但必須與 measurement status 分成兩個欄位；同一物件可以同時是「已選取」與「不可自動量測」。若硬塞成單一優先序，會遺失其中一個事實。顏色只顯示合成結果，文字報告保存兩軸狀態與原因強烈建議同意 Codex 的雙軸。 單一優先序會讓「已選取但不可量測」只剩一個標籤。顏色只是合成顯示；文字報告保存 Coverage 與 measurement 兩欄。EL-07 隱藏仍應能進 Coverage待決定
QR-14Excel（QO-12）一般建議：先鎖欄位契約與 golden xlsx，沿用既有 writer 產靜態表。公式屬可選後續，不擋 MVP。QTY 程式不進 v2/src/loopflow，以 adapter 呼叫共用 writer一般建議，條件同意：欄位契約、golden xlsx、靜態表優先都同意。但「共用 writer」須是版本化的公開 shared boundary；若仍是 v2/src/loopflow 私有模組，QTY 應有自己的薄 adapter／受測實作，不能形成隱性 runtime 耦合。公式不擋 MVP一般建議，同意 Codex 的條件。 先鎖欄位與 golden xlsx。不可直接 import v2 私有 writer；要嘛版本化 shared boundary，要嘛 QTY 自帶受測薄 adapter。公式不擋 MVP待決定

QR-15Dictionary measurement token 的軸向語意與現行算法衝突強烈建議：接受 Codex 的指認，且我原本的 §9 對照表確實錯了——把 8 個 token 映成 2 種算法等於宣稱查字典卻把 token 當同義詞。
但補一項本輪實測，它讓這題有第三條路：字典 92 筆中 8 個 token 只用了 5 個——COUNT 41、LEN_W 20、AREA_WD 14、AREA_WH 15、VOL_WDH 2，而 AREA_DH、LEN_D、LEN_H 全部 0 筆。也就是說字典實際做的唯一軸向區分是水平面積 vs 立面面積，而那正是面法向量給得出來的，不需要平面。真正無解的 W vs D 區分只存在於那三個 0 筆的 token。
因此提案：token 當「方向約束」而非「軸選擇器」——AREA_WD 要求最大面為水平、AREA_WH 要求垂直、LEN_W 要求中心線為水平走向；不符即 不可自動量測，不靜默替代。AREA_DH／LEN_D／LEN_H 第一版明確不支援，遇到即不可量測並註明原因是「QTY 不指定平面因此無法區分 W 與 D」。
已實測：15 個面積類物件 14 符、1 不符，唯一不符的正是 CB-06（AREA_WH 但最大面水平）——零誤報，且正好標出 QR-09 要的那件。
