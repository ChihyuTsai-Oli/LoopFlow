## 1　產品定位

QTY 與出圖 2.0 **同 repo、不同產品**。不是 2.0 的模組，不進 Package Manager `loopflow`，不共用 `.yak`。

```text
LoopFlow 2.0（出圖）          QTY（數量計算）
      │                            │
      ├─ 寫入物件 UserText          ├─ 只讀，不寫回
      ├─ 發布 Registry             ├─ 讀 Registry／物件／字典
      └─ 產出圖面                   └─ 產出獨立 Excel
```

**單向。** QTY 讀 2.0 留下的資料，自己產出 xlsx，不回寫任何東西。

## 2　做與不做

| 做 | 不做 |
|---|---|
| 讀 3D 幾何量測數量 | 寫回物件 UserText、Registry、Nexus |
| 讀 Dictionary 取得計量規則與單位 | 修改 Dictionary 的規則／單位詞彙表 |
| 輸出獨立 Excel（估價單＋明細） | 打進 2.0 的 `.yak` 或工具列 |
| 在模型中以顏色與文字做視覺檢核 | 永久改變 Rhino 物件的顯示屬性 |
| 標記漏算、重複、衝突、失效參照 | 自動修復上述任何一項 |
| 結構體另以 `layer_path` 查規則 | 要求結構體具備 UUID／空間／高程 |
| 讀取已命名的 Cabinet Group 並輸出 Z-up OBB 長寬高 | 建立／改名群組、替櫃體自動判斷高矮深淺 |

### 2.1 為什麼不能寫回物件

`v2/src/loopflow/foundation/usertext.py` 有一份 `STALE_OBJECT_KEYS`，包含 `Q_01_寬度W`～`Q_06_實作數量`、`lf_quantity` 等。它有兩個消費者：

1. `clear_stale_object_text()` — `LFNexus` 步驟 5 寫入時**清空**這些 key
2. `features/model_data/verify.py` — 步驟 6 檢核時把這些 key 回報為 `stale_dimension` **問題**

若 QTY 把數量寫回物件，會造成互鎖：

```text
檢核不通過 → LFPublishExchange 被擋 → 產不出新 Registry
           → 而 Registry 正是 QTY 的輸入來源
```

且症狀出現在 LoopFlow 側（「檢核一直報 stale dimension」），不易聯想到 QTY。**單向流程使此風險不存在**；本節僅作為未來變更時的警告。

## 3　核心流程

```text
Rhino 3D 物件
    ↓
使用者手動選取、分類          ← 人的判斷
    ↓
逐物件計算；已命名櫃體群組另計 Z-up OBB ← 系統
    ↓
模型中著色與標數字            ← 系統呈現
    ↓
使用者目視確認                ← 人的判斷
    ↓
分組、排序                    ← 系統
    ↓
Excel（估價單＋明細）
```

**核心不是「模型自動產生 Excel」**，而是：

> 選取 → 計算 → 空間視覺化 → 人工確認 → 輸出

Excel 是結果，不是系統中心。視覺檢查是正式流程的一環，不是裝飾——空間中的顏色與數字能提供 Excel 給不了的直覺檢查能力。

## 4　人機分工

沿用 LoopFlow 2.0 的原則：**保留人為判斷，系統負責檢查**。

| 人決定 | 系統負責 |
|---|---|
| 這次要算哪些物件 | 計算、加總 |
| 這批屬於哪個估價分類 | 顯示、著色 |
| 櫃體輸出後的分類與單位 | 依真正 Group Name 集合成員並輸出 raw OBB 長寬高 |
| 哪些是「一式」 | 檢核（漏算／重複／衝突／失效） |
| 衝突與異常怎麼處理 | 整理、排序、輸出 |

系統**只標記，不自動修**。這與 `LFTagO` 一致。

## 5　刻意排除在工具之外

以下不進 QTY 的自動計算範圍，最後在 Excel 人工加入：

- **非模型項目**：假設工程、清運、保護工程、管理費、利潤、稅
- **損耗率**（磁磚 +5%、木作 +10% 等）：依廠商、專案、市況變動，是商業判斷不是幾何事實。工具輸出**淨數量**，損耗在 Excel 以係數欄處理，隨時可改、改了看得見
- **單價**：估價單留白供人工填寫；是否預填參考單價尚未決定

## 6　「一式」的處理

「一式」**不列入 Dictionary**，不新增 `measurement_rule` 或 `estimation_unit` 的「式」token——避免動到 2.0 已發布的 schema，也避免舊版讀到新字典會 `block`。

> **這裡的 `block` 是字典驗證的判定值**（`pass`／`warn_no_quantity`／`block`，意即「擋下」），**不是 Rhino 圖塊**。一式對象**沒有「必須建成 Block」的要求**；相反地，Block 會讓實例內部的零件不再是文件物件，各零件無法個別掛 Tag、也不會進 Registry 與圖面材料標示。載體應為命名群組（QD-23 待裁決），估價上整座算一式，圖面上材料仍各自存在。

實際操作：在選取階段人工標記為「一式」類別，不進計算批次。

**排除必須是主動的集合差集，以物件識別為唯一依據。** 一式物件仍是正常的 LoopFlow 物件，身上照樣有 `type_id`，理論上仍可透過字典 join 到規則。若未來有任何元件是「依 `type_id` 自動抓取物件」，一式物件會因為有 `type_id` 而被撈進去算，**且不會報錯，只是安靜地多算一筆**。

因此：**不能倚賴「沒有接進計算電池」來避免計算**。一式集合的角色是全域黑名單，不是電路沒接到的消極結果。

## 7　執行環境

| 項目 | 決定 |
|---|---|
| 主要工作場所 | **Grasshopper**。整條資料鏈可見是 GH 的價值 |
| Rhino 工具列 | 刻意保持很薄，只處理啟動、工作環境、專案狀態 |
| 計算邏輯的位置 | **外部 `.py`**，GH Python 電池只放薄殼 |
| GH 版本 | GH1（Rhino 8）。不採用需要 Rhino 9 的 GH2 |

計算邏輯住外部 `.py` 的理由：`.gh` 是二進位，程式碼埋在裡面則 git 看不到 diff、無法 headless 測試、多 AI 接手時交接鏈中斷。

**薄殼必須含 `importlib.reload()`**，否則改了外部 `.py` 後 GH 重新求解仍吃到舊程式碼（實測確認，見 [`MCP評估/實測報告.md`](../MCP評估/實測報告.md) §4.2）。

## 8　與 MCP 的關係

MCP **不是產品的一部分**，是開發期的工具。

QTY 對 MCP 的用途限於：讀取模型與 canvas、建立／修改 GH canvas、執行無互動的 Python、驗證結果。

**不得**用 MCP 代替使用者操作 LoopFlow 產品指令，也不得 headless 載入 `.gh`（已造成一次 Rhino 當機）。細節見 [`MCP評估/MCP設定交接.md`](../MCP評估/MCP設定交接.md) §7。
