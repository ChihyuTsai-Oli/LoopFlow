## 0　本輪規則

決策編號 `QR-nn`（Round 2）。比照 [`v2/docs/前期規劃/資料生態決策表.md`](../../../v2/docs/前期規劃/資料生態決策表.md)，採三種建議強度：

| 強度 | 意義 |
|---|---|
| **強烈建議** | 最好照做；關係到資料不斷鏈、可復原、避免靜默錯誤或能否長期擴充。若不採用，需先設計同等安全的替代方案 |
| **一般建議** | 可以改，但會增加相應的規則、操作或維護成本；決定時需明確接受代價 |
| **輕鬆建議** | 原則上不影響核心資料鏈，可依實際習慣、時程或介面偏好調整 |

裁決規則（2026-09-23 使用者裁定）：**三家意見中，只要兩家持相同意見，就採用該多數意見**，不再逐項等待使用者確認。建議強度用來表達風險，不影響票數。若兩家只共同支持安全底線或「暫不實作」，卻沒有選出同一套具體做法，則只採用該共同部分，剩餘做法維持待決。

> 各家只填自己的欄，不代填、不推測其他 AI 的立場。

### 0.1 Codex 第二輪覆核結論（2026-09-02）

Claude 建立的第二輪骨架可沿用，但進入實作前要修正四點：

1. **裸 Rhino GUID 不能單獨作全類型持久主鍵**。它只在單一來源模型內唯一；來源的絕對路徑與 worksession model index／serial 又不能跨電腦、開檔方式與 attach 順序持久化。應採版本化、可分流的 locator（QR-01）。
2. **Dictionary token 與目前算法有語意衝突**。2.0 的 ND-28 明定 `AREA_WD／WH／DH`、`LEN_W／D／H` 各自選軸；現行量測方法卻把三種面積 token 都算最大面、三種長度 token 都算中心線。這不是單純 warning，須先裁決（QR-15）。
3. **測試資產必須與原始工作檔隔離**。幾何、Dictionary、Registry 都在副本補強；每個案例要有期望值、容差與期望狀態，不能只加形狀。
4. **QTY 是獨立產品**。可參考 2.0 的契約與 writer，但不能把 `v2/src/loopflow` 的私有模組變成未版本化的 runtime 相依；實作期也應仿照 2.0 使用獨立整合分支。

### 0.2 Cursor 第二輪覆核結論（2026-09-02）

在公司電腦對使用者已開啟的 `LoopFlow_R_MCP.rws`（Rhino 8 adopted slot `aardvark`，pid 28836）做唯讀 `run_python`。沒有開啟 GH、沒有執行產品指令、執行前後 `doc.Modified` 皆為 false。數字與 Claude／Codex 一致，另補三點：

1. **QR-01 採 Codex 的 locator，不採 Claude 的裸 GUID 單鍵。** GUID 跨 Rhino 重啟穩定只證明「不是每次啟動重配」。本 session 3116 個 GUID 互不重複，仍不能當跨來源、跨電腦的持久主鍵。
2. **QR-15 是第四個實作阻擋，不能用最大面先做再改 token。** QD-05「使用者不提供平面」可以保留；不能為了「尊重 ND-28」把 1.x 的 local W／D／H 或指定平面救回來。未裁決前 Excel 不得寫 `AREA_WH` 卻實際算最大面。
3. **原始模型現在測不到漂移、曲面、室外與一式。** Config／Registry 已在且 37／37 對得上，因此 QR-02 的失敗路徑必須靠隔離副本，不能再改這份工作檔。

共同安全底線（三家無衝突的強烈部分）：選取 JSON 不能只存 GUID、也不能存絕對路徑／session serial；未知 `schema_id`／`schema_version` 整批停止；失效不得輸出淨數量；`DNA_REF_` 必須明寫排除；產品 runtime 不依 MCP；確認前零寫入；Label 不得新增文件物件。

依 2026-09-23 二票多數決，QR-01 採版本化 locator，QR-13 採 Coverage／measurement 雙軸。QR-15 只有安全底線形成多數，具體 token 算法仍未形成兩家相同方案。

## 1　本輪新增的實測發現

2026-09-02 於公司電腦，同一份 `LoopFlow_R_MCP.rws` 以 MCP 唯讀複核。

### 1.1 GUID 跨 session 穩定（解掉阻擋項 2 的關鍵）

本 session 稍早在**不同 Rhino 行程**記錄的三個參照物件 GUID，於 Rhino 重啟後**全部仍指向同一物件**：

```text
ec5f23f1-4d2b-46ba-a136-3eb82ab5928e   ✅ 仍存在（結構 Stair.樓梯）
9bc74080-4bd0-4e90-918b-8c485a999b34   ✅ 仍存在（結構 Curb.墩座）
b4fae896-bf13-4b19-9ff3-6f5ed902ba1f   ✅ 仍存在（CL-06）
```

**意義**：worksession 參照物件的 GUID 來自來源 `.3dm`，不是執行期配發。結構體雖無 `_07_UUID`，仍有可跨 session 持久化的身分。

**未驗證的邊界**：來源 `.3dm` 被編輯後是否仍保持；物件被刪除重畫必然換 ID（與 2.0 的 ECO-11 同源問題）。

### 1.2 `DNA_REF_*` 全部是 Point，不會污染全集

3D 側 92 個 `DNA_REF_*`（2.0 的字典參考線，ED-11 保留用於防止空圖層被 Purge）**全部是 Point**。

因此「Brep ＋ InstanceReference」的全集篩選**誤收數為 0**。但這是巧合而非保證——若日後 `DNA_REF_*` 改用其他幾何，全集就會靜默納入字典佔位物件。
