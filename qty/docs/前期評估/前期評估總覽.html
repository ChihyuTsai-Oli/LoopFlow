2.1 為什麼不能寫回物件

v2/src/loopflow/foundation/usertext.py 有一份 STALE_OBJECT_KEYS，包含 Q_01_寬度W～Q_06_實作數量、lf_quantity 等。它有兩個消費者：

  1. clear_stale_object_text() — LFNexus 步驟 5 寫入時清空這些 key
  2. features/model_data/verify.py — 步驟 6 檢核時把這些 key 回報為 stale_dimension 問題

若 QTY 把數量寫回物件，會造成互鎖：

檢核不通過 → LFPublishExchange 被擋 → 產不出新 Registry
           → 而 Registry 正是 QTY 的輸入來源

且症狀出現在 LoopFlow 側（「檢核一直報 stale dimension」），不易聯想到 QTY。單向流程使此風險不存在；本節僅作為未來變更時的警告。

核心不是「模型自動產生 Excel」，而是：

選取 → 計算 → 空間視覺化 → 人工確認 → 輸出

Excel 是結果，不是系統中心。視覺檢查是正式流程的一環，不是裝飾——空間中的顏色與數字能提供 Excel 給不了的直覺檢查能力。

5　刻意排除在工具之外

以下不進 QTY 的自動計算範圍，最後在 Excel 人工加入：

  • 非模型項目：假設工程、清運、保護工程、管理費、利潤、稅
  • 損耗率（磁磚 +5%、木作 +10% 等）：依廠商、專案、市況變動，是商業判斷不是幾何事實。工具輸出淨數量，損耗在 Excel 以係數欄處理，隨時可改、改了看得見
  • 單價：估價單留白供人工填寫；是否預填參考單價尚未決定

6　「一式」的處理

「一式」不列入 Dictionary，不新增 measurement_rule 或 estimation_unit 的「式」token——避免動到 2.0 已發布的 schema，也避免舊版讀到新字典會 block。

這裡的 block 是字典驗證的判定值（pass／warn_no_quantity／block，意即「擋下」），不是 Rhino 圖塊。一式對象沒有「必須建成 Block」的要求；相反地，Block 會讓實例內部的零件不再是文件物件，各零件無法個別掛 Tag、也不會進 Registry 與圖面材料標示。載體應為命名群組（QD-23 待裁決），估價上整座算一式，圖面上材料仍各自存在。

實際操作：在選取階段人工標記為「一式」類別，不進計算批次。

排除必須是主動的集合差集，以物件識別為唯一依據。 一式物件仍是正常的 LoopFlow 物件，身上照樣有 type_id，理論上仍可透過字典 join 到規則。若未來有任何元件是「依 type_id 自動抓取物件」，一式物件會因為有 type_id 而被撈進去算，且不會報錯，只是安靜地多算一筆。

因此：不能倚賴「沒有接進計算電池」來避免計算。一式集合的角色是全域黑名單，不是電路沒接到的消極結果。

7.1 檔案配置（2026-09-03 裁決，QD-26）

QTY 作業一律在 3D 檔進行。只有兩種合法配置：

配置說明
a直接開啟「需要計算數量」的 3D 模型檔預設情形
b.rws worksession，2D attach 進 3D3D 是作用中模型，2D 只作參考

理由：計算過程需要從 GH 選取物件，也可能需要用 Nexus 補充或修改模型資料。參照物件不可編輯，所以要被計算與修改的 3D 模型必須是作用中模型，不能是被 attach 進來的那一份。

先前 MCP 驗證用的 LoopFlow_R_MCP.rws 是「3D attach 進 2D」，方向相反，不符合本規則。 它仍是既有數字的來源，但不再是實務配置的代表；新的 fixture 必須以 a／b 兩種配置建立（見 測試模型.md 項目 17）。

由此得到三個直接推論：

  1. 要計算的物件一律是本機物件（IsReference == False）。列舉器不需要靠 ReferenceObjects = True 才看得到計算對象——那是舊配置的產物（QD-15）。配置 b 底下 attach 進來的 2D 內容是參照物件、而且是 Curve，被 QD-01 與本規則雙重排除。
  2. 群組名稱不會帶來源檔前綴。<檔名> : 前綴只會出現在被 attach 的那一份；既然 3D 永遠是作用中模型，QTY 的群組名稱一律是原名。若真的讀到帶前綴的 QTY_ 群組，代表開錯檔（3D 被 attach 了），應報設定錯誤而不是照樣量測（QD-24 改寫）。
  3. layer_path 不帶檔名前綴，圖層正規化少一個分支。

薄殼必須含 importlib.reload()，否則改了外部 .py 後 GH 重新求解仍吃到舊程式碼（實測確認，見 MCP評估/實測報告.md §4.2）。

8　與 MCP 的關係

MCP 不是產品的一部分，是開發期的工具。

QTY 對 MCP 的用途限於：讀取模型與 canvas、建立／修改 GH canvas、執行無互動的 Python、驗證結果。

不得用 MCP 代替使用者操作 LoopFlow 產品指令，也不得 headless 載入 .gh（已造成一次 Rhino 當機）。細節見 MCP評估/MCP設定交接.md §7。

LoopFlow QTY — 量測方法

本文件是 QTY 量測方式的唯一來源。資料現況見 資料盤點.md，決策狀態見 決策紀錄_1.md／決策紀錄_2.md。

建立日期：2026-09-01　｜　本文數值均在驗證模型上實測；token 語意仍受 QR-15 阻擋，尚非實作契約

1　核心原則

不拆解 W／D／H。不需要平面輸入。不需要方位判斷。

第二輪覆核警告：這個幾何策略與 2.0 ND-28 的既有契約有衝突。ND-28 將 AREA_WD／WH／DH、LEN_W／D／H 定義為不同軸向；本文 §9 暫時把它們各自合併成同一算法。QR-15 裁決前，本文只能作演算法探索證據，不能宣稱已按 Dictionary token 執行。

1.1 為什麼放棄 W/D/H 模型

LoopFlow 1.x 的 features/dimension/frame.py 用 local frame 拆出 W／D／H。QTY 早期構想沿用此模型，需要使用者指定平面。實測證明這條路走不通，三個層次的理由：

① World bbox 會安靜地錯到離譜

驗證模型整體轉 30°（刻意的測試設計）。WL-14 磁磚牆面 的 World bbox 是真實體積的 127 倍。全程無任何錯誤或警告。

② 使用者給錯平面一樣不報錯

實測同一物件：正確平面（30°）得到精確值；錯誤平面（45°）錯 60%，同樣不報錯。所以「讓使用者指定平面」只是把靜默失敗的責任轉移，沒有消除它。

③ 同一道牆本身就可能有多個角度

L 型牆、弧牆、轉角包覆面——這類物件根本不存在「一個平面」可套，W/D/H 模型直接失效。而實務上牆的方位本來就是各角度混和。

1.2 改為直接從幾何取值

面的法向量與面積是每個面自帶的。轉幾度、彎幾次、混幾種角度，處理方式完全一樣。

規則需要的東西需要平面嗎
COUNT數量不需要幾何
AREA_WD水平面積❌
AREA_WH立面面積❌
LEN_W延伸長度❌
VOL_WDH體積❌

沒有一個需要平面輸入或軸向判斷。

2　共通設計原則

每種量測都採用：

一個主要算法 ＋ 一個能抓出它失效情境的對照值

不追求單一萬用演算法，而是確保失效時會出聲。

實測結果：30 個物件只對 3 個發出標記，其餘完全不吵。

這與 LoopFlow 一貫的「標記，不自動修」一致。

3　面積

主要值：最大單一面面積
對照值：體積 ÷ 厚度      （厚度 = 2 × 體積 ÷ 總表面積）
差異 > 10% → 標記「可能是多段包覆面，最大面會少算」

3.2 「最大單一面」的三個好處

① 自動排除邊帶。 薄板側邊那一圈不會被算進去。比「垂直面總和 ÷ 2」準 1～4%。

② 自動處理立面／平面。 它不管面朝哪裡。CB-06 是水平檯面卻掛 AREA_WH 規則，最大面直接給出正確的 3,675 cm²（＝100×36.75）；若用「取垂直面」則只會得到那圈側邊的 342 cm²，完全錯誤。

這順帶解掉一個難題：同一材料可能既用於立面又用於平面（例如同款石材做牆面也做檯面），難以在字典預先定義。最大面法不需要區分，問題在計算層自動消失。剩下的只是報表要不要分開列。

③ 自動扣除開口。 實際存在的面才會被算到。WL-03 的門洞自動不在面積內。

3.3 唯一失效情境

多段包覆面——WL-14 有 22 個面（牆轉了彎），最大面只抓到其中一段，少算約 47%。這正是對照值要抓的。

4　長度

主要值：體積 ÷ 端面截面積     （得到中心線長度）
對照值：最長邊
差異 > 2% → 標記

4.1 為什麼是「體積 ÷ 截面積」

長度類物件（收邊條、燈帶、窗簾盒）大多是沿折線或曲線擠出的實體，不是直線。bbox 完全不適用——彎曲物件的 bbox 寬度與其長度無關。

體積除以截面積得到的是中心線長度，不管路徑怎麼繞都成立。

6　開口扣除

原則上不扣除門窗開口。 但若出現很大的非門窗開口，需要判定。

偵測方式：毛體積 ÷ 實體積。

扣除率 = 1 − 實體積 / 毛體積

實測：24 個為 0.0%，WL-03 為 22.4%（≈一個門洞），WL-04 為 5.0%。

限制：此指標分不出「開口」與「形狀本來就不是方塊」。CB-04 鐵件框架 扣除 95.6%、CL-03 木作窗簾盒 79.2%，那些是中空構件。

因此只能標記後由人判斷。閾值待定（見 決策紀錄_1.md）。

7　方位偵測（備用）

雖然主要方法不需要方位，但若日後需要（例如做規則與幾何的相容性檢查），有兩種方式：

方法成本實測
掃描 0～89° 找最小貼合度90 次 bbox 運算30/30 正確找出 30°
最大平面面的法向量O(1)15/15 與掃描一致，0 不符

法向量法快幾十倍。但最大面為水平時（地坪、檯面）法向朝上、給不出牆向，需改用該面最長邊的方向。

貼合度的正確判準不是「＝1」，而是「在候選角度中最小」。非方塊形狀就算平面正確、貼合度也不會是 1——實測 L 型物件在正確角度的貼合度是 1.724，但那仍是所有角度中的最小值。

群組沿用 QD-01／QD-03 的全集定義，不另立例外：只有 Brep 與 InstanceReference 進入量測，其餘型別一律當作不存在。

  • 群組裡的施工參考線、中心線、放置點不會撐大 OBB。這正是要當作不存在的實益——否則一條超出櫃體的參考線就會讓長度多出一截。

  • 效能放大模型與參照失效模型各自獨立，不能和正確性模型混在同一檔，否則盤點數字與 golden baseline 會一起漂移。
  • repo 只保存可合法提交的小型 fixtures、期望輸出與建立說明；大型或含專案資料的 Rhino 工作檔留在工作檔區，repo 內以 manifest 記錄檔名、版本與雜湊，不寫某台電腦的絕對路徑。

0.3 每個樣本都要有 oracle

只「加一個形狀」不足以形成測試。每個樣本至少記錄：

  1. 建構尺寸／方式與用途
  2. 預期 measurement token、估價單位與 exact value
  3. 可接受容差
  4. 預期 measurement status、Coverage status 與警告原因
  5. 身分來源（object_id 或 source_model_key + Rhino GUID）

若預期答案尚未能由人工或另一種可信方法確認，該物件只能標為探索樣本，不能列入 golden pass/fail。

1　幾何形狀（優先）

1. 新增弧形牆面 目前所有 Brep 都是平面組成。弧牆的「最大單一面」是一個曲面，AreaMassProperties 給的是展開面積——這正是估價要的，但完全沒有驗證過。若曲面被切成多片，最大面法會像 WL-14 一樣少算，需要對照值抓。

2. 新增 L 型與 U 型牆面（各至少 2 個，轉角角度不同） WL-14 是目前唯一的多段包覆樣本。需要不同轉折數與不同夾角，才能確認「最大面 vs 體積÷厚度」的 10% 閾值是否合理，或該不該依轉折數調整。

3. 新增斜面物件（斜天花、斜屋頂或樓梯側牆） 目前所有面不是水平就是垂直。斜面會讓「最大面朝哪裡」的判讀進入灰區，也會影響 AREA_WD／AREA_WH 的相容性檢查（QR-09）。

4. 新增弧形收邊條或弧形燈帶 長度法的「體積 ÷ 端面截面積」理論上對曲線路徑成立，但目前只有直線與一個轉角驗證過。弧形是實務常見（弧牆的收邊），必須測。

5. 新增第二、第三種閉合環物件 CB-04 鐵件框架 是唯一的閉合環，且兩個實例完全相同。需要不同尺寸與斷面的環（例如圓形燈帶、口字型框），才能驗證 fallback「取環的中心線周長」。

6. 新增更多開口樣本，並涵蓋不同開口比例 目前只有 22.4%（門洞）與 5.0%（小開孔）。建議補：兩個開口的牆、開口占比 40～60% 的牆、以及開口貫穿但形狀不規則的牆。用來定 QR-07 的閾值。

7. 新增「中空但不是開口」的對照物件 CB-04（95.6%）與 CL-03（79.2%）目前是僅有的中空構件。多幾個（例如格柵、百葉、鏤空屏風）才能確認「扣除率分不出開口與中空」這個限制的實際嚴重程度。

2　規則涵蓋（優先）

8. 補上使用 m2 單位的 Type 目前字典用到的單位是 mm、cm、坪、才、組——沒有 m2。而舊 quantity.py 的 m2 換算有缺陷（少除 10000，錯一萬倍）。沒有 m2 樣本就測不到這個已知缺陷，修完也無從驗證。

這個 Type 只加在測試 Dictionary，不得為了測 QTY 修改現行 2.0 正式 Dictionary。

10. 補上 AREA_DH、LEN_D、LEN_H 的樣本 字典的規則詞彙有 8 個 token，但本模型只用到 4 個（COUNT、AREA_WD、AREA_WH、LEN_W）。另外 4 個從未執行過任何一次。即使實務上少用，也應各有一個樣本確認程式路徑會動。

只在結構測試副本補上，保留原模型「沒有真實 Brep」的基準事實。

19. 建立三層 fixture 集

不要把「不需 Rhino」與「能驗證 Rhino 幾何辨識」混為一談：

  • 純 Python domain fixtures：保存 adapter 已抽出的 typed records（面積、體積、候選端面／rail、身分、規則與來源 revision），驗證規則 join、狀態機、單位換算與報告；CI 可直接跑。
  • Rhino integration fixtures：小型 .3dm／.rws，驗證 RhinoCommon 的面、端面、block transform、reference 與 layer 正規化；需在 Rhino 內跑。
  • Golden outputs：兩層都對到同一份期望結果；若 integration 擷取結果改變但 domain 測試仍綠，差異必須可見，不能更新 golden 掩蓋。

合法／錯誤至少各一組，涵蓋直線、轉角、閉合環、包覆面、開口、Block、結構體與參照失效。

  • worksession 改變 attach 順序或多附加一個模型後，locator 仍指向原來源
  • 同一 3D 檔直接開啟與作為 reference 時，得到相同 canonical locator

1　執行規則

  • 一次只修改一個 repo；同一 repo 同一時間只由一台電腦／一個 AI 作業
  • P0 裁決完成、準備進入程式實作時，先由 main 建立長期整合分支 qty-development；每項任務再由該分支建立 codex/qty-<scope> 短期分支。日常批次回整合分支，達成發布關卡後才合回 main
  • 任務開始前確認 upstream、乾淨工作樹與 pull --ff-only；結束前完成檢查、commit、push 與交接
  • 任務須小到能在單一工作時段完成並留下可驗證的完整狀態。超過一個時段就先拆，不以未提交檔案換機
  • 程式一律放 qty/src/，不得寫進 v2/src/loopflow
  • 每個階段結束都是雙機安全停點：可換機、可中斷、下次接手不需要口頭補充
