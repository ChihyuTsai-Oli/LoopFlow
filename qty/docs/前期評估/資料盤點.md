### 2.2 `_07_UUID` 與 3D 物件是 1:1

| 每個 UUID 的組成 | UUID 數 |
|---|---|
| 1 個物件 | 13 |
| 2 個物件 | 11 |

組成模式：

```text
LCurve + RBrep                        x11
RInstanceReference                    x7      ← 無 2D
LCurve×3 + RBrep                      x6
RBrep                                 x6      ← 無 2D
LCurve×2 + RBrep                      x4
LCurve×14 + RBrep                     x1      ← 一項畫了 14 條線
```

**每個 UUID 恰好有一個 3D 代表**（30 Brep ＋ 7 Block ＝ 37），2D 則是一對多、最多 14 條。

**推論**：只算 3D 時，`_07_UUID` 與 3D 物件為 1:1，`object_id` 與 UUID 在 QTY 內可互換，「一個物件」的粒度問題不存在。

## 3　為什麼 2D 不採用

**計算標的一律是 3D 模型，所有 curve 直接略過。**

理由：2D 線稿是**出圖用**，而且是**從 3D 切出來的**，切出後還會做後續修改。因此 2D 與 3D 之間隨時可能不同步，不能作為計算依據。

實測也顯示 2D 覆蓋不完整——37 個項目裡只有 24 個有 2D 曲線，缺的 13 個包含全部 7 個 `COUNT` 類（電器、衛浴），那些本來就只要數不要量。

> 若開發過程中出現「一定得要有 curve 輔助計算」的情形，另議。

**2D 曲線的品質本身沒有問題**：實測 61/61 全部封閉且共平面，面積都算得出來。不採用是資料同步的考量，不是品質問題。

## 4　計算全集的定義

Coverage 檢核的「全部物件」**不是**文件中所有物件：

| 類別 | 數量 | 納入全集 |
|---|---|---|
| 帶 `type_id` 的 Brep／Block | 37 | ✅ |
| 結構體（`00_STR_*`）的 Brep | 16 | ✅ 但另計（§6） |
| **Point（放置點）** | 約 97 | ❌ **排除** |
| **Curve** | — | ❌ **排除** |

**若不排除 Point，那 97 個放置點會全部落入「未選取」，Coverage 一開跑就被雜訊淹沒。**

全集定義（2026-09-03 依 QD-26 改寫）：**作用中模型的本機 Brep 與 InstanceReference**（`IsReference == False`）。原文寫「3D 側」，那是舊配置下「3D 是被 attach 那一份」的描述；三家覆核都要求改掉這個綁 worksession 的措辭（QD-03），QD-26 給出了正式寫法。排除 Point 與 Curve 的結論不變。

## 6　結構體：查詢鍵不同，機制現成

結構體（`00_STR_*`）**完全沒有 `type_id`**——實測 16 個全部無標記。

但 [`qty/README.md`](../../README.md) 早已指出正確路徑：結構體改讀**圖層路徑**查字典。**實測全部命中**：

| 圖層 | type_id | 規則 | 單位 |
|---|---|---|---|
| `00_STR_結構::Beam.樑` | `EX-01` | `VOL_WDH` | m3 |
| `00_STR_結構::Column.柱` | `EX-02` | `VOL_WDH` | m3 |
| `00_STR_結構::Curb.墩座` | `EX-03` | `LEN_W` | cm |
| `00_STR_結構::Slab.樓板` | `EX-04` | `AREA_WD` | 坪 |
| `00_STR_結構::Stair.樓梯` | `EX-05` | `COUNT` | 座 |
| `00_STR_結構::Wall-Brick.牆-Brick` | `EX-06` | `LEN_W` | cm |
| `00_STR_結構::Wall-RC.牆-RC` | `EX-07` | `LEN_W` | cm |

**意義**：結構體不是「計算方式待議」，而是**查詢鍵是 `layer_path` 而非 `type_id`**。字典的 `EX` 類別（7 筆）就是為此準備的。

> **2026-09-03 補：查詢前必須先去掉專案 layer_prefix。** 上表列的是字典／Registry 側的值，不是模型裡的圖層全名。實測 `WIP_loopflow` 的 `Project_Registry.json`：`types[].layer_path` 為 `00_STR_結構::Beam.樑`，而模型的圖層全名是 `M3D::00_STR_結構::Beam.樑`。`M3D` 就是 `LoopFlow_Project.json` 的 `layer_prefix`（＝`project_id`）。
>
> 因此查詢鍵 ＝ **圖層全名去掉 `<layer_prefix>::`**。這一步原本沒寫進文件，實作若直接拿 `FullPath` 去比對會全部查不到。QD-26 之後只需要去掉這一層前綴；舊配置下還要多去掉一層檔名前綴（`<檔名> : `），現在不會再出現。

差異僅在：

- 查詢鍵：`layer_path`（不是 `type_id`）
- 不要求 UUID、空間、高程
- 出現 `VOL_WDH`（裝修材完全沒用到體積規則）
- 加總依 Type，不依房間

| 檢查 | 結果 |
|---|---|
| 3D Brep 是封閉實體 | **30 / 30** |
| 體積可計算 | **30 / 30**（103 ～ 324,900 cm³） |
| 2D 曲線封閉且共平面 | 61 / 61（雖不採用） |

`COUNT` 類的 7 個 Block：出口指示燈、開關面板、插座面板、瓦斯偵測器、冰箱、浴缸、馬桶——全部是**數量類**，與字典規則完全吻合。

### 7.1 開口

以「毛體積 ÷ 實體積」偵測：

| 物件 | 毛面積 | 淨面積 | 扣除 | 研判 |
|---|---|---|---|---|
| `WL-03` 藝術漆牆面 | 73,840 | 57,592 | **22.4%** | 缺 1.65 m²，尺寸符合一個門洞 |
| `WL-04` 裱布皮革 | 28,808 | 27,360 | 5.0% | 缺 0.14 m²，較像插座開孔 |
| 其餘 24 個 | — | — | **0.0%** | 完美方塊，無開口 |

**扣除率分不出「開口」與「形狀本來就不是方塊」**——`CB-04 鐵件框架` 扣除 95.6%、`CL-03 木作窗簾盒` 79.2%，那些是中空構件不是開口。只能標記後由人判斷。

### 7.2 方位

驗證模型整體繞 Z 軸旋轉 **30°**——這是**刻意的測試設計**，用來確保非 0/90 度的物件不會被算錯。

實測 30 個 Brep 的最佳貼合角度**全部落在 30°**，其中 24 個貼合度正好 1.00（完美方塊，只是轉了角度）。若用 World bbox 量，`WL-14` 會錯到 **127 倍**。

> **實務上牆的方位是各角度混和，而且同一道牆本身就可能有多個角度**（L 型、弧形、包覆）。因此不能靠「整體方位」或「每批一個平面」解決。方法見 [`量測方法.md`](./量測方法.md)。

## 8　MCP 讀取限制（影響實作方式）

> **2026-09-03 範圍限縮**：本節的結論成立於「要量的東西在參照側」，也就是舊配置。QD-26 之後計算對象一律是本機物件，MCP 原生工具**看得到**，本節描述的盲點不再擋住主路徑。仍保留的價值有二：一是 MCP 開發期若去讀配置 b 的 attach 2D 內容，盲點依然存在；二是最後一段的 adapter 寫法仍有效，但需補 `IsReference` 過濾（見 §11）。

worksession 下，MCP 原生工具**看不到 attach 進來的參照物件，且不報錯**：

| 工具 | 對參照物件 |
|---|---|
| `list_objects` | ❌ 看不到（回傳 2972 ＝ 本機數，`truncated: false`、`warning: null`） |
| `get_selection` | ❌ 看不到（即使物件確實選取中） |
| `set_selection` | ✅ 選得到 |
| `run_python` | ✅ 看得到（需正確設定列舉器） |

**「選得進去、讀不出來」的不對稱最危險。**

QTY 要量的 3D 實體全在參照側，因此**所有模型掃描一律走 `run_python`**：

```python
s = Rhino.DocObjects.ObjectEnumeratorSettings()
s.NormalObjects = True
s.LockedObjects = True
s.HiddenObjects = True
s.ReferenceObjects = True      # ← 少了這行就看不到 attach 的物件
s.DeletedObjects = False
objs = doc.Objects.GetObjectList(s)
```

讀取選取狀態要逐一檢查 `o.IsSelected(False) > 0`；`doc.Objects.GetSelectedObjects()` 同樣會漏。

**LoopFlow 2.0 本身沒有這個問題**——`v2/src/loopflow/platform/rhino/live.py:1032` 已明確設定 `ReferenceObjects`，需要排除時還會再檢查一次 `IsReference`。盲點只存在於 MCP 自己的原生工具。qty 應沿用 `live.py` 的既有寫法。

### 11.1 需要重做的事

1. **在合法配置下重跑一次盤點**，確認分側相關的數字（§1、§1.1、§2.2）。這不是懷疑舊數字，而是新配置下標籤相反，直接引用會誤導。
2. **adapter 列舉器補 `IsReference == False` 過濾**（QD-15 的連帶修正）。配置 b 若只靠 `ReferenceObjects = True` 而不過濾，會把 attach 的 2D 內容一起撈進來。
3. **`layer_path` 正規化寫進實作契約**：`FullPath` 去掉 `<layer_prefix>::` 才是查詢鍵。這是本輪掃描新發現的缺口，原文件從未寫出這一步。
4. **`LoopFlow_3D.3dm` 可作為配置 a 的現成樣本**：2026-09-03 實測 156 個全部是本機物件、0 個參照物件、worksession 模型數 1。
