# LoopFlow Loft — 全流程示範與 QTY 驗證模型需求書

版本：v1.0  
日期：2026-10-08  
模型名稱：Industrial Loft Demo Unit  
用途：LoopFlow、R2B、R2O、R2M、QTY 共用的示範模型；以 QTY 正確性驗證需求為建模依據。

> 本需求書整合使用者的 Loft 構想、前述空間規劃建議，以及《測試模型.md》（最後更新 2026-10-06）的 1～28 項補強需求。
>
> 本文件是待建模的設計與驗收規格，不表示模型、字典、Registry 或量測程式已完成。文中尺寸是本案建議值；未提供的正式 Dictionary、欄位契約與決策文件，須在建模時核對，不能將本文件的分類代號直接視為正式契約。

## 1. 模型目標與基本原則

建立一個由舊工業空間改造而成的 Loft apartment，具有矩形大平面、單側大窗、局部夾層、外露結構及工作生活混用的空間。模型應同時具備可拍攝的空間魅力，以及可核對的建築資料與數量。

五個流程各有明確示範任務：

| 流程 | 模型應支援的展示內容 | 建模重點 |
| --- | --- | --- |
| LoopFlow 主流程 | 分類、標記、空間／高程歸屬、既有／拆除／新建、圖說與模型資料對照 | 保留正式圖層與 Tag 契約；構件身分可追蹤 |
| R2B | Rhino 幾何與分類轉入 Blender，再進行指定構件修改與同步示範 | 一般 Brep、Block、重複構件與群組都有代表樣本 |
| R2O | 材質、Box Projection、玻璃與金屬、木地板與磚牆、日光與人工照明 | 材質區分清楚；材質紋理不靠增加計量幾何達成 |
| R2M | 建築殼體供 MEP 協作、IFC 類別對照及機電回參展示 | 可分離殼體、結構、天花與設備；機電路徑簡單易讀 |
| QTY | 幾何量測、八種 token、單位換算、群組、Coverage、身分與錯誤診斷 | 每個正式測試樣本都有尺寸、規則、期望結果與容差 |

建模原則：

1. 主體空間保持簡單，特殊幾何集中在可辨識的構件上。
2. 已知失效情境至少有三個彼此不同的樣本，不能只複製同一件改位置。
3. 正常幾何與正常資料可共存於母模型；故意製造的失效、碰撞、漂移與效能放大另存派生檔。
4. 展示畫面可使用圖層、狀態與視圖控制；不可因此改變 QTY 正確性基準。
5. 模型幾何、計量對象與輸出列不是一對一關係。例如櫃體由多件構成，一式成員則應退出逐物件計算。
6. 不為本案另造一套正式分類系統。下表的 category 只是需求對照用，須映射至現行圖層、Type 與規則。

## 2. 空間與尺寸設定

### 2.1 建議基準尺寸

| 項目 | 建議值 | 說明 |
| --- | --- | --- |
| 室內淨平面 | 14,000 × 8,000 mm | 基準面積 112 m²；外牆厚度向淨平面外側配置 |
| 座標 | X＝長向、Y＝深向、Z＝高向 | 主樓層完成面 Z＝0；大窗位於 Y＝0 長邊 |
| 室內樓板底高度 | Z＝5,600 mm | 外露樑另列樑底標高，不與樓板底混稱淨高 |
| 夾層完成面 | Z＝2,800 mm | 預留約 300 mm 的結構與地坪組合；夾層下概略淨高 2,500 mm |
| 夾層平面 | 後側 14,000 × 3,000 mm，扣一處 2,000 × 1,000 mm 缺角 | 投影面積 40 m²，約為主平面的 35.7% |
| 主要挑空區 | Y＝0～5,000 mm | 大窗前保留完整挑高，避免夾層遮住主視覺 |
| 大窗 | 6 組，各約 W1,800 × H4,200 mm | 窗台 Z＝450 mm；以壁柱與端部牆補足立面長度 |
| 外牆 | 建議 250～300 mm | 既有磚牆與 RC 牆分成不同實體與 Type |
| 新隔間 | 建議 100～150 mm | 面層、基材與結構厚度分別記錄 |

以上是示範模型的空間基準，不是結構設計或施工圖。夾層梁深、樓梯、欄杆與設備空間須先完成剖面檢查，再鎖定正式模型尺寸。

原建議中的「5 × 4 m 夾層」只有 20 m²，與 35%～45% 的面積目標不同。本案採約 40 m²；若後續縮小夾層，須同步修訂面積比例與 oracle。

### 2.2 使用配置

- **窗側主空間**：工作桌、畫架／模型工作台與開放客廳。家具自由分布，保留可穿越的空地。
- **後側夾層下**：廚房、衛浴、儲藏及設備區。以少量盒體收納需要隔間的機能。
- **入口端**：保留一段舊牆與圓角／弧形導引牆，形成新舊交接。
- **夾層**：睡眠與閱讀區，面向大窗及挑空；不另做完整封閉套房。
- **樓梯**：靠短邊配置鋼構單跑梯，接夾層缺角處；梯口、欄杆與主動線一併檢查。

樓梯起始配置可採 16 個踢面、每級高 175 mm、15 個踏面、每級深 280 mm，總升高 2,800 mm、水平行程 4,200 mm、淨寬約 1,000 mm。上層樓板作最後到達面；若加平台或改折返梯，踏步件數與行程須重新建立期望答案。

## 3. 新舊改造設定與顯示狀態

背景設定為舊工業單元改造成住家兼工作室：保留外殼與部分舊結構，移除舊隔間、局部設備平台與天花，新增鋼構夾層、樓梯、衛浴及廚房。

| 需求用 status | 中文 | 代表內容 |
| --- | --- | --- |
| EXISTING | 既有保留 | 外牆、舊樑柱、原樓板、保留窗、局部舊地坪 |
| DEMOLISH | 拆除 | 舊隔間、舊平台、舊門窗、局部天花及設備 |
| NEW | 新建 | 夾層、鋼梯、欄杆、衛浴、櫃體、飾面與新設備 |

status 必須映射到現行 `_02` 建構狀態契約；上述英文是閱讀用代號，不直接代替正式值。拆除與新建可以共用位置，但它們是不同身分的物件。

至少保存三組顯示預設：

- **改造前**：既有保留＋拆除。
- **改造後**：既有保留＋新建。
- **狀態對照**：三種狀態分色；拆除可用透明或線框呈現。

最終畫面隱藏拆除件，只是顯示選擇。QTY 的全集仍須能盤點 hidden／locked 物件；估價輸出是否篩選狀態，必須記錄在每次執行條件中。

### 4.4 樣本配置方式

弧牆、包覆面、轉角收邊與閉合環可自然融入入口、衛浴、書架、天花及燈具。若最低樣本數使主空間過度擁擠，保留最具代表性的可見構件，其餘放入明確隔離的 `_QTY_TEST` 測試分支或小型 integration fixture，並在總 manifest 指向來源檔。

不得為了完成清單，在同一片牆上疊放多個都被當作正式計量面的測試物件。測試件的存在、是否列入全集與展示時是否可見，都要分別記錄。

## 5. 八種 measurement token 與單位涵蓋

八種 token 皆須至少有一個可人工核對的正式樣本。構件能使用哪個 token，以測試 Dictionary 與正式契約為準；本表是預計安排，不是重新定義 W／D／H 或量測演算法。

| token | 建議樣本 | 核對重點 |
| --- | --- | --- |
| COUNT | 同型窗組／門／踏板 | 已選取且應計量的實例數；一式與群組重複排除 |
| AREA_WD | 矩形地坪、缺角板面 | 指定面積、孔洞與單位換算；與總表面積區分 |
| AREA_WH | 直牆指定面、包覆面對照 | 寬高方向、施工面、開口；不把其他面相加 |
| AREA_DH | 垂直側板／端牆指定面 | 正式 Type 的軸向定義；幾何轉向後不得誤用 World bbox |
| LEN_W | X 向直線飾條 | 基本長度與尺度；曲線 fallback 另以對應規則驗證 |
| LEN_D | Y 向直線收邊 | 未走過的規則分支與方向對照 |
| LEN_H | Z 向垂直收邊 | 高度方向分支；單位與幾何真長 |
| VOL_WDH | 矩形裝修填充塊 | 裝修材的體積路徑；不以結構特例代替 |

單位樣本至少涵蓋來源檔已有的 mm、cm、坪、才、組，以及測試專用 `m2`；若正式規則支援體積估價單位，再補對應單位。才、坪等換算常數須記錄其契約來源，不在模型內自行選另一種慣例。

為 `m2` 建立 2,000 × 1,000 mm 的指定施工面，人工答案為 2 m²；在 cm 檔為 200 × 100 cm、raw 面積 20,000 cm²。用此樣本驗證曾被指出的少除 10,000 缺陷。這個 Type 只進測試 Dictionary，不修改現行正式 Dictionary。

cm 與 mm 檔採相同物理尺寸、不同文件單位，各自保存；不可直接改原 baseline 的文件單位來測。若增加 m 檔，亦須另存並記錄。

## 6. Oracle：每個樣本的人工期望答案

### 6.1 必填欄位

每個計入 golden pass/fail 的樣本，至少具備下列紀錄：

| 欄位 | 內容 |
| --- | --- |
| specimen_id | 本需求書追蹤 ID＋樣本序號；非物件的正式身分 |
| source／version／hash | 來源檔、資產版本、內容雜湊 |
| identity | object_id，或 source_model_key＋Rhino GUID；必要時另記 `_07_UUID` |
| category／Type／status | 需求分類、正式 Type、正式建構狀態 |

| rule | measurement token、估價單位、規則來源及 revision |

## 7. 必備群組與 Block 測試

### 7.1 櫃體群組

使用真正 Group Name 作為群組載體，不以成員 Object Name 冒充。櫃體正式命名前綴依 QTY 現行契約核對；本文件不臆造前綴。

| 測試組 | 最低案例 | 預期檢查 |
| --- | --- | --- |
| 方向與尺度 | 0°／30°／45°／90°、任意角、鏡射、cm／mm | 相同櫃體物理外包尺寸一致；鏡射與 transform 正確 |
| 突出與異形 | 把手突出、檯面突出、弧櫃、不規則櫃 | OBB 如實變化；方向診斷不能靜默宣稱高信心 |
| 群組拓樸 | 巢狀、部分重疊、交叉群組；混入非櫃體群組 | 不重複計同一零件；不將任意 Group 當櫃體 |
| 命名與變更 | 真名與成員名不同、改名、解散、重組、成員增減 | lost／changed 可辨識；重組後新 group index 不猜配 |
| 複製與缺件 | Copy 後無名群組；重組漏選一件；櫃體圖層未成群零件 | 待命名／未成群不得消失；缺件導致尺寸縮小可被檢查 |
| 成員型別 | 超出櫃體範圍的 curve＋point；只有線的群組 | 輔助線點不改 OBB；只有線回報無可量測成員，非零尺寸 |
| Block 成員 | 旋轉把手、鏡射把手 | 使用實例 transform，不以 definition 原位尺寸取代 |
| 空間歸屬 | 同空間、跨空間、EXT 各一組 | 讀成員空間；跨空間診斷並輸出多值，不取多數決 |

### 7.2 一式燈箱

正常樣本使用 `QTY_LS_001_燈箱`，由鋼板骨架、烤漆、沖孔板與燈條組成；每類至少一件，實際成員數須盤點。成員仍保留各自 Tag 與 `_01`～`_14` 資料。

- 估價單只有「燈箱 一式 1」，所有成員退出逐物件計算，尤其不能另算燈條長度。
- 成員 Coverage 為「一式」，不得以「未選取」掩蓋。
- Z-up OBB 長寬高只作尺寸附註。
- 派生案例包含跨空間、與櫃體群組重疊、未命名一式候選；前兩者依契約診斷多值或衝突。
- 清運、管理費等無實體一式維持手動填寫，不虛構模型構件。

### 7.3 一般 Block

至少包含共用 definition 的多實例、旋轉、鏡射、非等比縮放、巢狀與 linked block。正常支援者核對實例幾何與件數；尚未支援者必須有明確原因，不能無聲略過。未標記門窗 Block 另建派生案例，待決策確認後固定計算與 Coverage 行為。

## 8. 檔案、資料與派生測試資產

### 8.1 正確性母模型與展示設定

QTY 專用母模型以《測試模型.md》指定的 `loopflow_qty_3D.3dm` 為基準，內容為本案 Loft。配套 2D 與 rws 的實際檔名，以工作檔區現行命名核對。展示可使用同一母模型的保存視圖，或建立明列來源版本的展示副本。

不得改寫原 MCP baseline、使用者正式專案、正式 Dictionary 或 Registry。來源檔中的48件候選是舊 baseline 的盤點，本案另有自己的物件數與版本，不沿用48作為本案答案。

工作檔存於 `<LOOPFLOW_QTY_WORKFILES_ROOT>`，由現行工作檔路徑文件解析。repo 留可提交的小型 fixtures、建立說明、manifest 與期望輸出；大型 3dm 留工作檔區，不記某台電腦的絕對路徑。

### 8.2 合法與錯誤開檔配置

| 配置 | 檔案角色 | 驗收要求 |
| --- | --- | --- |
| 直接開3D | 3D 為本機可編輯物件 | 正常量測與群組名稱；無來源檔名前綴 |
| 2D attach 進3D | 同一3D為主檔，2D為參照 | 與直接開3D的數量與Coverage完全相同；附加2D參照與Curve不進全集 |
| 3D attach 進2D | 派生反例 | 辨識來源前綴如 `<檔名> : QTY_...`，報設定錯誤並停止；不得輸出數量或OBB |

錯誤訊息應清楚指出：「請直接開啟3D檔，或改成2D attach進3D。」來源身分作為 reference 時仍可另測 canonical locator；這不表示該 reference 配置可以執行產品 QTY。

### 8.3 派生測試矩陣

| 派生組 | 最低案例 | 預期行為／紀錄 |
| --- | --- | --- |
| Registry漂移 | live有／Registry無；Registry有／live無；revision或hash不同；未知schema_id | 各案有明確狀態；不得只改數字而無可核對差異 |
| 參照失效 | 保存選取後來源物件缺失或參照失效 | Coverage失效態與原因可重現；不靜默變為未選取 |
| 身分生命週期 | 存檔重開、attach順序改變、增加來源、搬移專案、來源改名、刪除重畫 | 可解析者維持身分；應lost者不自動猜配 |
| 身分碰撞 | 來源副本含相同Rhino GUID；重複 `_07_UUID` | source_model_key可區分來源；無法唯一辨識時conflict |
| 單位對照 | cm／mm，同一物理尺寸；m視需要補 | raw、exact、display分別核對；不出現10／100倍尺度錯誤 |
| 幾何排除 | open Brep、invalid Brep、Mesh、SubD | 依支援範圍排除或拒絕；有明確原因；不讓無效幾何污染正常母模型 |
| 群組變更 | 第7節的無名、解散、重組、缺件、重疊及跨空間 | 各案有獨立oracle與盤點，不改正常基準 |
| 資料缺漏 | 未標記門窗Block、漏畫boundary造成EXT | 按決策記錄固定行為；未知處置先標探索 |
| 效能放大 | 100／1,000／5,000候選 | 獨立檔；複製產生新GUID；記錄候選數、列舉總量、耗時與執行環境 |

每次執行都保存資產版本、Dictionary／Registry revision、單位、選取集合、狀態篩選、量測列、Coverage與診斷。效能目標時間須依實作與硬體另定，本需求書不虛填秒數。

### 8.4 三層 fixture

1. **Rhino integration fixtures**：小型3dm／rws，檢查面、端面、rail、Block transform、群組、reference與layer正規化，須在Rhino內驗證。
2. **純Python domain fixtures**：保存adapter抽出的typed records，包括幾何量、候選端面／rail、身分、規則與來源revision；用於join、狀態機、換算與報告，可由CI執行。
3. **Golden outputs**：兩層對同一期望答案。integration改變但domain仍通過時，差異必須可見；不得直接更新golden掩蓋回歸。

manifest至少包括檔名、版本、hash、文件單位、建構方式、物件盤點、specimen與身分對照、規則來源、oracle位置以及所覆蓋的需求編號。
