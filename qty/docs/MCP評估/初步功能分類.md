## 1. 目前預計工作流程

QTY 的核心流程預計為：

```text
Rhino 場景物件
    ↓
Grasshopper 手動選取、分類
    ↓
Grasshopper 逐物件計算數量
    ↓
Grasshopper 視覺化檢查
    ├─ 不同分類顯示不同顏色
    └─ 在物件旁／空間中顯示數量文字
       例如：26 坪、35 m、12 pcs
    ↓
使用者直接在模型中檢視、確認
    ↓
Grasshopper 分組／排序
    ↓
輸出 Excel
    ├─ 估價單
    └─ 明細
```

QTY 的核心不是「模型直接自動產生 Excel」，而是：

> **選取 → 計算 → 空間視覺化 → 人工確認 → 輸出**

Excel 是最後的結果輸出，不是整套系統的中心。

## 2. 產品基本原則

### 2.1 人工分類，系統計算

QTY 不嘗試自動判斷所有估價分類。

使用者仍需在 Grasshopper 中依實際估價需求手動選取、分類 Rhino 場景物件；系統負責：

- 計算
- 加總
- 顯示
- 檢核
- 整理
- 輸出

這與 LoopFlow 2.0 保留人為判斷、系統負責檢查的方向一致。

### 2.2 計算以逐物件為基礎

即使最後 Excel 以「空間 × 工種／部件」群組加總，底層仍維持逐物件計算。

每個物件都應保留可追溯結果，例如：

- `object_id`
- `type_id`
- 空間
- 計算規則
- 單位
- 數量
- 所屬批次／分類

### 2.3 視覺檢查是正式流程，不是裝飾

QTY 應讓使用者在 Rhino / GH viewport 中直接看到：

- 哪些物件屬於哪一批
- 哪些物件已計算
- 哪些物件為一式
- 哪些物件漏選
- 哪些物件重複選取或衝突
- 每批或每個物件的數量結果

例如：

```text
[牆面以某顏色 Preview]

26.38 坪
```

空間中的數字與著色能提供 Excel 無法提供的直覺檢查能力。

---

### 2.4 計算標的：只算 3D，不算 2D

> 2026-09-01 定案。以下依實際 worksession 模型（`LoopFlow_R_MCP.rws`）實測確認。

**計算標的一律是 3D 模型。所有 curve 直接略過。**

理由：2D 線稿是**出圖用**，而且是**從 3D 切出來的**，切出後還會做後續修改。因此 2D 與 3D 之間隨時可能不同步，不能作為計算依據。

> 若開發過程中出現「一定得要有 curve 輔助計算」的情形，另議。

**連帶結果（皆經實測確認）**：

| 項目 | 結論 |
|---|---|
| 「一個物件」的粒度 | **`_07_UUID` 與 3D 物件為 1:1**。粒度問題消失，`object_id` 與 UUID 在 QTY 內可互換 |
| 2D 的一對多 | 不再有影響。實測一個項目最多由 14 條 2D 線構成，全部略過 |
| 帶 `_03_ID編號` 的 3D 物件 | 37 個（Brep 30 ＋ Block 7） |

### 2.5 計算全集的定義

Coverage 檢核的「全部物件」**不是**文件中所有物件。實測該模型的 3D 參照側共 144 個物件，其中：

| 類別 | 數量 | 是否納入全集 |
|---|---|---|
| 帶 `type_id` 的 Brep／Block | 37 | ✅ 納入 |
| 結構體（`00_STR_*`）的 Brep | 16 | ✅ 納入，但另計（見 §2.6） |
| **Point（放置點）** | 約 97 | ❌ **排除** |
| **Curve（空間框等）** | 2 | ❌ **排除** |

**若不排除 Point 與 Curve，那 97 個放置點會全部落入「未選取」，Coverage 立刻被雜訊淹沒。**

全集定義：**3D 側的 Brep 與 InstanceReference**。

### 2.6 結構體（`00_STR_*`）另列計算方式

`00_STR_*` 為結構體圖層（柱、樑、牆、板），其計算方式與裝修材不同，**另列計算方式，方法待議**。

實測該模型的結構分層：

```text
M3D::00_STR_結構
  ├ Beam.樑
  ├ Column.柱
  ├ Curb.墩座
  ├ Slab.樓板
  ├ Stair.樓梯
  ├ Wall-Brick.磚牆
  └ Wall-RC.牆-RC
```

**重要**：實測結構體物件**完全沒有 `type_id`**（16 個全部無標記），因此無法透過字典取得計量規則。這是結構體必須另列計算方式的具體原因，不只是慣例差異。

實務上這在**選取階段就由使用者手動分類處理**——結構與裝修本來就分在不同圖層，選取時自然分開。因此第一版不需要為此建立自動判別機制，只需在文件中確立此規範。

# 3. Grasshopper 功能分類

建議 QTY 的核心功能依照使用者工作節奏分類，而不是依照程式技術類型分類。

初步分為五大類：

| 類別 | 核心問題 | 主要工作 |
|---|---|---|
| 01 Selection | 我要算哪些東西？ | 選取、分類、一式排除、集合管理 |
| 02 Measurement | 這些東西是多少？ | COUNT / AREA / LEN / VOL |
| 03 Inspection | 算出來的東西看起來對不對？ | 顏色、文字、空間顯示 |
| 04 Validation | 有沒有漏算、重複、失效或規則異常？ | 涵蓋率、衝突、Reference、規則檢查 |
| 05 Output | 怎麼整理成可交付資料？ | 分組、排序、Excel、明細 |

## 3.1 Selection

### 目的

由使用者決定：

> 「這次要算哪些物件，以及這些物件屬於哪一種估價分類。」

### 可能元件

#### `QTY_Set`

將一組 Rhino objects 包成 QTY 的基本集合。

概念：

```text
Name: 牆面磁磚
Objects: 126
```

> **2026-09-01 決定：`QTY_Set` 不帶 Rule 輸入。**
>
> 計量規則與單位**一律由 `type_id` 查字典取得**，使用者只決定「算哪些物件」，不決定「怎麼算」。
>
> 依據：實測該模型 98 個帶標記物件的 26 個相異 `type_id`，**全部 26 個都在字典查得到 `measurement_rule` 與 `estimation_unit`**，量綱一致性檢查亦 26/26 通過。規則資料已經完整存在，在 GH 重新輸入一次只會製造靜默出錯的機會。
>
> **連帶影響**：
>
> - `QTY_RuleCheck` 的意義改變（見 §3.4）
> - **同一 Type 依情境使用不同規則，第一版明確不支援**（`數量計算需求筆記.md` §8 第 2 項）

後續 Measurement、Inspection、Validation、Output 都以相同的 QtySet 為輸入，而不是每個元件重新處理裸 Rhino objects。

概念資料流：

```text
Rhino Objects
      ↓
   QTY_Set
      ↓
 ┌────┼────────┐
 ↓    ↓        ↓
Measure View  Check
```

#### `QTY_LumpSum`

標記「一式」物件。

原則：

- 一式不加入 LoopFlow Dictionary 的 measurement rule / unit 詞彙表
- 一式物件仍是正常 LoopFlow 物件
- 排除必須以 `object_id` 為準
- 不能僅依賴「沒有接進計算電池」來避免計算

一式集合應視為全域排除集合。

#### `QTY_Save` — 選取狀態持久化

> **2026-09-01 決定：選取與分類狀態存成外部 JSON，不倚賴 `.gh` 內建的 referenced param。**

存放位置：`_LoopFlow_Config/loopflow_QTY/`（`工作檔路徑.md` 已預留此資料夾）。

| | 存 `.gh` | **存外部 JSON（採用）** |
|---|---|---|
| 使用者動作 | 點選即記住，零額外動作 | 需一個明確的「確認並儲存」 |
| GUID 解析 | GH 自己做 | 需自行實作 |
| AI 可讀 | ❌ 二進位，git 看不到 diff | ✅ 可讀、可 diff、可比對版本 |
| `.gh` 的定位 | 變成專案資料，一專案一檔 | 保持純工具，可跨專案重用 |

採用 JSON 的兩個附帶好處：

1. 「多一個確認動作」**與產品哲學一致**——人工確認本來就是正式流程的一環，不是負擔
2. 自行實作 GUID 查找時，**物件找不到的那一刻正好就是 Broken Reference 的攔截點**，恰好是 §3.4 需要的第五態

**實作注意：不要用 Panel 的 Stream Contents 寫檔。**

GH 元件每次 re-solve 都會執行，動任何上游輸入就會重寫檔案，且目標檔開啟中時會撞檔案佔用（`初步評估報告.md` §5.6）。正確做法是專用的 Python 元件配明確觸發：

```text
QTY_Set ──┐
          ├──> QTY_Save ──> selection.json
Button ───┘   （只有按下去才寫）
```

**待決**：寫入時機是「每次變更即寫」還是「按確認才寫」（見 §11）。

## 3.2 Measurement

### 目的

回答：

> 「這批物件實際是多少？」

### 初步規則

主要計算類型：

```text
COUNT
AREA
LENGTH
VOLUME
```

### 可能元件

可以先分開：

```text
QTY_Count
QTY_Area
QTY_Length
QTY_Volume
```

也可以後續收斂成：

```text
QTY_Measure
```

輸入：

```text
Objects
```

> **2026-09-01 修正**：原本列的 `Rule`、`Unit` 改由字典查得（§3.1）；`Plane / Direction` **不需要**（見下方「量測方法」）。

輸出：

```text
Object Qty
Total Qty
Unit
Details
```

例如：

```text
AREA
 ↓
42 objects
 ↓
86.37 坪
```

### 架構方向

真正的計算邏輯應住在外部 `.py`，GH Python 元件只保留薄殼。

開發期外部 module 必須處理 Python module cache，例如使用 `importlib.reload()`，避免修改 `.py` 後 GH 重新求解仍吃到舊程式碼。

### 量測方法（2026-09-01 實測定案）

**核心原則：不拆解 W／D／H，不需要平面輸入，不需要方位判斷。**

早期構想沿用 LoopFlow 1.x 的 W/D/H 模型，需要使用者指定平面。實測證明這條路走不通：

- 該模型物件整體旋轉 30°（測試用的刻意設計），用 World bbox 量會錯到 **127 倍**
- 更關鍵的是，**同一道牆本身就可能有多個角度**（L 型牆、弧牆、包覆面）。這種物件根本不存在「一個平面」可套，W/D/H 模型直接失效
- 實務上牆的方位是各角度混和，要求使用者依角度分類並不合理

改為**直接從幾何取值**後，上述問題全部消失——面的法向量與面積是每個面自帶的，轉幾度、彎幾次都一樣處理。

#### 面積

```text
主要值：最大單一面面積
對照值：體積 ÷ 厚度   （厚度 = 2 × 體積 ÷ 總表面積）
兩者差 > 10% → 標記「可能是多段包覆面，最大面會少算」
```

實測結果（15 個面積類物件）：

| 物件 | 面數 | 最大面 | 體積÷厚 | 判定 |
|---|---|---|---|---|
| `WL-13` 石材牆面 | 6 | 73,800 | 74,892 | 一致（73,800 ＝ 300×246，精確） |
| `WL-11` 裝飾壁板 | 6 | 6,270 | 6,604 | 一致（6,270 ＝ 57×110，精確） |
| `CB-06` 櫃體石材面 | 6 | **3,675** | 4,016 | 一致 |
| `FL-02` 地毯 | 6 | **27,300** | 29,490 | 一致 |
| **`WL-14` 磁磚牆面** | **22** | 57,871 | 110,054 | **差 47%，標記** |

「最大單一面」有三個好處：

1. **自動排除邊帶**。薄板側邊那一圈不會被算進去，比「垂直面總和 ÷ 2」準 1～4%
2. **自動處理立面／平面**。它不管面朝哪裡，所以 `CB-06`（水平檯面卻掛 `AREA_WH` 規則）直接得到正確的 3,675 cm²，不需要任何方位邏輯
3. **自動扣除開口**。實際存在的面才會被算到

唯一失效情境是**多段包覆面**（`WL-14`，22 個面），最大面只抓到其中一段。這正是對照值要抓的。

#### 長度

```text
主要值：體積 ÷ 端面截面積      （得到中心線長度，對折線與曲線自動成立）
對照值：最長邊
兩者差 > 2% → 標記
```

實測結果（15 個長度類物件）：**13 個一致**，2 個被正確標記——

- `CL-03 木作窗簾盒`：有轉角，內側 180.0／外側 183.8，最長邊只會給外側
- `CB-04 鐵件框架`：閉合環，**根本沒有端面**，端面辨識必然失敗

「體積 ÷ 截面積」的優點是**對彎折路徑自動正確**——得到的是中心線長度，不管路徑怎麼繞。缺點是端面辨識可能挑錯面，以及閉合環無端面。因此必須配對照值。

#### 共通設計原則

面積與長度都採用**「一個主要算法 ＋ 一個能抓出它失效情境的對照」**，而不是追求單一萬用演算法。實測顯示這個組合在 30 個物件上只對 3 個發出標記，其餘完全不吵。

這符合 LoopFlow 一貫的「標記，不自動修」。

## 3.3 Inspection

### 目的

將抽象數字重新放回模型空間，讓使用者可以直接目視判斷。

這可能是 QTY 最重要的使用者介面之一。

### `QTY_Color`

依 QtySet／分類設定 GH Preview Color。

原則：

- 優先採 GH Preview
- 不應為了顯示而永久修改 Rhino Object Color
- QTY 是分析層，避免污染原始模型

可能用途：

- 不同估價分類不同顏色
- 已計算
- 一式
- 漏選
- 衝突
- Broken Reference

### `QTY_Label`

顯示數量文字，例如：

```text
26.38 坪
35.2 m
12 pcs
```

Label 可以顯示：

- 單一物件結果
- 一批物件加總
- 空間／分類加總

### `QTY_Anchor`

負責決定 Label 放置位置。

真正困難的可能不是文字本身，而是：

> 「文字應該出現在哪裡才容易閱讀？」

候選策略：

#### AREA

```text
BoundingBox center
↓
可視表面附近
↓
26.38 坪
```

#### LENGTH

```text
Curve midpoint
↓
35.2 m
```

#### VOLUME

```text
Volume centroid
↓
12.6 m³
```

#### Group

```text
Group BoundingBox / centroid
↓
26 坪
```

`QTY_Anchor` 後續可能會成為獨立且較複雜的元件。

## 3.4 Validation

### 目的

QTY 最危險的狀況不是程式報錯，而是：

> **數字算錯，但整條流程看起來正常。**

因此 Validation 應為正式的一級功能，而不是附屬功能。

### `QTY_Coverage`

基本集合關係：

```text
全部物件
 ├─ 已計算
 ├─ 一式
 ├─ 未選取
 ├─ 衝突
 └─ 已選取但 Reference 失效
```

> 「全部物件」的精確定義見 **§2.5**——是 3D 側的 Brep 與 InstanceReference，**排除 Point 與 Curve**。實測該模型 3D 側 144 個物件中約 97 個是放置點，若不排除會全部落入「未選取」，Coverage 立刻失去意義。
>
> 結構體（`00_STR_*`）雖納入全集，但因無 `type_id` 且計算方式另立，應在報告中與裝修材**分開呈現**（§2.6）。

核心檢查：

```text
1. 已計算 ∩ 一式
   → 非空即衝突

2. 全部物件 − 已計算 − 一式
   → 漏選

3. 各計算批次彼此交集
   → 重複選取

4. GH Reference 失效
   → Broken / None
```

原則：

- 只標記，不自動修復
- 衝突優先顯示
- 使用者決定正確去向

### `QTY_Duplicate`

專門找出：

```text
Batch A ∩ Batch B
```

例如同一物件同時出現在兩種估價項目。

不一定代表模型錯誤，因此：

- Highlight
- Warning
- 不自動決定刪除哪一邊

### `QTY_RuleCheck`

> **2026-09-01 意義改變。** 規則既然一律由字典取得（§3.1），就不存在「GH 的規則」與「字典的規則」不一致的情況。RuleCheck 改為檢查下列四項：

**① 規則配不上幾何（實測發現，原文件沒有這項）**

`CB-06 櫃體石材面` 字典規則是 `AREA_WH`（立面），但它的幾何是 **100 × 36.7 × 2.5** 的**水平**檯面石材。規則與幾何不匹配。

判準：`AREA_WH` 應有明顯厚度方向且高度為垂直向；`AREA_WD` 應為水平延展。不符即標記。

**② 字典查不到規則**

實測目前 26/26 都查得到，但模型新增未登錄的 Type 時會發生。

**③ 同一批次混入不同規則的 Type**

通常代表選取範圍框錯了。

**④ 量測對照值不一致**

面積的「最大面 vs 體積÷厚」差 > 10%、長度的「體積÷截面 vs 最長邊」差 > 2%（見 §3.2）。

---

**開口扣除**

實測發現兩個物件有明顯扣除：

| 物件 | 毛面積 | 淨面積 | 扣除 | 研判 |
|---|---|---|---|---|
| `WL-03` 藝術漆牆面 | 73,840 | 57,592 | **22.4%** | 缺 1.65 m²，尺寸符合一個門洞 |
| `WL-04` 裱布皮革 | 28,808 | 27,360 | 5.0% | 缺 0.14 m²，較像插座開孔 |
| 其餘 24 個 | — | — | **0.0%** | 完美方塊，無開口 |

原則上**不扣除門窗開口**。但若出現很大的非門窗開口，需要判定。

**扣除率偵測得到**（毛體積 ÷ 實體積），但它**分不出「開口」與「形狀本來就不是方塊」**——`CB-04 鐵件框架` 扣除 95.6%、`CL-03 木作窗簾盒` 79.2%，那些是中空構件不是開口。

因此只能**標記後由人判斷**。**閾值待定**（見 §11）。

模型物件本身可取得：

- `type_id`
- `type_category`
- `space_id`
- UUID 等身分資料

但以下資料仍需向 Dictionary / Registry `types[]` 查詢：

- `measurement_rule`
- `estimation_unit`

因此 RuleCheck 應為模型現況與 Dictionary 的 join。

# 4. Rhino 工具列應負責什麼？

初步判斷：

> **QTY 的核心操作都應留在 Grasshopper。**

Rhino 工具列只處理：

- 啟動
- 工作環境
- 專案狀態
- 必要的跨文件／顯示模式操作

判斷原則：

> **需要持續看著資料流調整的 → Grasshopper**  
> **屬於啟動、專案狀態、跨文件操作的 → Rhino 工具列**

因此 Rhino 工具列應刻意保持非常薄。

---

## 4.1 建議第一版：只有兩個按鈕

```text
┌──────────── QTY ────────────┐

       [ QTY ]   [ Status ]

└─────────────────────────────┘
```

---

## 4.2 `QTY` / `QTY_Open`

### 用途

進入 QTY 工作環境。

這顆不是「開始計算」，而是環境入口。

可能工作：

```text
確認目前 Rhino 文件 / Worksession
↓
確認 LoopFlow 專案資料
↓
找到這個專案對應的 Qty .gh
↓
開啟 Grasshopper
↓
載入正確 Qty definition
↓
完成必要初始化
```

使用者心理模型：

> 我要算數量 → 按 QTY

而不是手動管理：

- 開 GH
- 找 `.gh`
- 確認專案
- 確認 Registry
- 確認是不是載錯檔

### MCP / GH 注意事項

Rhino MCP 的 `g1_start`：

- 只會開啟 Grasshopper 視窗
- 不會建立 Definition
- `Grasshopper - No document` 狀態下，其他 `g1_*` 工具無法工作

因此「開啟正確的 QTY GH Definition」本身就是合理的產品功能。

---

## 4.3 `QTY_Status`

### 用途

檢查目前的「工作環境狀態」，不是檢查估價涵蓋率。

可能顯示：

```text
QTY Project Status

Project       LoopFlow_R
3D Model      ✓ Attached
Dictionary    ✓ Found
Registry      ✓ Revision 18
Qty File      ✓ LoopFlow_R_QTY.gh
Grasshopper   ✓ Open

98 tagged objects
26 Types
```

可能警告：

```text
⚠ Registry revision 與模型現況可能不同
⚠ Worksession 缺少 3D reference
⚠ Dictionary 找不到
⚠ Qty definition 與目前專案不一致
```

Status 負責回答：

> 「我現在到底正在算哪一份模型，而且資料環境是否完整？」

# 5. 可能後續增加，但第一版不急著做

## 5.1 `QTY_View`

若日後 QTY 有大量 Preview：

- 分類顏色
- 數量 Label
- 漏選
- 一式
- Conflict
- Broken Reference

可能需要快速切換：

```text
正常 Rhino 工作狀態
↕
QTY 檢查狀態
```

`QTY_View` 可以：

- 開啟／關閉 Qty Preview
- 切換適合檢查的 Display Mode
- 控制必要顯示項目
- 必要時 Zoom / Restore View

是否需要，應待實際工作一段時間後再決定。

## 5.2 `QTY_Close` / `QTY_ResetView`

只有在 QTY 會改動：

- Rhino selection
- Display mode
- Temporary conduit
- Preview 狀態

而且無法自然恢復時才需要。

如果全部視覺效果都只存在 GH Preview，關閉 Preview 即可乾淨離場，則不必建立獨立按鈕。

# 6. 不建議放進 Rhino 工具列的功能

以下全部應優先留在 Grasshopper：


理由：

```text

    ↓

    ↓

    ↓

    ↓

    ↓
```

Grasshopper 的價值就是讓整條資料鏈可見。

> 「剛才按那顆按鈕到底改了什麼？」

不符合 QTY 希望保留透明操作與人工確認的方向。

# 7. 不建議建立 `QTY_Scan` 操作按鈕

「掃描全部可計算物件」乍看很適合放 Rhino 工具列，但目前不建議。

原因：

QTY 的工作入口仍然是：

> **使用者手動分類選取**

全模型掃描的主要角色不是自動分類，而是建立 Validation 的「全集」。

例如：

```text
全部物件
− 已計算
− 一式
= 未決定去向
```

因此全模型掃描應：

- 藏在 GH Definition / Python 底層
- 自動取得
- 作為 Coverage 檢核來源

使用者不需要特別按 Scan。

# 8. Rhino MCP / Worksession 對 QTY 的重要限制

## 8.1 Worksession Reference Objects

實際 LoopFlow 作業配置：

```text
2D .3dm
└─ Worksession attach
   └─ 3D .3dm
```

MCP 原生 Rhino 工具對 attach reference objects 有不對稱問題：

```text
list_objects     → 看不到
get_selection    → 看不到
set_selection    → 選得到
run_python       → 看得到
```

而且 `list_objects` / `get_selection` 看不到時不一定會報錯。

因此 QTY 所有模型現況掃描一律應走 `run_python`，並使用：

```python
s = Rhino.DocObjects.ObjectEnumeratorSettings()
s.NormalObjects = True
s.LockedObjects = True
s.HiddenObjects = True
s.ReferenceObjects = True
s.DeletedObjects = False

objs = doc.Objects.GetObjectList(s)
```

少掉：

```python
ReferenceObjects = True
```

會直接漏掉 attach 進來的 3D 實體，而且可能沒有任何警告。

---

## 8.2 MCP 不應直接操作 LoopFlow 產品指令

LoopFlow 指令包含大量：

- Eto modal UI
- ListBox
- GetPoint
- GetObject
- 人工確認

MCP 遇到未完成的 Rhino / LoopFlow command 時可能出現：

```text
腳本實際有執行
error = null
stdout = 空白
```

這種「靜默失效」比單純 crash 更危險。

QTY 對 MCP 的主要用途應為：

- 讀取
- 建立／修改 GH canvas
- 執行計算
- 驗證結果
- 執行無互動的 Python 邏輯

不應用 MCP 代替使用者操作 LoopFlow 指令。

---

## 8.3 不要用 MCP headless 載入 `.gh`（QTY 直接相關）

> 2026-09-01 公司電腦實測事故。完整記錄見 [`MCP設定交接.md`](./MCP設定交接.md) §7.8 與 [`實測報告.md`](./實測報告.md) §4.5。

在已開啟 worksession、已連 MCP 的 Rhino 中，透過 `run_python` 建立 `Grasshopper.Kernel.GH_DocumentIO` 並 headless 開啟 `.gh`：工具呼叫逾時，取消後 MCP 一度仍能回應，但**使用者稍後手動執行 `gh` 時 Rhino 凍結並退出**。

**這對 QTY 特別重要**，因為 QTY 的核心就是操作 `.gh` definition：

- `QTY_Open`（§4.2）要「載入正確的 Qty definition」——**必須由 Rhino／GH 正常開啟，不可由 MCP headless 載入**
- AI 要檢查 definition 時，正確做法是請使用者正常執行 `gh`、在 GH UI 開啟 `.gh`，AI 再用 `g1_get_canvas_graph` 等正式工具讀取
- 工具逾時後 MCP ping 成功**不代表** runtime 已恢復乾淨；應立即請使用者重開 Rhino

另外兩項同源限制：

- **`.rws` 由使用者手動開啟**，不要用 `run_python`／`run_command`／`open_doc` 代開
- **`MCPStart` 打完不會立刻結束**，畫面會停在 `MCPStart Port <10500>`，要按 Enter 才真正啟動
