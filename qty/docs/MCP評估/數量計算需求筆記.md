## 1　背景與動機

需要數量計算，源頭是**估價需求**。實務上常見的估價單或空白標單並不複雜，複雜的是項目數量多：

- 多數項目：某空間的某部件，列出面積或長度數量
- 難以拆分的項目：整包列為「一式」，直接給價格，不拆數量

工具要解決的是「項目多、重複整理耗時」，不是「估價本身複雜」。

---

## 2　計算原則（已確認）

### 2.1 逐物件計算

計算按**逐物件**進行，不是先分類再抓群體平均或抓層級預設值。Excel 上的一列是「群組」（空間 × 部件的加總），但底層算的時候永遠是一個個物件累加起來的。

### 2.2 輸出建議兩張表

| 工作表 | 內容 | 用途 |
|---|---|---|
| 估價單 | 依空間／工種群組加總後的一列一項 | 對外、給廠商 |
| 明細 | 逐物件：`object_id`、所屬群組、規則、單位、數量 | 自己查核，數字有疑問時往下追 |

明細表反正是計算過程中已經有的資料，多輸出一張表成本很低，但少了它，數字對不上時只能重跑猜測。

### 2.3 工具只產出「模型量得到的部分」

假設工程、清運、保護工程、管理費、利潤、稅等**不對應任何 Rhino 物件**的項目，一律**另外手動填寫**，不進工具範圍。標單的最終組裝在 Excel 完成，工具不試圖擁有整份標單。

## 3　一式（Lump Sum）

### 3.1 不進字典，靠 GH 選取排除

「一式」**不列入 LoopFlow 字典**（不新增 `measurement_rule` 或 `estimation_unit` 的「式」token），避免動到 LoopFlow 2.0 已發布的 schema、也避免舊版讀到新字典會 `block` 的問題。

實際操作：在 GH 選取物件進行計算時，**一式物件不選入計算批次**，改成人工在 GH 裡標記為「一式」類別（獨立的選取集合，不是文件或清單）。

### 3.2 一式物件仍帶標準 UserText——排除必須以 object_id 為準，不能只靠「沒被接進電池」

一式物件仍是正常的 LoopFlow 物件，身上照樣有 `type_id`、`type_category` 等標準身分 UserText（2.0 只拿掉尺寸／數量欄，身分欄沒動）。這代表只要有 `type_id`，理論上就能透過 Registry 的 `types[]` join 到一個 `measurement_rule`。

**風險**：如果未來有任何元件是「依 `type_id` 自動抓取物件」而不是純粹讀 GH 手動選取集合，一式物件會因為有 `type_id` 而被撈進去算，且不會報錯，只是安靜地多算一筆。

**原則**：一式排除必須是**主動的集合差集，以 `object_id` 為唯一依據**，在任何「物件要不要進計算」的入口都檢查——不管候選物件是怎麼冒出來的（手動選取、Registry 查 type_id、文件全掃），一律先減掉一式集合才能往下算。一式集合的角色是全域黑名單，不是「電路沒接到就自動不算」的消極結果。

## 4　涵蓋率檢核（防止漏選與重複選）

手動選取的最大風險：同一物件被兩批次選到（算兩次），或某些物件沒被任何批次選到（漏算）。兩種都不會報錯，只會讓數字錯掉，而估價數字錯是要花錢的。

### 4.1 GH 中以三個選取集合表達

```text
全部物件（基準集合）
  ├─ 已選取・已計算   （COUNT/AREA/LEN/VOL 電池吃到的批次）
  ├─ 已選取・一式     （人工標記，不參與計算）
  └─ 未選取           （檢核要抓的對象）
```

一式因此不是額外要維護的文件，而是檢核機制裡的一個合法狀態，跟「已計算」平起平坐，可用顏色 highlight 直接在 GH 裡看到「還沒決定去向」的物件。

### 4.2 四項檢核，衝突要排最前面

```text
1. 已計算 ∩ 一式        → 非空即衝突：同一物件同時被算又被標一式，列出、上色、擋下，不自動決定去留
2. 全部物件 − 已計算 − 一式  → 未選取（漏選）
3. 已計算內部批次互相 ∩    → 重複選取
```

第 1 步要最先做，否則後面兩項檢查會被污染的資料誤導。

行為原則與 `LFTagO`（TAG-O 健康檢查）一致：**只標記，不自動修**，由使用者判斷。

### 4.3 基準集合的兩個候選來源

- **Registry `objects[]`**：有 `type_id`，可以做「這個 Type 通常該用哪個規則」的合理性提示；缺點是若模型改動後未重新 Publish，基準會跟現況脫節
- **Rhino 文件現況掃描**：永遠最新，但沒有 `type_id`，只能做「有沒有被選到」的純粹檢核

建議兩者都留，分開報告：現況掃描做涵蓋率檢核，Registry 做規則合理性提示，兩邊不一致時也標出來——這是 [`MCP評估/初步評估報告.md`](./初步評估報告.md) 第 6.3 節「快照與現況漂移」的具體用途。

## 5　排序

估價單的排序原則會依情境切換：有時以空間為大項，有時以工種為大項，需要視情況採用，不是固定規則。

### 5.1 兩層決定，分開處理

- **外層（空間優先 vs 工種優先）**：全域開關，一份標單只選一種，用 GH 裡的 value list 切換即可，計算邏輯不因此分叉，只是輸出時 group by 順序顛倒
- **內層順序**（哪個空間先、哪個工種先）：無法自動生成——`spaces[]` 沒有樓層高程，型別碼也不代表想要的施工順序。建議做一張**獨立的排序對照表**（`space_display → sort_key`、`type_display_name → sort_key`），專案初始化時建立一次、之後重跑重複沿用；新項目沒在表裡就列最後並標色提醒

排序對照表與計算邏輯解耦，換排序方式不需要動任何計算程式碼。

## 7　刻意排除在工具之外的邏輯

- **損耗率**（磁磚 +5%、木作 +10% 等）：不寫進計算邏輯。損耗率依廠商、專案、市況變動，是商業判斷不是幾何事實。工具輸出淨數量，損耗在 Excel 上以係數欄處理，隨時可改、改了看得見

## 8　尚未討論／待展開（起頭層級，暫不展開）

以下項目已知存在，但尚未討論到可以定案的程度：

1. **輸出服務誰**：內部抓預算用（可能要預填參考單價）、還是對外空白標單用（單價留白）——兩種用途格式不同，尚未確認要哪一種或兩者皆要
2. **同一 Type 是否可能需要不同規則**：目前規則綁在 Type 層級，若同款部件依情境（例如室內／戶外）需要不同量法，現有結構撐不住
3. **SD/DD/CD 多階段重複出量**：LoopFlow 貫穿三個設計階段，量體隨設計發展變動；同一專案不同階段出量時，選取狀態是每次重選還是延續上次調整，尚未討論
4. **GH 原生斷線行為與 LoopFlow 原則不一致**：LoopFlow 一貫「標記斷連、不阻擋」；但 GH 的 referenced geometry 若物件被刪，通常直接報錯甚至讓整個 canvas 停止運算，不是優雅降級。電池內部如何處理單一失效參照，尚未設計
5. **`.gh` 檔案本身的存檔與備份**：程式碼走 git 沒問題，但 `.gh` 是二進位、選取狀態與這些使用者判斷都活在檔案裡，防止意外覆蓋或遺失的備份策略尚未討論
6. **輸出的可追溯性**：估價單對應專案哪個時間點／哪個 `registry_revision`；模型改動後重新出量，新舊版本如何比對差異（哪些項目變了、變多少），尚未討論

## 9　已確認的原則彙整（供後續實作對照）

- 逐物件計算，輸出估價單＋明細兩張表
- 非模型項目（假設工程等）一律人工填寫，不進工具範圍
- 一式不進字典，靠 GH 選取排除；排除以 `object_id` 為準，不依賴電路接線
- 涵蓋率檢核分四態：已計算／一式／未選取／衝突，衝突優先檢查
- 排序拆兩層：外層全域開關（空間優先／工種優先），內層靠獨立排序對照表
- 損耗率不進工具，留在 Excel

## 10　不要做

- 不要在 LoopFlow 字典加入「式」單位或修改 `measurement_rule`／`estimation_unit` 詞彙表
- 不要用「有沒有被接進計算電池」作為一式排除的唯一依據
- 不要讓假設工程等非模型項目混進工具的自動計算範圍
- 不要把損耗率、進位慣例等商業規則寫死進計算邏輯
