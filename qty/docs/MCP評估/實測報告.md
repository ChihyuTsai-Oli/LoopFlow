## 4　新發現的風險

### 4.1 未完成的模態指令會讓 MCP「靜默失效」（原報告 §8 第 1 項的修正）

原報告預期 MCP 碰到 LoopFlow 的模態視窗會「卡住或逾時」。**實測的失敗模式不同，而且更危險。**

在 LoopFlow 指令停在半路（等待使用者操作、尚未取消）時對 MCP 下 `run_python`：

| 觀察點 | 實際行為 |
|---|---|
| 腳本是否執行 | **是**（以寫檔驗證，檔案內容正確） |
| `error` 欄位 | **`null`** |
| `stdout` 欄位 | **空字串** |
| 是否逾時 | **否**，立即回應 |
| `run_csharp` | 同樣失效（故非 Python 專屬，是 RhinoCode 共用輸出擷取層） |
| `list_objects` 等外掛原生工具 | **不受影響，正常運作** |

**意義**：AI 會收到一個「成功但沒有輸出」的回應，沒有任何錯誤訊號可以據以判斷出了問題。這比乾脆卡死危險得多。

這正是 [`數量計算需求筆記.md`](./數量計算需求筆記.md) §4 所警告的失敗類型——「兩種都不會報錯，只會讓數字錯掉，而估價數字錯是要花錢的」。

**應對**：
- 不要對 LoopFlow 產品指令使用 `run_command`（原報告 §10 已列，此處補上具體理由）
- 任何依賴 `run_python` stdout 的自動化流程，都要有「空輸出＝異常」的檢查，不能把空當成成功

### 4.2 外部模組會被 Python 快取住（原報告 §5.3 的必要修正）

原報告 §5.3 的對照表宣稱程式碼住外部 `.py` 的好處包含：

> 「更新工具：改 `.py`，所有 `.gh` 自動吃到」
> 「AI 迭代一輪：直接編輯檔案，秒級」

**照字面實作是錯的。** Python 會把模組快取在 `sys.modules`，GH 重新求解不會重新讀取外部檔案。

實測：修改外部 `.py`（預期值 60 → 120），重新求解後電池仍回傳舊值 `60.0`。

**解法**：薄殼中必須加入 `importlib.reload()`。

```python
import sys, importlib

REPO_SRC = r"<repo>/src"
if REPO_SRC not in sys.path:
    sys.path.append(REPO_SRC)

import loopflow_qty as qty
importlib.reload(qty)          # ← 開發期必要，否則改了程式碼不會生效

result = qty.measure_batch(objects, rule, unit, plane)
```

加上這一行之後，實測「改 `.py` → 只按重新計算（電池程式碼完全不動）→ 吃到新值」完全如原報告所述。

**這一行必須寫進架構文件。** 少了它，實作時會遇到「明明改了程式碼卻沒生效」而難以查覺原因的狀況。

### 4.3 `MCPStart` 會停在 Port 提示（2026-09-01 公司電腦）

同日稍早的實測沒有把「指令打完之後還會問埠號」寫清楚。稍後以 Cursor 連線時，畫面停在：

```
Command: MCPStart
MCPStart Port <10501>
```

少按一次 Enter，指令就一直佔著。此時：

| 觀察點 | 實際行為 |
|---|---|
| `run_python` | `error` 為 `null`、`stdout` 空白（與 §4.1 相同） |
| `run_command` | 回 `Rhino is already running a command` |
| 監聽器 | 可能已寫出公告檔，`list_slots` 甚至能 adopt，但腳本仍無輸出 |

用 `Start-Process Rhino.exe /runscript="MCPStart"` 代跑，也會停在同一個 Port 提示，不能當成已連上。

另外：若上一個 Rhino 的 `listeners\` 公告檔還沒清掉，`MCPStart` 會改問 `10501` 而不是 `10500`。兩個埠都可以用，以 `list_slots` 回傳的 `pid` 對目前 Rhino 為準。

### 4.4 以 MCP 開啟 `.rws` 會弄死監聽器（同日）

對已連上 MCP 的空白文件執行 `-_Worksession _Open "...\LoopFlow_R_MCP.rws"`：

### 5.3 GH referenced geometry 的斷線行為（需求筆記 §8 第 4 項，原標記「尚未設計」）

需求筆記原文推測：

> 「GH 的 referenced geometry 若物件被刪，通常直接報錯甚至讓整個 canvas 停止運算，不是優雅降級。」

**實測推翻了這個推測，但實際行為在數量計算上更危險。**

情境：`Param_Brep` 參照兩個 Rhino 物件 → 接到 `Volume` 元件 → 刪除其中一個物件 → 重新求解。

| 觀察點 | 實際行為 |
|---|---|
| Param 的訊息 | **Warning**（非 Error）：`A referenced Brep could not be found in the Rhino document.` |
| Param 資料筆數 | **仍為 2**（缺失者成為空位，不是少一筆） |
| `Volume` 輸出 | **`None` 與 `306000.0`**，共 2 筆 |
| **`Volume` 元件本身的訊息** | **無錯誤、無警告** |
| 整個 canvas | **繼續運算**（`SolutionState = PostProcess`） |

**意義**：GH 確實優雅降級，但降級得太安靜——

1. 警告只出現在**最上游的 param**，下游元件完全不提示
2. **筆數不變**，所以「數量對不對」的檢查抓不到
3. `None` 會一路傳到計算末端

若下游加總時把 `None` 略過，就會**安靜地少算一筆**。

**應對**：null 檢查必須寫在計算程式碼裡，不能倚賴 GH 的警告傳播。這與需求筆記 §4「涵蓋率檢核」的精神一致，但檢核對象要多加一項：**已選取但參照已失效**。

### 5.4 MCP 能看見上述所有異常（本次最重要的發現）

## 6　幾何量測的核心問題（原報告 §7.2）

本節是本次測試中對實作影響最大的部分。

### 6.1 測試場景

在獨立圖層建立 11 個**已知尺寸**的 Brep（10 個軸對齊、1 個繞 Z 軸旋轉 30°），並寫入符合 2.0 契約的 UserText（`_03_ID編號`、`_11_類型類別`、`_09_空間ID` 等）。測試後已全數刪除。

### 6.2 World bbox 對旋轉物件會安靜地錯一倍

| | World bbox 誤差 |
|---|---|
| 10 個軸對齊物件 | **0.0%**（完全正確） |
| 1 個旋轉 30° 的物件 | **+104.3%** |

旋轉物件真實尺寸 150×80×90，World bbox 量得 **169.9×144.3×90**。體積 1,080,000 → 2,206,266。

**全程無任何錯誤或警告。**

這替原報告 §7.2 所述 `frame.py` 的「封閉 Box 無舊框**不猜** World bbox」提供了具體數據：拒絕不是保守，是不猜就會錯一倍。

### 6.3 使用者指定平面可以完全救回——但給錯也一樣不報錯

| 量法 | 結果（真實為 150×80×90） | 體積 |
|---|---|---|
| ① World bbox（自動猜） | 169.9 × 144.3 × 90.0 | 2,206,266（+104%） |
| ② 使用者給對的平面（30°） | **150.0 × 80.0 × 90.0** | **1,080,000（正確）** |
| ③ 使用者給錯的平面（45°） | 165.6 × 116.1 × 90.0 | 1,730,250（+60%） |

需求筆記 §5.2「手動選取，每批共用平面／軸向輸入」的做法**有效**——但它把「每個物件一個判斷」減少為「每批一個判斷」，**並未消除判斷錯誤時的靜默失敗**。批次內若混入方向不同的物件，或使用者選錯平面，數字一樣會安靜地錯。

### 6.4 建議新增：平面貼合度檢查（兩份文件皆未提及）

**可以用程式抓出「平面選錯」。**

定義：`貼合度 = 該平面下的 bbox 體積 ÷ 物件真實體積`（真實體積由 `VolumeMassProperties` 取得）。

實測結果：

| 物件 | World 平面 | 30° 平面 |
|---|---|---|
| 旋轉 30° 的方塊 | 2.04 ❌ | **1.00 ✅** |
| 軸對齊的方塊們 | **1.00 ✅** | 1.87 ～ 9.68 ❌ |

每個物件都正確辨識出哪個平面適合自己。

**但判準不是「貼合度 = 1」。** 非方塊形狀就算平面正確、貼合度也不會是 1：

| L 型實體（真實方向 30°） | 貼合度 |
|---|---|
| World 平面 | 2.281 |
| 30° 平面（正確） | **1.724**（不是 1.00，因為 L 型填不滿 bbox） |
| 掃描 0–89° 取最小值 | **出現在 30°** ✅ |

**正確的判準是「貼合度在候選角度中最小」**，此規則對方塊與 L 型皆成立。

**這個檢查的極限（必須誠實記錄）**：

- 它能抓出「這個平面不適合這個物件」
- 它**無法決定三個軸中哪個是 W、哪個是 D**——方塊在 0° 與 90° 的貼合度相同
- 因此它是**防呆機制，不是取代使用者判斷**，與需求筆記 §5.2 的設計方向一致

**建議**：計算時對每個物件計算貼合度，若明顯高於同批次其他物件即標示出來，交由使用者判斷。行為與 `LFTagO` 一致——**標記，不自動修**。
