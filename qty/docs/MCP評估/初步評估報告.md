## 1　結論摘要

| 評估對象 | 結論 | 依據 |
|---|---|---|
| 用 AI 自動操作 LoopFlow 產品指令 | **不可行**（且不建議勉強做） | 模態視窗鎖死主執行緒；滑鼠互動無語意；與 2.0 的人為判斷設計相反 |

## 3　評估一：AI 自動操作 LoopFlow 指令 → 不可行

### 3.1 模態視窗會鎖死 MCP（決定性）

MCP 把指令送進 Rhino **主執行緒**執行並等回傳。LoopFlow 幾乎每支產品指令都會彈出 Eto 視窗或 `rs.ListBox` 等待使用者：

| 指令 | 等待人操作的位置 |
|---|---|
| `LFNexus` | 6 步選單、專案名稱輸入、選 Excel 檔視窗、高程數字輸入、重疊衝突清單 |
| `LFCatalog` | 六個動作的常駐面板 |
| `LFTagO` | 可捲動深色面板 |
| `LFTaggerLayoutID` | 核對清單（確認後才寫入） |
| `LFDuplicateLayout` | 份數輸入視窗 |
| `LFAnchorFrame` | 外擴距離輸入視窗 |
| 任一指令首次執行 | 語系選擇視窗 |

視窗一出現，主執行緒停住，MCP 端只會逾時；而且**沒有人去按的話 Rhino 處於卡住狀態**，不是失敗返回。這不是設定問題，是兩邊設計前提相反。

UI 實作位於 `platform/rhino/prompts.py`（Eto ＋ `rs.ListBox`）。

### 3.2 滑鼠互動指令無法用文字驅動

| 指令 | 需要的實體操作 |
|---|---|
| `LFTaggerLaser` | 在 Detail 內「剖面上的正確位置」點一下 |
| `LFTaggerGrab` | 點進 Detail、選來源物件或家具圖塊 |
| `LFAnchorFrame` | 框選線稿 ＋ **恰好一個** Text Dot |

底層是 `Rhino.Input.Custom.GetPoint` / `GetObject`、`rs.GetObject(s)`。即使 MCP 能送座標，AI 也無法判斷「這條線是門框的完成面」。**目標本身無法用文字描述**，不是自動化難度問題。

### 3.3 與 2.0 的設計哲學相反（真正的風險）

`README_zh-TW.md` 明載「每一步、每個動作都需要自己執行……不是黑盒模式」；`LFTagO` 明載「只檢查與上色，不會自動修復」。

LoopFlow 停下來詢問的每一處，都是**刻意保留的設計決策點**：

- 空間框面積重疊 → 列出全部衝突，不自動選
- 物件同時落在兩個空間框 → 拉近畫面讓使用者選
- `LFTaggerLaser` 射線命中多個物件 → 給候選清單
- `LFExtractCP` 已抽取過 → 詢問取代／新增／略過
- `LFTaggerLayoutID` → 核對清單確認後才寫入

AI 在這些位置代答，等於用猜測取代設計意圖。**這是本節最重要的一點：技術上就算可行也不該做。**

### 3.4 破壞性寫入與復原

`LFNexus` 步驟 5 寫入物件 UserText、`LFPublishExchange` 版次 +1 並回寫物件、`LFInfuserPart/All` 覆寫 Tag 顯示欄、`LFDuplicateLayout` 清掉來源綁定——都是破壞性寫入，且 MCP 執行指令的 undo 行為不保證。錯誤只能靠 `.3dm` 備份回復。

### 3.5 環境層風險

| 風險 | 說明 |
|---|---|
| Dropbox 衝突 | 專案資料在 `.3dm` 同層 `_LoopFlow_Config/`；高頻反覆寫入易產生衝突副本，而 `Project_Registry.json` 不可刪 |
| 雙機 | MCP 設定屬「本機專屬、Git 帶不走」，兩台需各自設定 |
| RhinoCode 路徑（有前科） | 2.0.3 才剛修好「指令被 RhinoCode 拷到 `%USERPROFILE%\.rhinocode\stage\` 後找不到 `lib`」。MCP 若以不同方式執行腳本，此坑可能重現 |

### 3.6 架構上留了門（若日後要做）

`features/` 底下的模組把 UI 當成**注入的 callable**，而非寫死的依賴。例如 `features/tagger/laser.py`：

```python
PickTag   = Callable[[RhinoSession], Optional[str]]
PickPoint = Callable[[RhinoSession], Optional[Sequence[float]]]
Probe     = Callable[[RhinoSession, Sequence[float], Sequence[float]], Sequence[dict]]
ChooseHit = Callable[[Sequence[dict]], Optional[dict]]
```

`platform/rhino/memory.py` 的 `MemorySession` 加上 `v2/tests/` 的測試就是靠這個機制跑的（38 支測試中 28 支使用 `MemorySession`）。

> **2026-09-01 實測修正**：本節原本寫「`features/` 底下的模組**不 import** `platform/rhino/prompts.py`」，**這句不正確**。實際上 `features/` 有 **38 處** import `prompts`，分布在 **17 個檔案**。
>
> 但**結論仍然成立**，因為那 38 處**全部位於函式內部**（頂層 0 處），且都在 `_default_*` 這類後備函式裡。真正的接縫在函式簽章——UI 是預設為 `None` 的關鍵字參數：
>
> ```python
> def run_tagger_laser(
>     session, *,
>     pick_tag:   Optional[PickTag]   = None,   # 不傳 → 用 _default_pick_tag（才去 import 彈窗）
>     pick_point: Optional[PickPoint] = None,   # 傳了 → 完全不碰 UI
>     probe:      Optional[Probe]     = None,
>     choose_hit: Optional[ChooseHit] = None,
> )
> ```
>
> 也就是說：注入縫**存在且可用**，但不是靠「模組不 import UI」達成的，而是靠「UI 是參數、且 import 延遲到後備函式被呼叫時才發生」。

**意義**：若未來要讓某支指令可被程式驅動，不需重寫邏輯，只需另寫一組「參數版」注入函式取代 UI 版。成本不高，但**目前沒有需求，不列入計畫**。

> **補充（2026-09-01）**：這條路**現在就能走**，不需要改 LoopFlow 任何一行——MCP 的 `run_python` 可直接 import `features/` 的函式並傳入自訂 callable，完全繞過指令與 UI。2026-09-01 的整場實測即全程使用 `run_python`、未使用 `run_command`。
>
> 附帶澄清一個容易誤解的點：把彈窗改成**指令列**互動**並不會**讓 MCP 能自動執行。`RhinoGet.GetPoint()` 一類的指令列提示同樣在主執行緒同步等待，一樣會卡住 MCP，只是比較容易按 Esc 救回。能被自動化的關鍵是 Rhino 的**腳本模式**（`-` 前綴，如 `-Export`），也就是「所有選項一次以文字參數給足、過程不互動」。

### 3.7 一個必須記錄的矛盾

2.0 的邏輯層已由 `MemorySession` 覆蓋得相當完整；真正缺驗證的是「在 Rhino 裡實際跑起來」那一層——**而那一層正好是 MCP 最卡的模態 UI**。

因此 MCP 對 LoopFlow 本體的價值不在「代替操作」，而在：

1. **唯讀分析**：讀 `Project_Registry.json` ＋ 模型現況，產出檢查報告（零寫入風險）
2. **自動佈置測試場景**：建圖層、放假家具、擺剖面，把實機測試的前置做掉——對應 `../重構進度.md` 待辦「2.0.3 Laser／Grab／Index 尚未實機驗收」；本 repo 已有 `devtools/random_m3d_layers.py` 這類先例

## 4　評估二：AI 操作 Grasshopper → 可行

官方文件載明 AI 可以「開啟 Grasshopper（若未開）、放入正確的元件、連線、solve canvas」，具體包含：

- 尋找元件、放到 canvas、排版
- 拉線建立資料流
- 設定 slider 數值
- 執行求解、讀回結果
- **腳本失敗時回頭檢查 canvas，反覆修正**

關鍵差異：**GH 沒有模態視窗擋路，canvas 狀態可讀**，所以存在完整的「改 → 跑 → 看結果 → 再改」回饋迴圈。這正是第 3 節指令做不到的事。

### 版本岔路（需決定）

| 選項 | Rhino 需求 | 評估 |
|---|---|---|
| GH1（`gh1_` 工具） | Rhino 8 | **建議採用** |
| GH2（`gh2_` 工具） | Rhino 9 WIP/BETA | 暫不採用 |

理由：LoopFlow 2.0 使用者全在 Rhino 8。數量工具若要求裝 Rhino 9 beta 才能跑，等於一開始砍掉使用者。官方有 GH1→GH2 移植指引（`docs/advanced/`），Rhino 9 正式版後再遷移，不算沉沒成本。

## 5　數量計算獨立 repo 的方向

以下為 2026-08-24 討論確認的架構意圖，實作細節後續再議。

### 5.1 單向流程

```text
Rhino 物件 ─┐
            ├→ GH：視覺化檢視、抓取資料、計算 ─→ Excel 表單
JSON ───────┘                                   （與字典 Excel 不同檔）
```

- **與 LoopFlow 完全切開**，GH 純粹作為檢視與輸出資料之用
- **不寫回 Rhino 物件**、不寫回 Registry
- Rhino 模型與 JSON 皆可作為 input
- 輸出的 Excel 是獨立檔案，非字典

### 5.2 手動選取，分類責任在使用者

**不是**自動選取全部 Rhino 物件再分類，而是**使用者手動選取物件後，GH 依這些物件做分析計算**。

這個決定消掉了最難的問題：

| 問題 | 自動分類的處境 | 手動選取的處境 |
|---|---|---|
| W／D／H 對應哪個軸 | 每個物件一個判斷，無法自動決定 | **每批一個判斷**（批次共用平面／軸向輸入） |
| 計量規則從哪來 | 需 `type_id` → `types[]` join | 由使用者選取時指定（電池輸入） |
| 選擇如何持久化 | 需 per-object sidecar 檔 | GH referenced param 自帶 GUID，存在 `.gh` 內 |

**推論**：原先為「每物件持久化座標框」而寫的 `features/dimension/frame.py` 在此做法下大致不需要（見第 7 節）。

### 5.3 py 電池只放 shim，程式碼住外部 `.py`（本節為主要建議）

預計的工作方式是：使用者在 GH 放上 input 電池並接好線，接到一顆**空的 py 電池**，然後交給 AI 處理該電池。

**程式碼不要住在電池裡。** 電池內只放薄殼：

```python
import sys
sys.path.append(r"<repo>/src")
from loopflow_qty import measure_batch

result = measure_batch(objects, rule, unit, plane)
```

| | 程式碼在電池內 | 程式碼在外部 `.py` |
|---|---|---|
| `git diff` | 埋在 `.gh` 二進位，看不到 | 正常 diff |
| 測試 | 只能開 Rhino 手動跑 | `python test_*.py` 直接跑 |
| AI 迭代一輪 | 需透過 MCP 寫進電池 | 直接編輯檔案，秒級 |
| 更新工具 | 每個專案的 `.gh` 都要重貼 | 改 `.py`，所有 `.gh` 自動吃到 |
| 多 AI 接手 | 看不到前一個做了什麼 | commit 說明一切 |

最後一列對本工作區特別重要：多個 AI 輪流接手依賴 commit diff，程式碼一旦進入 `.gh` 二進位，交接鏈即斷。

### 5.4 MCP 的角色因此縮小（而且更健康）

程式碼走外部檔案後，MCP **不負責寫程式**，只負責：

- 讀 canvas，確認實際接線與預期一致
- 回答「這樣接對不對」時看得到真實狀態
- 執行後讀結果驗證

**副作用**：整條路不再押注在 MCP 上。MCP 目前僅 0.1.3，若讀 canvas 不穩，改用截圖或文字描述即可繼續工作——只是慢一點，不會停擺。

### 5.5 動工前唯一必須先定的事：py 電池的輸入簽章

接線之前先講定每個輸入的**名稱、型別、access（item／list／tree）**，接一次就到位。

**第一版建議全部使用 flat list，不使用 tree**：

- 一顆電池處理一批同規則物件
- 要處理三個類別就放三顆電池，不用 tree 分支
- Tree 分支結構若判斷錯誤，數字會錯得很安靜——在數量計算上是最糟的失敗模式

流程跑順之後再考慮是否收斂成 tree。

### 5.6 GH re-solve 寫檔陷阱

**不要讓 GH 元件負責寫 Excel。** GH 元件在每次 re-solve 都會執行；調整任何上游輸入都會觸發寫檔，反覆覆寫，Excel 開著時還會撞檔案佔用。

建議切成兩段：

| 段 | 位置 | 職責 |
|---|---|---|
| 前段 | GH | 量幾何、上顏色、收集選取與選擇 |
| 後段 | Rhino 指令（純 Python） | 讀輸入 → 計算 → 寫 Excel |

後段不需要 GH 也不需要幾何，寫檔變成「使用者按一下才發生」，而非 re-solve 的副作用。`features/registry/publisher.py` 已有檔案佔用短重試的先例可循。

### 5.7 顏色 highlight 的做法

用 **Custom Preview 疊加**顯示顏色，不要改動 Rhino 物件本身的顯示屬性。原始物件完全不動，符合單向流程，也不會在 `.3dm` 留下需要清理的痕跡。

## 6　與 LoopFlow 的邊界

### 6.1 單向流程使互鎖風險不存在（但必須記錄）

`foundation/usertext.py:51` 有一份 `STALE_OBJECT_KEYS`：

```python
# 2.0 不再寫尺寸／數量／座標框；Apply 時清掉面板上的殘留。
STALE_OBJECT_KEYS = (
    "_05_寬度W", "_06_深度D", "_07_高度H", "_09_實作數量",
    "_14_座標框", "_19_座標框",
    "Q_01_寬度W", "Q_02_深度D", "Q_03_高度H", "Q_06_實作數量",
    "lf_dimension_w", "lf_dimension_d", "lf_dimension_h",
    "lf_quantity", "lf_local_frame",
)
```

兩個消費者：

1. `clear_stale_object_text()` — `LFNexus` 步驟 5 寫入時**清空**這些 key
2. `features/model_data/verify.py:_stale_notes()` — 步驟 6 檢核時把這些 key 回報為 `stale_dimension` **問題**

**若日後有人讓數量工具把結果寫回物件這些 key，會造成互鎖**：

```text
檢核不通過 → LFPublishExchange 被擋（前置要求步驟 6 通過）
           → 產不出新 Registry → 而 Registry 是數量工具的輸入來源
```

且症狀出現在 LoopFlow 側（「檢核一直報 stale dimension」），不易聯想到數量工具。**目前採單向流程，不寫回物件，此風險不存在；本段僅作為未來變更時的警告。**

### 6.2 Registry 可提供什麼（若採用 JSON 輸入）

`features/registry/schema.py`（`loopflow.registry` v1）：

| 區塊 | 可用欄位 |
|---|---|
| `types[]` | `type_id`、`type_category`、`type_sequence`、`type_display_name`、`layer_path`、**`estimation_unit`**、**`measurement_rule`**、`elevation_basis`、`construction_default`、`remarks_default` |
| `spaces[]` | `space_id`、`level_id`、`space_display` |
| `objects[]` | `object_id`、`type_id`、`type_category`、`type_sequence`、`type_display_name`、`construction_status`、`space_id`、`space_display`、`elevation_basis`、`elevation_value`、`elevation_display`、`remarks`、`data_revision` |
| 根層 | `project_id`、`registry_revision`、`published_at`、`model_unit` |

重點：

- **`measurement_rule` 與 `estimation_unit` 只在 `types[]`**，不下放物件。從 Rhino 物件 UserText 抓不到規則，物件上只有 `type_id`
- `FORBIDDEN_OBJECT_KEYS = (dimension_w, dimension_d, dimension_h, quantity, local_frame)` — Registry schema 主動拒收尺寸與數量
- `objects[]` 的 `object_id` 是回頭抓 Rhino 物件的橋樑，也是顏色 highlight 的依據
- 若採用 JSON 輸入，輸出的 Excel 應蓋上 `registry_revision`，供日後追溯「這份數量是哪一版模型算的」

### 6.3 快照與現況會漂移

Registry 是發布當下的快照，幾何是現況。若採用 JSON 輸入，至少要處理：

- Registry 有 `object_id` 但模型找不到 → **回報，不可靜默略過**（否則少一筆而無人知）
- 模型有物件但不在 Registry → Publish 之後新增，提示需重新 Publish

行為應與 `LFTagO` 的「斷連」一致：**標出來，不自動修**。

### 7.4 架構紅利

因為單向、不碰物件、Excel 為純 stdlib，計算核心可以完全不依賴 Rhino：

```text
選取結果 ＋（可選）Registry JSON  →  計算  →  .xlsx
```

**需要開 Rhino 才能驗的部分被壓縮到只剩幾何量測與顏色顯示**，其餘全部 headless 可測。這正好對沖掉「GH definition 沒有測試框架」的顧慮——邏輯不在 canvas 上，canvas 只是眼睛。
